# [하위 페이지] om-verify — 정의·논의 정리 (2026-09-02: 완성·verified)

## 1. om-verify가 하는 일

**om-apply가 반영한 후보를 실제로 빌드·기동해, "계획대로 반영됐고 은행 기능이 실제로 동작하는지"를 결정론 검사로 확인**한다.

- 직전: om-apply(코드 반영) → **om-verify(실제 실행·대조)** → 다음: om-report(요약, 미착수).
- om-plan/apply가 못 하는 "실제 실행·화면 확인"을 담당. 판정은 검사기가 하며 재해석하지 않는다.

### 핵심 용어
- **build receipt**: 후보를 빌드해 만든 이미지·산출물이 그 후보 코드에서 나왔음을 봉인값으로 증명.
- **fixture**: 계약 테스트가 볼 표본 데이터(확장 컬럼·실패 단언·쿼리 등)를 기동한 환경에 심는 것.
- **계약 테스트(contract test)**: 은행 커스텀 ID별로 "이 동작이 실제로 되는가"를 검증하는 필수 테스트. 검사기 저장소에 실물이 있음.
- **verified / infra_error / failed**: 검사기 최종 판정. verified만 성공, 배포 승인은 별개.

## 2. 진행 상태

- **완성 + verified.** 설계·구현·한글화·독립 검증까지 마치고 GitLab 배포. 스킬 문서는 claude-skill-author로 저작·감사 통과.
- **실전 실적(1.13.1→1.13.2)**: 후보를 실제 이미지로 빌드 → build receipt 발행 → 격리된 새 환경 기동 → fixture 적용 → **필수 계약 테스트 9종 전부 통과**(API 4·브라우저 3·정적 2), skip·error·flaky 0, retries 0. 실제 브라우저(playwright)로 은행 화면(확장 컬럼 고객번호/CUST_MASTER/PII·실패 단언 행·한글 IME 조합)까지 확인.
- **최종 판정 verified** — receipt digest 봉인, 게이트 전부 통과.

## 3. 실전에서 나온 검사기 보강 2건

- **verify 시작조건 정밀화**: apply가 남긴 관리 파일 미커밋 변경이 있어도, 그 내용이 apply 기록과 정확히 일치하면 검증 시작 허용(그 외는 차단). apply 성공조건과의 배타 모순 해소.
- **계약 실행 규약 2건**: ① 서버 주소 전달 규약 통일(엔진이 API 경로로 조립) ② 커넥터 계약 테스트가 보는 파일 위치를 1.13.2 구조로 갱신(기능은 이미 이관됨). 이 둘로 첫 실행의 8종 실패가 재주행에서 전부 통과.
- 둘 다 반례 테스트 동반·MR merge. 상세: `시연자료/수정핫픽스_전체정리.md`.

## 4. 남은 것 (사람 결정)

- **UI 표시 일치 검증**: 현재 `ui_presentation_consistency` 게이트는 not_configured(UI 부품 미제공). test-agent를 결속하면 화면 표시 일치까지 실제 판정. 시연 재주행 때 포함 권장.
- **관리 파일 커밋**: 검증된 후보를 만든 관리 파일 변경이 미커밋 상태 — 등록자료 확정하려면 커밋 승인.
- **배포**: verified는 동작 검증까지이고 실서버 반영은 별개 승인.

## 5. 설계 근거 (참고)

- 계약 테스트는 검사기 저장소 루트 기준으로 해석(`suite_digest`). 제품 저장소엔 tests/가 없는 게 정상.
- build receipt는 현재 local-issued(발행자 정직에 의존) — 서명화는 개선 백로그(#16).
- 화면 검증 2층: ① 계약 테스트 안의 playwright(특정 요소 확인, 이미 통과) ② ui_presentation_consistency 게이트(test-agent 형식, 사람 검수 결속까지 — 미결속).
