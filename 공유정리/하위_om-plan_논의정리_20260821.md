# [하위 페이지] om-plan — 정의·모드·산출물·논의 정리

> 자동화 파이프라인의 1단계인 **om-plan(계획)**에 대한 정리 페이지입니다. 무엇을 하는지, 4가지 모드를 언제 쓰는지, 각 모드가 무엇을 만들어내는지(산출물), 그리고 설계 과정에서 내린 주요 결정을 담습니다.

---

## 1. om-plan이 하는 일

OpenMetadata 커스터마이징을 **등록·수정·버전업**할 때, **사람이 검토·승인할 수 있는 "변경 계획서(proposal)"를 만들고, 그 계획서가 규칙에 맞는지 검사기가 검증**합니다.

- **실제 코드나 등록 정보를 바꾸지 않습니다.** 계획서를 만들고 검증하는 데까지입니다.
- 검증은 **결정론 검사기**(LLM을 타지 않는 규칙 프로그램)가 합니다. 검사기는 저장소를 직접 훑어 "사실(discovered-facts)"을 스스로 재계산하고, LLM이 쓴 계획서를 그 사실과 대조합니다. 그래서 LLM이 사실을 지어내거나 속일 수 없습니다.

### 핵심 용어

- **커스터마이징(customization)**: 은행이 OpenMetadata에 넣은 개별 개조 기능. 각각 `BANK-OM-001` 같은 고유 ID를 가집니다.
- **매니페스트(Manifest)**: 커스터마이징 하나가 **어떤 파일을 바꾸는지** 등을 적은 명세 파일.
- **계약(Contract)**: 그 커스터마이징이 **지켜야 할 동작(불변식)** 과 그것을 확인하는 **필수 테스트**의 묶음.
- **discovered-facts**: 검사기가 저장소를 직접 계산해 만든 사실 데이터.
- **proposal**: LLM이 작성한 등록/변경 계획 문서 묶음.
- **plan check 판정**: 검사기가 proposal을 사실과 대조한 결과(아래 5가지 상태).

> 위 관리 파일들(매니페스트·계약·등록 명단·공유 파일 등)의 **실제 예시**는 같은 폴더의 **`참고_관리파일_실제예시_20260821.md`**에 하나씩 있습니다.

### 검증 결과(판정) 5가지

1. **통과** — 계획서가 규칙을 모두 만족.
2. **검토 준비됨(approval)** — 계획서는 유효하고, 이제 사람이 검토할 차례. *배포 승인이 아니라 "검토 준비"라는 뜻.*
3. **조건부(사람 결정 대기)** — 담당자 미정 등 사람이 정할 항목이 남음.
4. **차단(block)** — 규칙 위반. 계획서를 고쳐 다시 검증.
5. **검증 불가(analysis_error)** — 사실 수집·검증 자체가 실패. 원인 보고 후 중단.

## 2. 4가지 모드 — 언제 쓰나 / 무엇을 만드나

om-plan은 요청 파일의 `mode` 값에 따라 4가지로 동작합니다.

### 2-1. initial — 최초 등록

- **언제 쓰나**: 등록부가 아직 없고, **공식 버전 대비 현재 커스텀 코드에 무엇이 들어갔는지 처음으로 전수 식별**해 등록할 때.
- **입력**: 공식 버전 커밋, 현재 커스텀 커밋, (담당자).
- **검사기가 계산하는 사실**: 커밋 인벤토리(커밋별 커스터마이징 ID·바뀐 경로), 공식→커스텀 순변경 경로.
- **산출물(역할·정의)**:
  - **매니페스트 초안**: 커스터마이징별로 "이 기능이 바꾼 파일 목록"을 커밋 사실에서 모은 명세.
  - **판단 항목(decisions)**: 각 커스터마이징을 왜 이렇게 등록하는지의 결정. 근거는 실제 커밋(관찰).
  - **공유 영향(shared_impact)**: 바뀐 파일이 여러 기능이 공유하는 파일이면 그 소유 지분을 선언.
  - **미해결 질문**: 담당자 미정, 업무 정상 조건 미정 등 사람이 정할 항목.

### 2-2. feature — 신규 기능 추가

- **언제 쓰나**: 기존 등록에 **없던 새 커스터마이징을 추가**할 때.
- **입력**: 새 커스터마이징 ID(기존에 없어야 함), 새 기능의 근거, (담당자).
- **산출물(역할·정의)**:
  - **새 매니페스트 초안**: 새 기능이 바꿀 파일 목록과 목적.
  - **명단 항목 초안**: 새 ID의 제목·상태·중요도.
  - **재사용 판단**: 기존 기능·공유 코드와 겹치는지 확인하고, 겹치면 공유 영향으로 지분 선언.
  - **계약 초안**: 새 기능이 지켜야 할 동작 + 그것을 확인할 테스트.
  - **미해결 질문**: 담당자·재사용 범위 등.

### 2-3. change — 기존 기능 수정

- **언제 쓰나**: **이미 등록된 커스터마이징을 수정**할 때. 두 갈래가 있습니다.
  - **pre_plan**: 아직 코드를 안 고친 상태에서 "무엇을 어떻게 바꿀지" 계획.
  - **post_change_reconcile**: 이미 코드를 고친 뒤, 실제 변경을 등록과 대조해 정합을 맞춤.
- **입력**: 대상 커스터마이징 ID(등록돼 있어야 함), 두 갈래 중 하나, (post_change_reconcile이면 변경 전/후 커밋).
- **산출물(역할·정의)**:
  - **변경 계획(pre_plan) / 변경 정합(post)**: 수정의 범위·방식.
  - **매니페스트 변경분(delta)**: 바뀐 파일 목록의 **차이분만**.
  - **재실행할 계약·테스트**: 이 수정으로 영향받는 계약과 그 필수 테스트 목록.
  - **공유 영향**: 바뀐 파일이 공유 파일이면 소유 지분 선언.
  - **미해결 질문**.

### 2-4. upgrade — 버전 업그레이드

- **언제 쓰나**: 공식 OpenMetadata를 **인접한 다음 버전으로 올릴 때**(예: 1.13.1 → 1.13.2). 커스터마이징이 받는 영향을 정리하고 이동·재적용 계획을 만듦.
- **입력**: 인접 정책(고정), base/target 버전, 배포 방식, 공식 문서(1건 이상, 원문 포함), 공식 base/target 커밋 + 현재 커스텀 기준.
- **검사기가 계산하는 사실**: 공식 버전이 바꾼 경로(수백~수천 개일 수 있음), 공식 문서 원문 스냅샷.
- **산출물(9종, 모두 다뤄야 하며 해당 없으면 사유 명시)**:
  1. **공식 문서 발견사항**: 공식 문서 원문에서 뽑은 요구사항.
  2. **문서-코드 대조**: 문서 설명과 실제 코드 변경이 맞는지 대조.
  3. **업그레이드 계획**: 이동·대체·충돌 처리 계획.
  4. **경로 이동표(path-remap)**: 커스텀 코드가 새 버전에서 어디로 옮겨가는지의 대응표.
  5. **매니페스트 변경분**: 각 커스터마이징 명세의 변경분.
  6. **공유 코드 정의 이동분**: 공유되는 코드의 위치 이동 차이분.
  7. **재실행할 계약·테스트**: 버전업 후 다시 돌려야 할 계약과 테스트.
  8. **운영 작업**: 데이터 마이그레이션·재색인·설정 변경 등.
  9. **미해결 질문**: 사람 결정 항목.

## 3. 진행 상태

- **반영·검증 완료**: 논의사항 1~8. → om-plan(계획 단계)은 기능적으로 완성.
- **남은 것**: 실제 파이프라인 검증 후 배포. 논의사항 9·10은 **사람 결정 대기**. 이후 단계(코드 반영·검증·요약)는 별도 구현 예정.

## 4. 사람이 내린 결정 · 나중으로 미룬 것 (요약)

> 사람이 직접 판단한 것과 나중으로 미룬 것을 한눈에 모았습니다. 상세는 아래 부록(논의사항) 참조.

| 항목 | 사람이 정한 것 · 상태 |
|---|---|
| 정상 계획을 자동화 시스템에서 "성공"으로 처리 (논의 6) | ✅ 확정 |
| 버전업 필수 산출물·문서 요구사항 누락을 여러 겹으로 강제 (논의 7) | ✅ 확정 |
| 변경된 파일 개수는 "변경 전 릴리즈" 기준으로 계산 (논의 8) | ✅ 확정 |
| 테스트 등록 통로: **3개 안 중 "계약을 통해서만"(3안) 채택** (논의 3) | ✅ 확정 |
| 수정 시 필수 테스트 누락은 계획 단계에서 차단 (논의 2) | ✅ 확정 |
| 동작 변경 자동 판정은 안 함 / 기준선 잠금은 뒤 단계로 미룸 (논의 1) | ⏳ 임시 — 재검토 예정 |
| 기준선을 "릴리즈 때만" 갱신, 동시작업은 별도 브랜치 (논의 1) | ⏳ 임시 — 재검토 예정 |
| 버전업 후 "기준 버전" 갱신을 어느 단계에서·어떻게 (논의 9) | ⬜ 미결 — 사람 결정 대기 |
| "등록 안 된 변경" 검사를 파이프라인 어디에 연결할지 (논의 10) | ⬜ 미결 — 사람 결정 대기 |
| 설정의 빈 "직접 테스트" 칸 제거 (논의 3) | ⏳ 나중으로 미룸 |
| 실제 파이프라인 검증 전 배포 (논의 11) | ⏳ 검증 후로 보류 |

## 5. (부록) 설계 과정에서 내린 주요 결정 — 논의사항 (상세)

> 무엇이 문제였고, 어떻게 정했는지의 기록입니다.

### 논의사항 1 — 커스터마이징을 수정했을 때 "동작이 실제로 바뀌었는지"를 계획 단계에서 자동 판정할 수 있는가

- **문제**: 수정이 "단순 정리(변수명 변경 등)"인지 "실제 동작 변경"인지에 따라 필요한 검증이 다릅니다. 이를 계획 단계에서 자동으로 가리고 싶었습니다.
- **확인한 사실**: 자동 판정을 하려면 "수정 전 상태(비교 기준 커밋)"가 필요한데, 이 기준을 **작업자가 요청서에 직접 지정**하는 구조입니다. 기준을 유리하게 고르면 변경을 없어 보이게 만들 수 있어, 자동 판정을 신뢰할 수 없습니다.
- **사람이 판단한 것(여러 안 중 선택)**:
  - 계획 단계에서는 동작 변경 여부를 **자동 판정하지 않는다.** 대신 논의사항 2(필수 테스트 누락 방지)만 검사기로 강제하고, 실제 동작 변경 여부는 **실제 실행 단계와 사람**이 본다.
  - "비교 기준을 고정해 조작을 막는 장치(기준선 잠금)"는 **실제 코드 반영 단계가 열린 뒤로 미룬다.** (지금은 검사기만 손대는 게 안전하고, 잠금은 반영 단계 없이는 완성 못 하기 때문.)
  - 그 기준선은 **매 변경마다가 아니라 "릴리즈 때만" 갱신**하기로 정했다. 동시 작업은 각자 **별도 브랜치**로 처리한다. *(이 잠금 관련 결정은 임시이며 나중에 재검토 대상.)*

### 논의사항 2 — 등록된 커스터마이징을 수정할 때, 그 커스터마이징에 딸린 필수 테스트를 실행 목록에서 누락하는 것 차단

- **문제**: 코드를 수정하면서, 원래 그 기능을 지키던 필수 테스트를 계획서의 실행 목록에서 빠뜨릴 수 있습니다.
- **결정**: 그 커스터마이징에 등록된 필수 테스트가 계획서의 실행 목록에 **하나라도 빠져 있으면 차단**합니다. (실제 실행·통과 확인은 뒤 단계가 하고, 계획 단계는 "목록 누락"만 막습니다.)

### 논의사항 3 — 커스터마이징의 테스트를 등록하는 통로를 "계약을 통한 등록" 하나로 통일

- **문제**: 테스트를 등록하는 경로가 두 갈래(계약을 통해 / 매니페스트에 직접)로 나뉘어 있어, 두 곳의 목록이 어긋날 수 있었습니다.
- **사람이 세 가지 안을 두고 판단**:
  1. 두 통로를 모두 인정하되 양쪽 목록을 일치시킨다.
  2. 직접 통로에 전용 의미를 부여해 문서·검사기에 명시한다.
  3. 직접 통로를 없애고 **"계약을 통한 등록" 하나로 통일**한다.
- **확인한 사실**: 직접 등록 통로는 실제로 아무 커스터마이징도 사용하지 않고 비어 있었습니다.
- **결정(사람)**: **3안 채택** — 직접 통로를 없애고 계약을 거쳐서만 등록. (쓰지도 않는 통로를 살리는 것보다 하나로 정리하는 편이 명확.)
- **나중으로 미룬 것**: 설정 파일에 남은 빈 "직접 테스트" 칸 자체는 지금 지우지 않고 남겨둠(등록자료 정리를 몰아서 할 때 제거).

### 논의사항 4 — 커스터마이징별로 "어떤 파일·계약·테스트와 연결되는지"의 관계를 뭉개지 않고 보존

- **문제**: 각 커스터마이징이 어떤 파일·계약·테스트와 연결되는지가, 사실을 계산하는 과정에서 **여러 기능이 하나로 합쳐져** 사라지고 있었습니다.
- **결정**: 기능별 연결 관계를 **하나하나 분리해 보존**합니다. 그래야 뒤 단계 검증이 "이 기능은 이 파일·이 테스트와 연결" 하고 정확히 대조할 수 있습니다.

### 논의사항 5 — 계획서(proposal) 필드의 자료형(type) 오류를 자동 차단

- **문제**: 계획서를 쓸 때 필드의 자료형 오류(예: 목록이어야 할 칸에 문자열 하나를 넣음)가 조용히 통과될 수 있었습니다.
- **결정**: **필드의 자료형을 검사**해 잘못된 형식은 차단합니다. 단, 이 검사는 "형식이 맞는가"만 보며, **"내용이 옳은가"는 다른 검사와 사람**이 판단합니다(형식 검사와 내용 판단은 역할이 다름).

### 논의사항 6 — 계획 검사가 낸 "검토 준비됨" 결과를 CI(자동화 시스템)가 실패로 오해하는 문제

- **문제**: 계획 검사의 정상 결과는 대부분 "검토 준비됨"인데, CI 자동화 시스템은 기본적으로 이 결과를 **실패(빨간불)로 처리**합니다.
- **결정**: "검토 준비됨"을 **성공으로 처리**하되, "자동 배포됨"이 아니라 **"검토 대기"** 상태임을 함께 표시합니다. 계획 단계는 실제로 아무것도 바꾸지 않으므로 성공 처리해도 안전합니다.

### 논의사항 7 — 버전 업그레이드 시 필수 산출물과 "문서상 요구사항 누락"을 강제로 검증

- **문제**: 버전업 때는 코드 이동뿐 아니라 **문서에만 적힌 요구사항**(예: "기동 전 데이터 마이그레이션 필요")을 놓치면 운영에서 장애가 납니다. 이런 누락은 코드 테스트로도 안 잡힙니다.
- **결정**: 단순히 "항목이 있는가"만 확인하지 않고 여러 겹으로 강제합니다 — (1) 영향받는 경로를 빠짐없이 다뤘는지 검사기가 기계적으로 확인, (2) **원문서를 다시 읽는 별도의 독립 검토**가 계획서에서 빠진 요구사항을 잡아냅니다.

### 논의사항 8 — 커스터마이징으로 변경된 파일 개수를 어느 시점 기준으로 세는가

- **문제**: "변경된 파일 개수"를 어느 시점 기준으로 세느냐에 따라 값이 달라집니다(변경 전 릴리즈 기준 vs 현재 작업 상태 기준).
- **결정**: **변경 전 릴리즈(등록 기준 스냅샷)** 를 기준으로 셉니다. 처음에는 이 값이 어긋난 것을 오류로 봤으나, 두 값은 기준 시점이 달라 **원래 다른 것이 정상**임을 확인했습니다.

### 논의사항 9 — 버전 업그레이드 후 등록부의 "기준 공식 버전" 정보를 새 버전으로 갱신(재베이스)하는 시점과 방법

- **문제**: 새 버전으로 올린 뒤, 등록부가 가진 "기준 공식 버전" 정보(기준 버전 태그·커밋·변경 파일 목록 등)를 새 버전으로 갱신해야, **다음 버전업이 올바른 기준에서 비교**됩니다. 이걸 안 하면 계속 옛 버전을 기준으로 착각합니다.
- **확인한 사실**: 이 갱신은 "실제 코드가 새 버전 위에 올라간 뒤"에만 정확히 계산되므로, **계획 단계 혼자서는 할 수 없고** 뒤 단계(코드 반영 이후)에서 처리해야 합니다.
- **상태**: 어느 단계에서 어떻게 갱신할지는 **사람 결정 대기**(권고안 있음).

### 논의사항 10 — 코드에는 변경이 있으나 어떤 커스터마이징에도 등록되지 않은 변경(등록 누락)을 파이프라인에서 차단

- **문제**: 시간이 지나면, 코드에는 변경이 있는데 **"이건 어느 커스터마이징의 변경"이라고 등록되지 않은 누락**이 생길 수 있습니다.
- **확인한 사실**: 이런 등록 누락을 잡는 검사는 이미 일부 존재하지만, **계획 명령에 자동으로 연결돼 있지는 않습니다**(별도 도구에만 있음).
- **상태**: 이 검사를 파이프라인 어느 지점에 연결할지 **사람 결정 대기**.

### 논의사항 11 — 실제 파이프라인 검증 전 배포 보류, 기록 원천 저장소 일원화

- **문제**: 검증 완료분을 서둘러 배포하면, 실제 CI 파이프라인에서 한 번도 돌려보지 않은 상태로 올라갑니다.
- **결정**: **실제 파이프라인 검증(정상 계획이 통과로 처리되고 4모드가 전부 통과)** 전에는 배포하지 않습니다. 또한 설계·기록의 원본은 한 저장소를 원천으로 두고, 배포처에는 **실제로 동작하는 도구 파일만** 보냅니다.
