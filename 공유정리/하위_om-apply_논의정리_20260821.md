# [하위 페이지] om-apply — 정의·논의 정리 (설계 단계)

> 자동화 파이프라인 2단계인 **om-apply(반영)**의 정리 페이지입니다. **아직 구현 전, 설계·결정 단계**입니다. 무엇을 할지와 설계 과정에서 내린 결정을 담습니다. (om-plan 하위 페이지와 같은 형식)

---

## 1. om-apply가 하는 일 (예정)

**om-plan이 만든 "계획"대로 LLM이 실제 코드를 작성·반영하고, 그 과정에서 관리 파일(매니페스트 등)을 함께 최신으로 유지**합니다.

- 직전: **om-plan(계획)** → om-apply(코드 작성) → 다음: **om-verify(실제 테스트 실행)**.
- om-apply는 **테스트를 실제로 돌리지 않습니다.** "계획대로 구현했고, 코드와 관리 파일이 서로 맞다"까지 증명하고, **실제 동작 확인은 다음 단계(verify)**로 넘깁니다.
- om-apply의 끝 상태 = **"정적으로는 일치, 실제 동작은 검증 대기"**. (배포 승인 아님.)

### 핵심 용어
- **계획**: om-plan이 낸 승인 산출물. 그 안의 **후보 관리 파일(매니페스트)**이 "이 커스텀이 바꿀 파일 목록"을 정함.
- **관리 파일 싱크**: 실제 코드와 관리 파일(매니페스트·레지스트리 등)이 항상 일치하도록 함께 유지하는 것.

## 2. 진행 상태

- **설계 초안 + Codex 적대검토 완료.** 검토에서 P0(치명) 3건 등 발견 → 설계 수정 방향 확정(아래 논의사항 반영).
- 다음: 검토 결과를 설계에 반영 → 구현 지시서 → 구현.

## 3. 사람이 내린 결정 · 나중으로 미룬 것 (요약)

| 항목 | 정한 것 · 상태 |
|---|---|
| 방식: LLM이 코드까지 작성(A) vs 개발자 변경 등록(B) → **A** | ✅ 확정 |
| 관리 파일 싱크를 **3방향(계획·실제변경·관리파일) 독립 대조**로 | ✅ 확정 |
| 계획 밖 변경(민감=STOP): **v1 = 사유 작성 → 사람 승인** | ✅ 확정 |
| 독립 검토 sub-agent(사유 자기변호 방지) | ★ 우선순위 0 향후 개선 (v1 직후) |
| 위 중 '안전 유형 자동 통과' 도입 여부 | ⏳ 검토 중 (미확정) |
| 끝낼 때 실행 검사: **컴파일·생성기 같은 빠른 검사 포함**(전체 테스트는 verify) | ✅ 확정 |
| 업그레이드 병합 실패: **LLM이 고쳐보기 → 안 되면 재계획 → 그래도 안 되면 사람** | ✅ 확정 |
| 예전 apply: 통째 재활용 ❌, **안전 부품만 부분 재활용** | ✅ 확정 |
| 두는 위치: **깨끗한 배포본에 편입** | ✅ 확정 |
| "계약(업무 규칙) 충족" 판정은 om-apply에서 **통과로 안 침**(주장만, 실제 확인은 verify) | ✅ 확정 |

## 4. (부록) 설계 과정에서 내린 결정 — 논의사항 (상세)

### 논의사항 1 — 코드를 누가 작성하나 (LLM인가, 개발자인가)
- **문제**: om-apply가 "LLM이 계획대로 코드를 직접 작성"하는 것인지, "개발자가 이미 만든 변경을 등록만" 하는 것인지에 따라 성격이 완전히 갈린다. (기존 코드는 후자였다.)
- **결정**: **LLM이 코드까지 작성**한다. 개발자가 미리 만들 필요 없이, 계획을 받아 LLM이 구현.

### 논의사항 2 — 관리 파일이 코드와 맞는지 어떻게 믿나 (가장 중요)
- **문제**: 코드와 관리 파일을 **같은 LLM**이 쓴다. 둘 다 틀리게 써도 **둘끼리는 일치**할 수 있다. 예: 계획에 없던 파일을 실수로 고치고 그걸 매니페스트에도 슬쩍 추가 → "코드=매니페스트"는 통과하지만 **승인 안 된 변경이 정식 범위로 세탁**됨.
- **결정**: 두 개(코드·매니페스트)만 비교하지 말고 **세 개를 독립 대조** — ①승인된 계획 ②실제 코드 변경(진짜 Git 기록) ③최종 관리 파일. 셋이 어긋나면 조용히 맞추지 않는다.

### 논의사항 3 — 계획 밖 변경이 생기면 (범위 이탈)
- **기본 지시(스킬 md에 명시)**: LLM은 **최대한 승인된 계획(후보 매니페스트) 범위 안에서만 개발**한다. 범위 밖은 **예외이며 최소화**한다. (이게 1차 방어선 — 이탈 자체를 드물게 만들어 아래 승인 흐름 부담을 줄인다.)
- **문제**: 그래도 개발하다 보면 계획 밖 파일을 건드리게 될 수 있다 — 불가피하게 생김. 이걸 조용히 매니페스트에 추가하면 논의사항 2의 세탁 구멍이 된다.
- **결정(확정)**: 계획 밖 경로는 **멈추고 승인.** 처리 방식:
  - **민감 경로**(보안설정 등) → 그냥 **STOP**.
  - **그 외 계획 밖 경로** → LLM이 **구조화된 사유**를 쓴다: ①어떤 기능을 반영 중이었나 ②기존엔 왜 안 건드려도 작동했나 ③이번엔 왜 꼭 수정해야 하나 ④근거(실제 코드/사실 위치).
- **v1(지금 구현) = 사유 작성 → 사람이 직접 승인.** 핵심 안전(3방향 대조·STOP·사람 승인·verify)은 이걸로 성립.
- **★ 우선순위 0 향후 개선(v1 직후 첫 작업) = 독립 검토 sub-agent 추가.** 사유를 쓴 LLM의 **자기변호 구멍**을, 코드를 안 쓴 **별도 LLM이 사유↔실제 변경을 검토**해 막음(om-plan 독립 2차 판독과 같은 패턴). 정직한 한계: 이것도 LLM이라 ground truth 아님 → 최종 안전망은 verify.
- **v1의 잔여 위험(명시)**: sub-agent 전엔 "LLM이 자기 변경을 자기 사유로 정당화"하는 위험이 남음. 사람 승인 + verify로 받치되, sub-agent 도입으로 굳힘.
- **검토 중(미확정)**: 안전 유형(생성물·DB짝·다국어 전파 등) **자동 통과** 도입 여부 — 실제 이탈 사례 보며 정함.

### 논의사항 4 — 끝낼 때 어디까지 검사하나
- **문제**: 실제 테스트 전체 실행은 다음 단계(verify)인데, om-apply가 아무 실행도 안 하면 엉뚱한 코드도 그냥 넘어간다.
- **결정**: **컴파일·코드 생성기 같은 "빠르고 싼 검사"까지는 om-apply에서** 한다(엉터리 코드 조기 차단). 테스트 전체 실행·통과는 verify.

### 논의사항 5 — 업그레이드 자동 병합이 동작을 망가뜨렸을 때
- **문제**: 새 버전 위로 커스텀을 옮길 때 Git이 **충돌 없이 합쳐도** 커스텀 기능이 사라질 수 있다(경고 없이). 이걸 "수용 검사"(꼭 있어야 할 코드가 남았나)로 잡는다.
- **결정(복구 3단)**: ① **LLM이 사라진 동작을 다시 얹어 고쳐본다** → ② 안 되면 **되돌리고 계획부터 다시** → ③ 그래도 안 되면 **사람**. (전부 LLM이 하고 사람은 최후.)
- **한계(정직)**: "명백히 사라진 것"은 om-apply가 정적으로 잡지만, "있는데 미묘하게 깨진 것"은 **verify(실제 실행)에서만** 잡힌다.

### 논의사항 6 — 예전 apply 코드를 재활용할까
- **문제**: 예전 apply는 **다른 용도의 구버전**이라, (1) 흐름이 다르고(개발자가 만든 걸 등록), (2) **현재 정책과도 어긋난다**(폐기한 방식의 테스트를 다시 쓰고, 최신 관계·계획 결속을 모르고, 계약·공유 파일을 못 씀).
- **결정**: **통째 재활용은 부적합.** Git 고정·안전한 파일 쓰기·되돌리기 같은 **검증된 저수준 안전 부품만 부분 재활용**하고, 본체는 새로 만든다.

### 논의사항 7 — om-apply를 어디에 둘까
- **결정**: **깨끗한 배포본(om-plan이 있는 곳)에 편입.** 배포 묶음으로 깔끔하게. (안전 부품은 옮겨온다.)

### 논의사항 8 — "업무 규칙(계약) 충족"을 om-apply가 판정할까
- **문제**: 코드를 쓴 LLM이 자기 코드를 보고 "규칙 충족"이라 쓰는 건 **독립 검증이 아니다.**
- **결정**: om-apply는 계약 충족을 **통과로 처리하지 않는다.** LLM의 판단은 "주장(claim)"으로만 남기고, **실제 충족 확인은 verify(테스트 실행)**가 한다.

## 5. 사람 결정 (일부 확정, 일부 미룸)

- **신규 공유 경로(두 커스텀이 새로 함께 쓰게 된 파일) 처리 — ✅ 확정(v1)**: 승인자를 지정하지 않고 **STOP + 사람 검토 질문**으로. 정식 승인 주체(관련 담당자 전원 vs 통합 담당자 한 명)는 **승인 체계 생길 때 재검토**.
- 그 외 세부는 설계 반영 중 정밀화.
