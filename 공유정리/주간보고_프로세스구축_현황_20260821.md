# 주간보고 — OpenMetadata 커스터마이징 자동화 프로세스 구축 현황

작성일: 2026-08-21 (합의된 프로세스 2형식 기준)

## 0. 이 프로젝트란 (한눈에)

**은행이 OpenMetadata에 넣은 개조(커스터마이징)를 "기능 단위 고유 ID"로 등록·관리하고, 그 ID를 기준으로 등록·수정·버전업·검증을 일관되게 운영하는 프로세스를 만든다.**

- OpenMetadata 공식 코드 위에 은행 개조가 여러 개 얹혀 있는데, "무엇이·왜·어디가 개조됐는지"가 흩어져 있으면 공식 버전을 올릴 때마다 무엇이 깨질지 알 수 없다.
- 그래서 각 개조를 **고유 ID(예: `BANK-OM-001`)로 등록**하고, 그 ID에 **바뀐 파일·지켜야 할 동작·필수 테스트**를 묶어 관리한다.
- 이 **ID(기능/커스텀) 기준 관리**를 사람 손이 아니라 **LLM(제안) + 규칙(검증) 자동화 파이프라인**으로 운영하는 것이 목표다. 사람은 위험·예외·최종 통합만 검토한다.

> 즉, 핵심은 **"기능별(커스텀별) ID 관리 체계"** 이고, 아래 파이프라인은 **그 체계를 자동으로 운영하는 수단**이다.

## 1. 무엇을 만들고 있나 (목표)

OpenMetadata에 은행 커스터마이징을 **등록·수정·버전업**할 때, **LLM이 변경을 계획·반영·검증**하고 **규칙(결정론 검사)이 매 단계를 강제**하며, **사람은 위험·예외·최종 통합만 검토**하는 자동화 파이프라인을 만든다.

핵심 원칙:
- **LLM은 제안하고, 규칙(검사기)이 검증한다.** 검사기는 LLM을 안 타므로 속일 수 없다.
- **각 단계는 앞 단계 산출(A→B→C→D)을 근거로만** 진행한다.
- **문제가 있으면 다음 단계로 안 가고 앞 단계로 되돌린다.**

## 2. 전체 프로세스 = 논리 6단계 (산출물 A~D)

| # | 논리 단계 | 누가 | 산출 |
|---|---|---|---|
| 1 | 사전 분석 (ID별 현재 위치·새 버전 반영 위치·방법) | LLM + 사람 | **A** 계획 |
| 2 | 커스터마이징 반영 (코드 유지·추가·이동·대체·삭제 + 이유 기록) | LLM | **B** 반영코드 |
| 3 | 변경 확인 (A Manifest ↔ 실제 Git 대조, 미등록 변경 시 회귀) | 규칙 + LLM | (B 검증) |
| 4 | 필수 테스트 (승인 테스트를 최종 commit에 실행·기록) | LLM + 규칙 | **C** 테스트 |
| 5 | 결과 결속 (최종 commit SHA에 테스트결과·승인·이미지 digest 연결) | 규칙 | **D** 결속 |
| 6 | 통합 승인 (규칙이 A~D 관계 확인 + 사람이 위험·예외·최종 검토) | 규칙 + 사람 | 승인 |

## 3. 실현 = 4 커맨드 + 사람 (스킬 정의 · 진행)

논리 6단계를 아래 커맨드가 담당한다.

### ① /om-plan — 사전 분석(A)  ✅ 사실상 완성 (실전 CI 검증 전)
- **용도**: 변경 "계획"을 LLM이 쓰고 규칙이 검증. **아무것도 실제로 바꾸지 않음.** 결과 = 담당자가 검토할 계획.
- **모드 4종**:
  - `/om-plan initial` 최초 도입 — 기존 커스텀을 조사해 ID별 반영계획·테스트 초안을 한 번에.
  - `/om-plan feature` 신규 기능 — 새 ID 후보·목표 경로·유지 동작·필수 테스트 제안.
  - `/om-plan change` 기존 수정 — 기존 ID 유지, 바뀐 범위·영향 경로·재실행 테스트 제안.
  - `/om-plan upgrade` 버전업 — 기존 ID 기준으로 새 공식 구조 비교, 이동·대체·충돌 처리안.
- **진행**: 4모드 동작 ✅ / 품질 게이트(아래 §4) 완료·검증 ✅ / **남은 것 = 실제 CI 초록불 전**.

### ② /om-apply — 커스터마이징 반영(B)  🔶 일부 존재
- **용도**: 확인된 계획만 코드에 반영하고 **각 변경에 커스텀 ID를 commit에 남긴다.**
- **진행**: 반영·기록 코드 일부 존재(등록준비). 단 **버전업 재베이스 미구현**, 커맨드로서 미완성.

### ③ /om-verify — 변경·기능 검증(논리 3·4·5 = B·C·D)  ⬜ 미착수
- **용도**: **B**(계획 ↔ Git 변경 일치), **C**(필수 테스트 실행·통과), **D**(같은 최종 코드/SHA인지)를 확인. 계획 단계가 못 하는 "실제 실행·대조"를 담당.
- **진행**: 커맨드 없음. 단 일부 검사 기계(등록 밖 변경 커버리지·재구성 검증)는 별도 도구에 이미 존재 → 연결(배선)만 필요.

### ④ /om-report — 결과 요약(논리 6 일부)  ⬜ 미착수
- **용도**: A~D의 PASS·중단 사유·다음 행동을 **한 화면에** 보여준다.
- **진행**: 커맨드 없음.

### ⑤ 사람 검토 — 통합 코드 판단
- **용도**: 담당자가 결과를 보고 다음 작업을 선택. **정식 승인 체계 연결은 이후 범위(PoC 제외).**

## 4. ①/om-plan 세부 (이번 주 집중)

계획 단계의 품질 게이트를 완결(전부 반례 검증 통과):

| 완결한 품질 게이트 (계획 단계) | 상태 |
|---|---|
| 커스텀별(경로·계약·테스트) 관계를 사실로 보존 | ✅ 검증 |
| 테스트 등록 통로를 "계약을 통해서만"으로 통일 | ✅ 검증 |
| 수정 시 그 커스텀의 등록 테스트 누락 차단 | ✅ 검증 |
| 계획서 필드의 자료형(type) 오류 차단 | ✅ 검증 |
| 변경 파일 개수 기준 정정(변경 전 릴리즈 기준) | ✅ 검증 |
| 버전업 필수 산출물·문서누락 검증(독립 LLM 2차판독 포함) | ✅ 구현 |

> 각 항목의 배경·결정 근거는 하위 페이지(`하위_om-plan_논의정리_20260821.md`)의 "논의사항"에 정리.

## 5. 현재 위치 한눈에

- **①/om-plan**: 기능 완성·단위검증 완료 → **실전 CI 검증만 남음.**
- **②/om-apply**: 일부 코드만.
- **③/om-verify ④/om-report**: 미착수(조사·설계까지 됨).

> 즉, **커맨드 4개 중 1개(/om-plan) 완성**, 나머지는 구현 전.
