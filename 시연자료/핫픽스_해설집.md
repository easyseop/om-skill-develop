# 핫픽스 해설집 — 각 수리의 동작 원리까지 (처음 보는 사람 기준)

> 배경: 이 시스템은 검사기 프로그램이 업그레이드의 각 단계(계획→반영→검증)를 자동 검사하고 문제가 있으면 멈춘다. 아래 4회의 핫픽스는 전부 **검사기 프로그램 자체의 오류** 수리이며, 오픈메타데이터 제품 코드는 한 줄도 고치지 않았다. 4회 모두 검사기가 스스로 멈춰서 발견됐고, 수리마다 "일부러 틀린 상황을 여전히 잡아내는가" 반례 테스트가 함께 추가됐다.

---

## 1번 (8/26) — 명령어가 처음부터 실행되지 않던 오류

**지키려던 규칙**: `/om-plan` 같은 명령은 AI가 몰래 실행하면 안 되고, 사람이 직접 입력했을 때만 실행돼야 한다.

**동작 원리 (사람 입력을 어떻게 표시하나)**:
1. Claude Code에는 "사용자가 채팅창에 입력하고 엔터를 쳤다"는 순간에만 실행되는 연결 지점(훅)이 있다. AI가 스스로 명령을 실행할 때는 이 지점이 아예 지나가지 않는다 — 사람 입력이라는 사건 자체가 없으므로.
2. 사람이 `/om-plan`을 입력하면 그 지점에서 **표시 파일**(세션 고유번호가 든 마커)을 만든다.
3. 검사기 명령이 실행되기 직전, 다른 연결 지점(도구 실행 전 검사)이 표시 파일 유무를 확인한다. 있으면 실행 허용 후 **그 자리에서 삭제**(1회용 — 입력 한 번에 실행 한 번). 없으면 "planning command requires an active session marker"로 거부.
4. AI가 표시 파일을 직접 만들어 우회하는 것은 ① 스킬 문서의 금지 조항(실제로 서버 세션이 이 조항을 근거로 우회하지 않고 사람 입력을 요청함) ② 마커 생성 명령의 권한 차단, 이중으로 막는다.

**오류**: 표시를 "만드는 지점"과 "확인하는 지점"의 순서가 반대로 배선돼, 사람이 정당하게 입력해도 아직 표시가 없는 시점에 확인부터 해서 거부됐다.

**수리**: 표시 발급을 더 이른 연결 지점으로 옮겨 순서를 바로잡음. 규칙 설계는 옳았고 조립 순서만 틀린 순수 구현 버그. (분류: 설계 ○, 배선 실수)

## 2번 (8/28) — 사람이 승인해도 그 승인을 입력할 방법이 없던 오류

**지키려던 규칙**: 하나의 파일을 두 기능이 함께 쓰게 되면(예: 파일 분해로 새로 생긴 공용 파일), 검사기가 "이 공유가 맞는지 사람이 확인해달라"고 묻고 멈춘다.

**동작 원리 (수리 후)**:
1. 반영(apply) 검사가 "이전에 없던 공유 파일"을 발견하면 질문 목록에 올리고 `awaiting_shared_path_review` 상태로 멈춘다.
2. 사람이 승인하면 그 내용을 실행 기록 파일(execution-report.yaml)의 전용 항목에 적는다 — 파일 경로, 공유하는 기능 ID 조합, 승인자, 승인 이유 4가지 전부 필수.
3. 같은 결과물로 검사를 재실행하면, 검사기가 승인 기록과 실제 상황을 대조한다: 경로와 ID 조합이 **정확히 일치**할 때만 질문을 해소. ID가 하나라도 다르면 차단, 승인 없는 새 공유는 여전히 정지, 실제 새 공유가 아닌 파일에 대한 승인은 경고로 기록.
4. 승인 내용(승인자·이유 포함)은 결과 봉인값(digest) 계산에 통째로 들어간다 — 나중에 승인 기록을 몰래 바꾸면 봉인값이 달라져 들통난다.

**오류**: 1번(묻고 멈추기)만 있고 2~4번(대답 받기)이 없었다. 승인해도 영원히 멈춘 상태 — 파일 분해가 흔한 업그레이드에서는 구조적으로 검증 단계에 도달 불가.

**수리**: 위 2~4번을 신설. (분류: 설계에 빠진 조각)

## 3번 (9/2) — 반영 단계와 검증 단계의 규칙 충돌

**지키려던 규칙 두 개** (각각은 옳음):
- 반영: 코드를 반영하면 "무엇을 반영했는지 기록하는 관리 파일 10개"를 반드시 수정해야 성공.
- 검증: 시작하려면 검사기 저장소에 수정된 채 저장 안 된 파일이 0개여야 함(남의 손이 탄 상태에서 검증하지 않기 위해).

**오류**: 반영을 규칙대로 성공하면 관리 파일 10개가 수정 상태로 남고 → 검증이 시작을 거부. 저장(커밋)하면 "검사기 버전이 반영 시점과 다르다"는 별도 검사에 걸리고, 되돌리면 "반영 결과와 내용이 다르다"는 검사에 걸림 — **세 경로 전부 막힌 완전한 모순**. (반영이 정상일수록 검증이 불가능해지는 구조)

**동작 원리 (수리 후)**:
1. 검증 시작 시 수정된 파일이 있으면, 그 전부가 ① 관리 파일 목록에 속하고 ② 각 파일의 현재 내용 지문(digest)이 반영 단계가 결과에 봉인해 둔 값과 **한 글자도 다르지 않을 때만** 통과.
2. 관리 파일이 아닌 파일이 수정돼 있거나, 내용이 봉인값과 다르면 기존대로 거부 — 어떤 파일이 왜 걸렸는지 사유를 구조화해 남긴다.
3. 검사기 버전 동일성 검사와 등록부 전체 대조는 그대로 유지 — 완화가 아니라 "반영이 만든 바로 그 상태만" 예외로 인정하는 정밀화.

(분류: 설계끼리 충돌 — 단계 간 인수인계 규칙 미정의)

## 4번 (9/2, 진행 중) — 첫 계약 테스트 실행에서 드러난 규약 결함 2건

사상 첫 계약 테스트 실행(9종 중 8종 실패)의 원인. 둘 다 제품이 아니라 시험 도구 쪽이며, 제품 코드 결함은 0건이었다.

**4-A. 서버 주소 전달 규약 미정의 (6건 차단)**

- 동작: 검사기는 테스트 프로그램에 서버 주소를 환경변수(OPENMETADATA_BASE_URL)로 넘긴다.
- 오류: 검사기는 `http://서버:포트`(뿌리 주소)를 넘기고 자신은 거기에 `/api/v1/...`을 붙여 쓰는데, 테스트는 받은 값에 `/v1/...`만 붙인다. 실제 API는 `/api/v1/...`이므로 테스트는 전부 엉뚱한 주소(화면 HTML이 나오는 곳)에 접속해 실패. **`/api`를 누가 붙일지 정한 곳이 없어** 양쪽이 제멋대로였다. 어떤 값을 넣어도 검사기 자신 또는 테스트 한쪽이 반드시 깨진다.
- 수리: 의미를 "뿌리 주소"로 확정하고, 검사기가 테스트에 넘길 때만 `/api`를 붙여 전달. 테스트는 무변경. (분류: 규약 미정의)
- 중요: 이 6종 테스트는 "실패"한 게 아니라 **아직 검증 자체가 수행되지 못한 것** — 수리 후 실행에서 진짜 결과가 처음 나온다.

**4-B. 계약 테스트가 옛 파일 위치를 검사 (2건)**

- 동작: Sybase·Tibero 커넥터 테스트는 "이 코드가 특정 파일에 특정 형태로 존재하는가"를 확인한다.
- 오류: 1.13.2 업그레이드에서 그 코드는 승인된 계획(U8 이식)대로 DatabaseServiceUtils.tsx(switch 형태) → DatabaseServicePureUtils.ts(맵 형태)로 옮겨졌다. 코드는 새 자리에 정상 존재하는데 테스트가 옛 파일명·옛 형태를 검사해 "없다"고 판정. 코드 이동을 계획에 기록하는 절차는 있었지만 **테스트의 검사 위치를 함께 갱신하는 절차가 계획에 없었다.**
- 수리: 테스트가 보는 위치·형태를 새 자리로 갱신하되 검사 내용(두 커넥터가 실재하고 스키마 왕복이 되는가)은 그대로. 반례: 맵에서 커넥터 한 줄을 지운 가짜 코드 → 반드시 실패해야 함. (분류: 절차의 빈칸. 사람 결정으로 "등록 변경이 아닌 검사 기준 정정"으로 규정 — 결정기록 24)

## 전체를 관통하는 관찰

- 순수 코딩 실수는 1번 하나. 나머지는 전부 **단계와 단계가 만나는 경계**(질문↔대답, 반영 결과↔검증 시작, 값 전달, 코드 이동↔검사 기준)의 약속이 빠졌거나 어긋난 것.
- 그래서 다음 개발 라운드의 방향: 단계 간 인수인계 약속을 문서가 아니라 **기계 검사**로 만들기 (백로그 #10·#17·#18·#19).
- 수리의 공통 형태: 완화가 아니라 정밀화 — 통과 조건을 넓히지 않고, "정당한 상태"를 더 정확하게 정의해서 그것만 통과시킨다.
