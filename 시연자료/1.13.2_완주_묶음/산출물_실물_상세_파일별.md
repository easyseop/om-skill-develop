## ② 반영 단계 파일들 — `apply/` (5개)

### `execution-report.yaml` — 실행 기록 (무엇을 어떻게 반영했나)
**단위별 시작→끝 SHA (계획↔실제 결속):**
```yaml

start_sha: 2763bf97ce…      # 공식 1.13.2 지점에서 시작
end_sha:   7fdb43dd09…      # 반영 후 커밋
status: completed
review_note: 13 actions. conflicts 0. 13 files, +1476.
```

**공유 경로 사람 승인 (`shared_path_acknowledgments`) 4건 — 왜 사람이 결정?**
```yaml
path: .../utils/EntityLinkUtils.ts
customization_ids: [BANK-OM-001, BANK-OM-002]
approved_by: seop
rationale: 원본에서 이미 같은 조합으로 공유되던 코드의 이동이며 새 기능 결합 아님
```
- **왜 사람이 결정하나**: "이 파일을 두 기능(001·002)이 **같이 쓰는 게 의도된 건지, 실수로 얽힌 건지**"는 기계가 판단 못 한다. 담당자 조율 문제라 사람이 확인해야 한다.
- **어떻게 탐지했나**: 검사기가 "최종 결과에서 2개 이상 기능이 함께 쓰는 파일" 목록을 계산 → 그중 **이전(baseline) 공유 목록(39건)에 없던 것**이면 "새 공유"로 잡아 멈춘다. 이번엔 파일 분해(U7·U8)로 새 공유 4건이 생겨 승인이 필요했다.
- **왜 이것만**: 나머지 반영은 "은행이 원래 건드리던 파일을 다시 적용"이라 새 판단이 없다. 새 공유만 "처음 생긴 관계"라 사람 확인 대상.

## ③ 검증 단계 파일들 — `verify/`

### `pytest/*.junit.xml` — 실제 테스트 실행 증거 (9개)
검사기는 "pass"를 믿지 않고 실제로 돌려 XML을 남긴다:
```xml
<testsuite failures="0" errors="0" skipped="0" tests="1" time="2.857"
           timestamp="2026-09-02T04:06:53Z" hostname="jupyter-x-…">
  <testcase classname="tests.bank.contracts.test_korean_ime"
            name="test_hangul_composition_roundtrip" time="2.846"/>
```
> `failures="0"` = 실제 서버에서 실제 브라우저로 한글 조합을 돌린 진짜 결과.

### `verify-receipt.json` — 검증 판정 + 봉인 결속 (검사기가 "완료"를 확인하는 방식)
```
status: verified
게이트 4개: handoff_and_build_binding·runtime_candidate_binding·
           required_contract_tests·ui_presentation_consistency = 전부 verified
tests:
  candidate_sha: 2a70bba2…       # 어느 코드에 대한 테스트인지
  image_id: sha256:603877d5…     # 어느 빌드 이미지에서 돌았는지
  suite_digest: sha256:a62b9bfa… # 실행한 테스트 파일들의 지문
  test_run_set_digest: sha256:d89f27…
  kind_summary: api 4/4 · browser 3/3 · static 2/2 pass
  retries: 0   waiver: {}         # 재시도·면제 없이 정직 통과
```
**검사기의 "완료 확인" 4단계:**
1. pytest 실제 실행 → junit XML 생성 (failures 수를 코드가 읽음)
2. 실행한 테스트 파일·세트 지문 계산
3. 그 결과를 **후보 SHA + 빌드 이미지 ID**에 묶음 → 딴 코드/딴 이미지 결과는 통과로 못 씀
4. 재시도·면제 0 확인 → verified
