## A. 검사기 핫픽스 — 검사기 파이썬 코드를 고친 4건

**모두 SKILL.md(지침 문서)가 아니라 검사기 엔진의 `.py` 코드·스키마 수정이다.** 지침 문서는 실전 8일간 0회 수정 — 고친 것은 전부 "어기면 막는 기계 로직". 수리마다 반례 테스트 동반.

### 1. 명령어가 처음부터 실행 안 됨  · 08-26 · MR !4
- **문제**: "사람이 직접 입력했을 때만 실행" 규칙을 위해 입력 표시(마커)를 확인하는데, 표시를 만들기도 전에 확인부터 하도록 순서가 뒤바뀌어 정당한 호출까지 거부.
- **수리**: 표시 발급을 더 이른 훅 지점으로 이동. 규칙은 옳았고 순서만 틀린 순수 버그.
- **고친 파일**: `harness/acgh/plancore/hook_cli.py` (+ 테스트)

### 2. 사람이 승인해도 입력할 방법이 없음  · 08-28 · MR !6
- **문제**: "새로 두 기능이 공유하는 파일이 생기면 사람 확인" 규칙에서, 검사기가 질문을 띄우고 멈추기만 할 뿐 "사람이 확인했다"는 응답을 받아 기록할 입력 항목이 없어 계속 멈춤. 파일 분해가 흔한 업그레이드에선 구조적으로 검증 도달 불가.
- **수리**: 실행 기록 파일에 사람 승인용 입력 항목 신설(파일 경로·공유 기능 ID·승인자·사유). 실제 상황과 정확 일치 시만 통과, 승인 내용은 봉인값 계산에 포함(몰래 바꾸면 발각).
- **고친 파일**: `applycore/workflow.py` · `integrations/om/apply.py` + 스키마 2개 (+ 테스트)

### 3. 반영 성공조건 ↔ 검증 시작조건 충돌  · 09-02 · MR !7
- **문제**: 반영 단계는 관리 파일(무엇을 반영했는지 기록하는 파일 10개)을 수정해야 성공인데, 검증 단계는 그 파일들이 수정 없이 저장된 상태여야 시작. 둘 다 옳은 규칙이지만 동시에 만족할 방법이 없어, 저장(커밋)·그대로 두기·되돌리기 세 경로 전부 다른 검사에 막힘.
- **수리**: 수정된 파일이 정확히 그 관리 파일 10개이고 내용이 반영 단계가 기록한 값과 한 글자도 안 다르면 시작 허용. 그 외는 여전히 차단(완화 아님).
- **고친 파일**: `harness/acgh/verifycore/workflow.py` (+ 테스트)

### 4. 검증 테스트가 실행 못하거나 옛 위치 검사  · 09-02 · MR !8
- **문제 4-A**: 검사기와 테스트가 서버 주소의 뜻을 달리 해석(`/api`를 누가 붙일지 미정) → 9종 중 6종 접속 실패.
- **문제 4-B**: 커넥터 테스트가 1.13.2에서 옮겨진 옛 파일 위치를 검사 → 기능은 멀쩡한데 "없다" 판정.
- **수리**: 주소 조립을 검사기가 통일 / 테스트 검사 위치를 새 자리로 갱신(검사 내용은 불변). 재주행에서 9종 전부 통과.
- **고친 파일**: `verifycore/workflow.py` · `tests/bank/contracts/_connector_contract.py` (+ 테스트)

## B. 환경·빌드 함정 — 이 서버 첫 빌드의 1회성 통과의례 5건

시스템 결함이 아니라 서버 준비 부족. `시연자료/기준정보/D6` 체크리스트로 정리돼 재주행 땐 안 나옴.

- **5. JDK 버전 오기** (09-01): 가이드가 "JDK 17"이라 적었으나 제품은 Java 21 요구(1.13.1부터 동일, pom.xml 실측). 빌드 즉시 실패.
- **6. antlr4 미설치** (09-01): UI 빌드가 파서 생성 도구 antlr4를 호출하는데 준비물 목록에 없었음.
- **7. 디스크 부족 2회** (09-01): 홈 파티션 9.8G 만석 → ENOSPC. 캐시를 루트 파티션으로 이전. yarn의 "네트워크 문제" 오진을 실측으로 구분.
- **8. 경로 의존 node_modules 이동 부작용** (09-01): 캐시 이전이 상대경로 링크를 끊어 새 빌드 오류 유발 → 제자리 복귀로 해소(내 조치가 원인, 자기적발).
- **9. 서버 사양·컨테이너 재시작** (09-01): 2코어에서 UI 빌드 시간초과 → 8코어 증설 후 통과("2코어 기아" 확정). 컨테이너 재시작으로 /var/tmp 캐시 증발.

## C. 계획·문서 정정 — 검사기 코드가 아닌 계획서·가이드 수정 6건

대부분 "손으로 쓴 것"의 실측 누락. 검사기가 apply·빌드 단계에서 잡아 정정.

- **10. 계획서에 실행계획 파일 누락** (08-26 · I4): 계획은 합격했는데 다음 단계가 요구하는 실행계획서가 산출물에 없어 착수 불가. (봉인값이 우회 변조는 차단 — 설계 실증)
- **11. 시작 커밋 역할 오기** (08-26 · I6): 계획 전략은 맞고 시작 지점 숫자 하나가 딴 곳을 가리킴 → apply 착수 차단.
- **12. 계획서 자기모순(관리 파일 목록)** (I8 계열): "11개 고친다" ↔ 허용 목록 "9개" 불일치. 3방향 교차검증 신설로 정정.
- **13. requires_diff 모순** (08-28): "이 파일 반드시 바뀜" 옛 표시 ↔ "내용은 다른 곳으로 이관" — apply 마지막 관문에서 적발, 정식 표현으로 정정.
- **14. 제3유형: 참조 대상 rename** (09-01 · I11): 공식이 StringsUtils→StringUtils 파일명 변경, 은행 파일 2줄이 옛 이름 import → 빌드 실패. 계획에 import 교정 정식 등록.
- **15. 가이드 오류(JDK·antlr4·관리 파일 커밋 단계)** (09-01~02): 손으로 쓴 가이드 94A를 3회 정정. 검증 시작 전 "관리 파일 커밋" 단계 누락도 실기동으로 발견·추가.

## 관통 통찰 — 모든 결함의 공통점은 "단계 사이의 인수인계"

순수 코딩 실수는 **1번 하나**뿐. 나머지는 각 단계(계획·반영·검증)를 따로 보면 다 잘 설계됐는데, **단계와 단계가 만나는 경계**의 약속이 빠지거나 어긋난 것 — 질문↔응답(2), 반영 결과↔검증 시작(3), 값 전달(4-A), 코드 이동↔검사 기준(4-B).

4회 핫픽스 모두: 기계 게이트가 먼저 잡음 · 당일 수리 · "일부러 틀린 상황을 잡아내는지" 반례 테스트 동반 · **제품 코드는 한 줄도 안 다침.**

최종 검증(9/9 통과) 때 제품 트리가 직전 사이클과 동일(`f925ab5d`)했다는 것이 이를 확증 — 통과 원인은 코드 수정이 아니라 **검사 방식 교정**이었다.
