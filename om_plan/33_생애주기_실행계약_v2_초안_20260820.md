# 생애주기 실행 계약 v2 초안 (2026-08-20)

성격: 29 폐기 후 재설계. 32의 4자 검토 종합(확정 P0 6·유효 P1)을 전건 반영. **검토용 초안 — 다각 적대검토 통과 전 구현 금지.**
언어: "설명"이 아니라 **계약** — 각 단계 사이에 오가는 아티팩트의 스키마·생산자·소비자·결속·거부 규칙을 정의한다.

## 0. 유지하는 기반 (4자 공통 확인된 실재 방어)

- 사실-정합: evidence_refs expected 대조, facts 재계산 비교, 결과위조 재검증 거부(COMPLETED_RUN_READ_ONLY), no_change 머신증거.
- base 신선도: apply의 `registration_state_digest` 불일치 → StaleProposalError(fail-closed).
- 사람 승인 파일: apply의 registration-approval(approved_by placeholder 거부, review_required 전건 decision 커버).
- upgrade 층1: path-remap 커버리지(교집합), crosscheck 연결, 9항목 meaningful, 2차판독 게이트(형식).

## 1. 용어 계약 (P0-2 해소 — 혼동 금지)

| 용어 | 뜻 | 아닌 것 |
|---|---|---|
| `plan-verdict: approval` | 계획이 **사람/후속 검토 준비**됨(exit 2) | 구현 지시 승인 아님 |
| `plan-approval` (신규 아티팩트) | 이 계획대로 **구현해도 좋다**는 승인 기록 | 배포 승인 아님 |
| `registration-approval` (기존) | 검증된 결과를 **등록에 반영**해도 좋다는 사람 승인 | 계획 승인 아님 |

## 2. 아티팩트 체인 (P0-1·P0-3 해소 — 연속성의 실체)

```
plan ──► plan-approval ──► implement-result ──► verify-receipt ──► apply
 │            │                  │                    │               │
 plan_digest  plan_digest 서명   plan_digest+tree SHA  전체 체인 결속   체인 전건 검증
```

**정직 고지(위조 한계):** 단일 운영자 로컬에서는 어떤 파일도 위조 가능하다. 신뢰 앵커는 (a) CI의 fresh 재실행(기존 om_plan_ci 패턴 — 저장 바이트를 믿지 않고 새로 실행), (b) 사람 승인 2회(plan-approval·registration-approval)다. 아티팩트 체인의 역할은 "위조 불가"가 아니라 **"정직한 자동화가 표류하지 않게 + 위조 시 재실행에서 반드시 어긋나게"** 만드는 것이다.

### 2.1 `plan-approval.yaml` (신규)

- 생산: 사람(또는 위임된 자동화 정책 — Q9 결정과 일관되게 approval verdict 후 자동 진행 허용 가능. 단 기록은 남김).
- 필수 필드: `schema_version` · `plan_run_id` · `plan_digest`(승인한 계획) · `approved_scope`(모드·customization_id 목록) · `approved_by`(사람 또는 `automation-policy:<정책ID>`) · `approved_at`.
- 소비: /om-implement 시작 전제. plan_digest 불일치 → 시작 거부.

### 2.2 `implement-result.yaml` (신규)

- 생산: /om-implement (미래 명령. 그 전엔 수동 작성도 같은 스키마).
- 필수 필드:
  - `plan_run_id`·`plan_digest` (어느 계획을 구현했나)
  - `base_commit_sha`·`implemented_commit_sha`·`implemented_tree_sha` (뭘 만들었나)
  - `observed_changed_paths[]` (실제 git diff — 계획의 예상 경로와 대조용)
  - `deviations[]` (계획과 다르게 한 것. **비어있지 않으면 재계획 루프** — 아래 2.5)
  - `conflict_resolutions[]` (upgrade 병합 충돌 해소 기록 — 각각 {path, resolution, rationale})
  - `implement_result_digest` (canonical digest)
- 거부 규칙(소비자=verify): plan_digest 불일치 / observed_changed_paths ⊄ (계획 예상경로 ∪ deviations 신고 경로) → 거부. **신고 없는 이탈 = block.**

### 2.3 `verify-receipt.yaml` (신규)

- 생산: /om-verify (미래 명령).
- 필수 필드:
  - `plan_run_id`·`plan_digest`·`implement_result_digest`·`verified_tree_sha` (**implement-result의 tree와 일치해야 함**)
  - `contracts_executed[]`: {contract_id, test_id, owner_customization_id, command, exit_code, log_digest}
  - `mutants_executed[]`: {mutant_id, expected: fail, actual} (기준선 실효성 — §5 initial)
  - `completeness`: shared-impact가 지목한 **전 소유 ID**의 contracts-to-run 전건 실행 여부(누락 목록 포함, 비면 안 됨을 명시)
  - `verdict`: pass / fail / partial(부분실행 사유)
- 거부 규칙(소비자=apply): 체인 digest 불일치 / verified_tree_sha ≠ 반영하려는 custom_ref tree / completeness 누락 / 필수 contracts 중 fail / mutant가 fail하지 않음(actual=pass) → apply 거부.
- CI 앵커: CI 모드에서는 verify-receipt를 믿지 않고 **재실행**해 receipt와 대조(기존 fresh-validation 패턴 확장).

### 2.4 apply 전제조건 (기존 + 체인)

기존 유지(proposal_digest·registration_state_digest·registration-approval) **+ 신규**: verify-receipt 체인 전건 검증(2.3 거부 규칙). upgrade의 재베이스 쓰기는 **Q10 결정 전 금지**(§6).

### 2.5 재계획 루프 (B의 F-E 해소 — 충돌해소=재계획을 정직하게)

- implement 중 계획에 없는 판단(병합 충돌 해소, 예상 밖 경로)이 생기면: `deviations[]`/`conflict_resolutions[]`에 기록 → **자동 진행 금지** → 계획 갱신(새 plan run 또는 proposal-only resume) + plan-approval 재발급 후에만 verify 진행.
- 즉 "무표류"가 아니라 **"표류는 기록·재승인 없이는 전진 불가"**가 계약이다.

## 3. 성격 3분법 (2분법 폐기 — F-C 해소)

| 성격 | 계약·테스트 | 해당 |
|---|---|---|
| A. 동작 세움 | 계약·테스트 **신설** | initial(확립), feature |
| B. 동작 보존 | 계약·테스트 그대로 + **재실행** | change-보존, upgrade 기본 |
| C. **기반이 동작 변경을 강제** | 계약 **은퇴/개정**(retire/delta) + 사람 승인 | upgrade에서 공식 폐기·모순 발견 시 |

- C 진입 조건(관측): upgrade의 crosscheck에 `documented_contradicts_observed` 또는 deprecation finding이 있으면 → `contracts-retire-delta.proposed.yaml` 산출 **조건부 필수**(없으면 block). 계약 은퇴·개정은 **사람 승인 필수**(계약=사람 큐레이션, §7).

## 4. change 분기 — 자기신고 금지, 관측으로 판정 (P0 change_kind 해소)

`change_kind` 필드 도입하지 않는다. 대신:

1. **post_change_reconcile(관측 있음)**: 검사기가 `observed-change-paths ∩ 계약 앵커 경로(그 ID의 registered changed_paths + 등록 테스트 파일)`를 자동 계산.
   - 교집합 ∅ → "보존 후보". 단 **그 ID의 계약·테스트 전건 재실행이 verify 필수**(receipt로 증명).
   - 교집합 ≠ ∅ → **동작변경으로 취급**: `contracts-delta.proposed.yaml`(신/개정 계약 정의 + 테스트 계획) 필수. 없으면 block.
   - 그 ID의 등록 계약이 **0개** → "보존" 판정 자체 불가(기준선 미성립, F-G 연결). 계약 신설 필수.
2. **pre_plan(관측 없음)**: 계획만 허용. **구현 후 post_change_reconcile 재실행이 apply 전제**(Codex P1-5). pre_plan만으로 apply 진입 금지.

## 5. initial 기준선 — green 금지, mutant 계약 (F-G 해소)

- initial의 계약 초안(`contracts.proposed`)은 각 계약마다 **최소 1개 반례(mutant) 명세** 필수: {mutant_id, 어떤 변형, 어떤 테스트가 fail해야 하는지}. 반례 없는 계약은 초안 불완전으로 block.
- verify 기준선 = "테스트 green"이 아니라 **"계약 green + mutant fail"** 둘 다. (mutant가 pass하면 그 계약은 아무것도 안 지키는 것.)
- 실행은 /om-verify 몫(미래). plan 단계 계약: 초안에 mutant 명세가 **존재**하는지만 검사기가 강제.

## 6. upgrade 재베이스 — Q10 미결정 명시 (P0-4 해소)

- source 블록·source-snapshot-owners·source-diff의 새 버전 갱신(재베이스)은 **Q10 결정 전 설계·구현 금지.** 이 문서는 자리만 표시한다: "재베이스 아티팩트·주체·시점 = Q10".
- Q10 전 가능한 것: upgrade plan(9항목+2차판독, 기존), implement(병합, §2.5 루프), verify(생존확인 receipt). **재베이스 쓰기만 금지.**

## 7. 계약·공유 파일 — 자동반영 금지 (P0-6·순환 오라클 해소)

- `contracts.yaml`·`shared-path-owners.yaml`·`shared-code-definitions.yaml`은 apply 화이트리스트에 **추가하지 않는다.**
- 대신 proposal 필수 산출물에 `required_human_actions[]` 신설: {action: "contracts.yaml에 CONTRACT-X 추가", target_file, 근거}. 
- apply는 기존 fail-closed(카탈로그에 없는 CONTRACT-X 참조 시 검증 실패)를 **의도된 게이트로 명문화**: 사람이 그 액션을 완료해야만 apply가 통과한다. (계약 저작=판단. 같은 LLM 출처로 자동화하면 오라클 독립성 붕괴 — B F-B.)

## 8. 모드별 필수 산출물 + proposal 스키마 (C P0-2 해소)

- proposal에 **JSON 스키마 도입**(현재 무스키마 → 누락 무비용). 모드별 필수 문서·파일명 표준(Codex P1-8):

| 모드 | 필수 (파일명 표준) |
|---|---|
| initial | `registry-entries.proposed.yaml` · `manifests.proposed/` · `contracts.proposed.yaml`(+mutant 명세 §5) · `unresolved-questions.yaml` |
| feature | `id-availability.decision.yaml` · `contract-definitions.proposed.yaml`(+mutant) · `test-plan.proposed.yaml` · `expected-paths.proposed.yaml` · `unresolved-questions.yaml` |
| change | `manifest-delta.proposed.yaml` · `contracts-to-run.yaml`(**shared-impact 전 소유 ID 포함**) · (교집합≠∅ 시) `contracts-delta.proposed.yaml` · `unresolved-questions.yaml` |
| upgrade | 기존 9항목 + `independent-document-review.yaml` + (C성격 발견 시) `contracts-retire-delta.proposed.yaml` |

- 검사기: 모드별 필수 목록 **존재+meaningful**을 upgrade와 동형으로 강제(`mode in {...}` 게이트 확장).

## 9. N/A 공동화 방어 (C P1-5 해소)

- upgrade에서 층1 교집합(=path-remap expected)이 ∅이면: **최소 실질 증거 대체 요건** 발동 —
  1. `official-doc-findings`가 비공허해야 하고(최소 호환성/마이그레이션 판정 1건 또는 명시적 "요구사항 없음" 판정), 
  2. 2차판독이 그 "없음" 판정을 **명시적으로 확인**(missing_requirements=[] + `no_requirements_confirmed: true` 필드 신설)해야 approval.
- 즉 "겹치는 게 없으니 전부 N/A"가 아니라, **"없음" 자체를 이중으로 증명**해야 한다.

## 10. 2차판독·owner 강화 (C P1-4·P1-6 — 정직한 한계와 함께)

- 2차판독: 로컬 위조는 원천 차단 불가(정직 고지). CI 모드에서 하네스가 **직접 별도 컨텍스트를 기동**해 결과를 out-of-band 기록(운영자 proposal 복사 경로 제거)하는 것을 배선 목표로 명시(§2 CI 앵커와 동형).
- owner: 요청 owner가 채워져 있어도 **신원 검증은 없음**을 계약에 명시. 신원 결속은 Q6(보류) — GitLab 계정/보호환경 승인자와 연결 시 해소. 그전까지 owner 값은 "선언"이며 registration-approval의 approved_by가 실질 사람 게이트.
