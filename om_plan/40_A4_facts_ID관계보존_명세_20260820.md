# A-4 명세 — facts에 ID별 관계 보존 (2026-08-20)

> ★ 개정(2026-08-20, D-directtest 옵션3 확정): 아래 `tests` 정의에서 **매니페스트 `assurance.direct_tests`를 제거**한다. 관계 `tests` = 그 ID 계약 required_tests만. (근거: direct_tests는 계약 우회 통로이고 실데이터 전부 빈 값. 지시서 48.) 본문 중 direct_tests를 tests에 포함한다는 서술(§2.1·§3·수용#4)은 이 개정으로 무효.

트랙 A(계획 품질 완성)의 1항목. **범위: fact 수집만.** 이 facts의 소비(관측 분기 등)는 A-3, verify는 downstream — 여기서 구현하지 않는다. 목표: 이미 소스에 있으나 facts에서 union으로 소실되는 ID별 관계를 **결정론적 fact로 보존**한다.

## 1. 문제 (코드 근거)

`work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/acgh/integrations/om/collectors.py::_registration_metadata`:

- L67-92: entry별 manifest `implementation.changed_paths`를 읽지만 **하나의 `customization_paths` set에 union** → ID→경로 소실.
- entry의 `contracts:` 필드(그 ID가 가진 계약) → **아예 안 읽음** → ID→contracts 소실.
- L96-109: `contract.required_tests`를 읽지만 **하나의 `test_ids` union** → contract→tests 소실.
- 제품 repo 경로(manifest changed_paths)와 검사기 repo 테스트(required_tests selector)를 namespace 구분 없이 각각 flat union.

소스에는 관계가 온전하다: `customization-registry.yaml`의 entry {customization_id, contracts[], manifest}, `manifests/<ID>.yaml`의 changed_paths, `contracts.yaml`의 contract{id, required_tests}.

## 2. 신규 fact (수집 대상)

기존 flat fact는 **전부 유지**한다(다른 검사가 소비 중: registered-customizations, registered-customization-paths, registered-contracts, registered-tests, shared-path-owners). 아래를 **추가**한다.

### 2.1 `customization-relations` (fact_id)
kind: `customization_relations`. 등록된 ID별 관계. 값 = ID로 정렬된 리스트:

```yaml
- customization_id: BANK-OM-001
  changed_paths:            # 매니페스트 implementation.changed_paths (제품 repo), 정렬
  - openmetadata-service/.../InstanceCodeResource.java
  required_changed_paths:   # 매니페스트 implementation.required_changed_paths (load-bearing 부분집합), 정렬
  - openmetadata-service/.../InstanceCodeResource.java
  contracts:                # 그 ID의 registry entry.contracts[] (authoritative), 정렬
  - CONTRACT-INSTANCE-CODE
  tests:                    # 그 ID contracts→required_tests + 매니페스트 assurance.direct_tests, 정렬. 검사기 selector
  - tests/bank/contracts/test_instance_code.py::test_crud_search_roundtrip
```

- 각 필드 비면 `[]`. `tests`는 **그 ID 한정**(전역 union 아님) = (그 ID의 contracts의 required_tests) ∪ (매니페스트 `assurance.direct_tests`).
- **authoritative 소스**: ID→contracts는 registry `entry.contracts`를 정본으로 쓴다. 매니페스트 `assurance.contracts`·`contracts.yaml`의 `customization_ids`는 **양방향 교차확인용**(§2.3).
- 매니페스트 부재/경로이탈은 기존 `REGISTRATION_MANIFEST_PATH_INVALID` 방어를 그대로 탄다.

### 2.3 (선택) `id-contract-consistency` — 양방향 정합 크로스체크
kind: `id_contract_consistency`. ID↔계약 관계가 세 소스(entry.contracts / manifest assurance.contracts / contracts.yaml contract.customization_ids)에서 일치하는지의 판정. 값 = `{consistent: bool, divergences: [...]}`. 어긋난 소스가 있으면 divergence로 기록(현재 1.13.1은 일치). 위조 저항: 한 곳만 조작하면 여기서 드러난다.

### 2.2 `contract-tests` (fact_id)
kind: `contract_tests`. 계약별 테스트. 값 = contract_id로 정렬된 매핑:

```yaml
CONTRACT-INSTANCE-CODE:     # contracts.yaml의 contract.id
- tests/bank/contracts/test_instance_code.py::test_roundtrip
```

- contract가 required_tests 없으면 `[]`.

## 3. namespace 구분 (제품 vs 검사기)

- `changed_paths` = **제품 repo** 경로(매니페스트). `tests` = **검사기 repo** selector. 두 필드를 **분리**해 담고, 한 경로 집합으로 섞지 않는다.
- (참고) 향후 A-3가 "관측된 제품 diff ∩ 그 ID의 changed_paths"를 계산할 때 제품 namespace만 교차하도록 이 분리가 전제.

## 4. 결정론 / canonical

- 모든 리스트·매핑 키를 **명시적으로 정렬**. 중복 제거. (주의: `canonical_digest`(`acgh/verdict.py:62`)는 dict 키만 정렬하고 **리스트 순서는 보존**한다 → 결정론은 전적으로 collector의 정렬에 달림. 삽입순서에 의존하지 말 것.) `schema.py:77 canonical_payload_digest`는 이를 감싼다.
- 같은 등록자료 → 같은 fact digest여야 함(재계산 대조가 이 fact도 커버).
- **stale digest 주의**: 신규 fact append로 전체 `discovered_facts_digest`는 **바뀐다**(per-item digest는 값 불변이라 안 바뀌고 기존 테스트 회귀 없음 — 리뷰 확인). 인계문서가 못박은 옛 digest(commit `a564d48`/tree·`/private/tmp` 예행연습 산출물)를 신규 수집 후 재사용 금지.

## 5. 범위 경계 (헛발질 방지)

- **하지 않는 것**: validate_proposal에서 이 fact를 강제/소비하는 로직(=A-3), verify 실행, 관측 분기 판정. 이번엔 **fact 생성·노출·테스트만**.
- **바꾸지 않는 것**: 기존 flat fact, 기존 검증 규칙, apply, 제품 코드, /om-plan SKILL·references.

## 6. 수용 기준 (Claude 반례 검증)

| # | 정상 | 반례(잡혀야) |
|---|---|---|
| 1 | `customization-relations`가 각 ID의 changed_paths·contracts·tests를 **그 ID 것만** 담음 | ID-A 경로가 ID-B 항목에 섞이면 실패 |
| 2 | 공유 경로는 그 경로를 매니페스트에 넣은 **여러 ID 각각**에 나타남(정상). **shared-path-owners와 등가 비교 금지** — shared-path-owners는 큐레이션 부분집합이라 manifest 파생 공유집합과 다르다(1.13.1 실증: serviceConnection.ts가 006·007 매니페스트엔 있으나 shared-path-owners엔 없음). 관계는 `customization-relations 공유집합 ⊇ shared-path-owners`(포함)만 성립 | 한 ID에만 임의로 몰면 실패 / #2를 등가로 검사하면 정상 데이터서 거짓 실패 |
| 3 | `contract-tests`가 contract별 required_tests를 정확히 분리 | 전역 union이면 실패 |
| 4 | changed_paths(제품)와 tests(검사기)가 필드 분리 + `tests`에 assurance.direct_tests 포함 | 한 집합에 섞이거나 direct_tests 누락 시 실패 |
| 5 | 레지스트리 entry 순서·매니페스트 경로 순서를 **뒤섞어 입력해도 동일 digest** | 정렬 누락으로 순서 치환 시 digest 달라지면 실패 |
| 6 | 기존 flat fact·기존 테스트 회귀 0 | 회귀 시 실패 |
| 7 | 매니페스트 부재/경로이탈 → 기존 방어 유지 | 우회되면 실패 |
| 8 | `required_changed_paths`가 매니페스트 값대로 per-ID 보존(⊆ changed_paths) | 누락/전체 changed_paths로 대체 시 실패 |
| 9 | `id-contract-consistency`가 세 소스 불일치를 divergence로 잡음 | 한 소스만 조작해도 consistent=true면 실패 |

> **주의(P1 지뢰 실현 조건)**: 위 #2의 거짓 실패는 **A-3가 "customization-relations 공유집합 == shared-path-owners" 등가 검사를 넣을 때** 실제로 터진다. A-4(수집)에서는 fact만 만들므로 안전하나, A-3 설계 시 이 등가검사를 넣지 말 것(포함관계만). A-3 명세에 이 경고를 전달한다.
