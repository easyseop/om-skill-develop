# 모드별 생애주기 시나리오 초안 (검토용, 2026-08-20)

성격: 확정 아님. 적대 검토용 제안. 근거는 28(전수 매트릭스)·24(결정)·22(감사)·01A(설계).

## 원칙

1. **자동화 최대화** — 사람은 최종 배포 승인만. 계획 단계엔 사람이 없으니 완전성은 기계가 강제(빠지면 block), 판단 불가만 질문.
2. **후보 파일 연속성(중요)** — plan이 만든 후보 산출물(`proposal/*`)을 implement·verify·apply가 **반드시 그대로 바라본다.** 각 단계가 스스로 재유도/표류하면 안 된다. 연속성은 `plan_digest`(=proposal+input_lock+facts 결속)로 강제: 각 단계는 자기가 다루는 후보가 승인된 plan_digest에 묶였는지 확인, 아니면 중단.
3. **재베이스·반영은 verify 게이트 통과 후 apply에서만.** plan은 아무것도 안 바꿈.

## 2가지 성격 (계약·테스트 취급을 가름)

- **동작 세움/바꿈**: initial(확립)·feature(신규)·change-동작변경 → 계약·테스트 신규/갱신.
- **동작 보존, 기반 이동**: upgrade·change-리팩터 → 계약·테스트 **그대로 + 재실행(생존확인)**. 바뀌는 건 버전·경로지 동작 아님.

## 단계 공통 계약 (4모드)

| 단계 | 입력(후보 연속성) | 하는 일 | 파일 변형 | 결속 |
|---|---|---|---|---|
| /om-plan | facts | 무엇을·어디로·어떤 계약/테스트 필요를 **계획** → `proposal/*` | 없음 | plan_digest 생성 |
| /om-implement | **plan의 `proposal/*`** | 후보대로 코드+테스트 작성/이동 | 제품 코드 | plan_digest 확인 |
| /om-verify | **plan의 `proposal/*` + 구현본** | 계약·테스트 실행 → 신규/생존 증명 | 없음 | plan_digest 확인 |
| apply | **검증된 후보** | 등록 반영(매니페스트·entry / upgrade는 source 재베이스) | 관리 파일 | plan_digest + verify-pass 확인 |

**후보 연속성 규칙(누락 금지):** implement는 plan의 path-remap·manifest-deltas·test-plan·contract 정의를 **소스로** 삼고, verify는 plan의 contracts-to-run·expected 변경을 소스로 삼는다. 어느 단계도 후보를 무시하고 새로 만들지 않는다.

## 모드별 시나리오

### initial (코드 이미 존재 → 카탈로그화)
- 구현 단계 없음(커스텀 이미 있음). plan(식별+계약·소유자·criticality 초안) → 사람 확인(판단부) → verify(기존 테스트 green 기준선) → bootstrap(전체 등록 기록).
- 갱신: 전체 관리 파일. 계약=초안+사람확인.

### feature (신규 동작)
- plan: 새 ID + **계약 정의 + 테스트 계획**(코드 아님) + 예상 changed_paths.
- implement: 후보대로 코드 + **테스트 작성**.
- verify: 새 테스트 + 회귀.
- apply: 새 매니페스트·registry entry. contracts.yaml·shared-path-owners에 **신규 반영**(자동화 목표: apply가 쓰거나, 못 쓰면 "사람 작업"을 명시 강제).
- source 블록: 불변.

### change (먼저 종류 판정 → 분기)
- plan 0단계: **동작-보존 vs 동작-변경** 판정(요청 명시 필드 권장).
  - 보존: 계약·테스트 그대로, 재실행. (upgrade와 동형, 단일 커스텀)
  - 변경: 계약·테스트 갱신/추가.
- manifest delta / source 불변(P1-1) / 공유파일 조건부.
- apply: manifest delta + (변경 시) entry contracts·shared 파일 갱신.

### upgrade (동작 보존, 버전 이동)
- plan: path-remap·영향 계약 식별(안 바꿈). 9항목 산출.
- implement: 새 공식버전 위로 병합 + 테스트 **경로만** 수정.
- verify: 기존 계약·테스트 재실행 → **생존 확인**.
- apply(re-base): verify 통과 시에만 source 블록·source-snapshot-owners·source-diff를 새 버전으로 재베이스. shared-code-definitions delta 병합.
- 계약·테스트: **신규 없음**(보존).

## 잠정 권고 (자동화-우선, 사람 확정 필요)

1. change 판정: 요청에 `change_kind: behavior_preserving|behavior_changing` 명시 필드 → 기계가 분기.
2. 재베이스 게이트: apply는 verify-pass를 반드시 확인(없으면 중단).
3. verify 실패 upgrade: 등록 옛 버전 유지 + 반영 차단.
4. Q12: feature/change도 계약·테스트 계획을 **필수 산출물로 강제**(upgrade 9항목처럼). 자동화 목표상 강제.
5. 사람-큐레이션 파일(contracts.yaml·shared-path-owners): **가능하면 apply가 후보로부터 자동 반영**, 진짜 사람 판단만 남는 부분(예: owner 신원)만 질문.

## 열린 갭 (이 초안이 겨냥)

- 덩어리 A(feature/change 델타가 계약·공유 파일에 전파) → Q12 + apply 화이트리스트 확장 또는 사람작업 강제.
- 덩어리 B(upgrade 재베이스) → Q10, 위 upgrade apply 시퀀스로 해소 제안.
- implement/verify가 후보를 안 보는 표류 위험 → plan_digest 연속성 강제.
