## P1 (2건)

### P1-1 — apply changed_path_count가 source-스코프 불변식과 충돌 (Q10 인접)
- A5 즉시 갭(count ↔ current-diff-paths.txt)은 닫혔다. 그러나 apply는 `source.changed_path_count`를 **current 스코프**(net_paths)로 덮으면서 같은 source 블록의 `diff_inventory`/`source-diff-paths.txt`는 **source 스코프**로 둔다 → source 블록 반쪽 갱신.
- 기존 `vendor_rebuild.build_reconstruction_plan`은 `len(source-diff-paths.txt)==changed_path_count`(source)를 강제. 두 스코프가 벌어지면(=om-temp-1.13.0 limitation이 명시한 후속작업 상황) apply가 **자기 source-gate를 실패시키는 번들**을 만든다. 반례 실증: `source diff inventory count 111 != registered changed_path_count 110`.
- 근거: `registration_prep.py:1054-1074`, `validate_registration_bundle.py:40-82`, `vendor_rebuild.py:100-106`.
- 판정: 결함으로 단정하기보다 **Q10(source 스코프 정의) 결정에 물린 위험**. Q10 확정 없이 지금 방향으로 두면 스코프 발산 시 모순.
- 최소안(결정 의존, 지금 구현 말 것): (a) count를 source 스코프로 유지(1072 재계산 제거, 교차검증은 diff_inventory 기준) **또는** (b) current로 갈면 apply가 diff_inventory도 current로 통일 — 이는 Q10 provenance 결정 필요.

### P1-2 — 결과서26의 "전체 harness/tests 그린" 주장이 clean-export에서 거짓
