## 1. 결과 요약

checker가 dirty라는 이유만으로 verify를 일괄 차단하던 조건을 다음과 같이 정밀화했다.

- checker가 clean이면 기존과 동일하게 다음 검사로 진행한다.
- checker가 dirty여도 모든 dirty 경로가 활성 등록부의 관리파일이고, 현재 파일 내용 digest가 apply 결과의 `management_file_digests`와 정확히 같으면 진행한다.
- 관리파일 밖 dirty 경로, 파일 누락·심볼릭 링크·읽기 실패, digest 불일치는 `VERIFY_CHECKER_DIRTY`로 차단한다.
- 차단 결과의 `mismatched_paths`에 경로·사유·기대/현재 digest를 기록한다.
- checker HEAD 동일성 검사와 등록자료 전체/개별 파일 digest 대조는 그대로 유지했다.

따라서 이번 변경은 checker dirty 허용으로 완화한 것이 아니라, apply가 만든 정확한 관리파일 상태만 예외적으로 인정하도록 범위를 좁힌 것이다.

### `harness/acgh/verifycore/workflow.py:250-276`

기존 검사 순서를 유지했다.

1. checker HEAD와 apply 결과의 SHA 대조
2. checker dirty 경로의 허용 범위·내용 대조

## 4. 리허설 81이 기존 검사에 걸리지 않은 이유

결론: 당시 verify 코드에 checker dirty 게이트가 없었던 것이 아니라, **리허설에서 verify가 바라본 checker 복사본이 clean이었고 해당 apply 계획에는 관리파일 변경 작업이 없었다.** 따라서 기존 clean 요구를 정상 통과했다.

실측 근거:

1. `git blame`상 checker dirty 게이트는 최초 om-verify 구현 커밋 `82be68e7336b5ba50062e66c824543eee1880212`에 포함되어 있다.
2. 리허설 결과서 80 §2는 당시 om-verify 구현이 검사기 작업 트리에 미커밋 상태로 존재했다고 기록한다.
3. 실제 `apply-refresh-run/apply-context.yaml`이 가리키는 checker는 구현 작업 트리가 아니라 별도 복사본이다.

   ```text
   work/om-apply-rehearsal-20260824-02/checker-normal
   HEAD b691f781d68f3d82211b5368e4ce0b86a13387ee
   ```

4. 결과서 80 §8과 결과서 81 §1·§5는 이 `checker-normal`이 clean이었다고 기록한다. 현재 보존된 복사본을 다시 확인해도 `git status --short` 출력이 비어 있다.
5. 실제 `apply-refresh-run`의 `execution_plan.management_actions`는 빈 배열이다. BANK-OM-005 제품 변경의 검증 인계를 새 형식으로 재발행한 시나리오였으며, 이번에 문제가 된 관리파일 `must_change` 작업을 수행한 시나리오가 아니었다.

즉, 리허설 81은 “관리파일 미커밋 변경이 있는 정상 apply → verify” 경로를 시험하지 않았다. 별도 clean checker snapshot을 사용했기 때문에 모순이 드러나지 않았다. 현재 실기동의 9개 관리파일 변경 경로가 이 누락된 상태를 처음 재현한 것이며, 이번 핫픽스는 그 상태만 digest 결속으로 허용한다.

## 7. 남은 확인 사항

1. 이번 테스트는 경로와 파일 내용을 실제로 만들지만 Git dirty 목록은 반례별로 주입한다. Claude 최종 검증에서는 현재 실기동 run의 실제 `git status --porcelain` 경로 9건을 그대로 사용해 한 번 더 확인하는 것이 좋다.
2. 허용되는 dirty 파일도 이후 adapter snapshot의 등록자료 전체·개별 digest 대조를 통과해야 한다. 따라서 승인 결과와 다른 관리파일 상태는 계속 차단된다.
3. 성공 후 관리파일을 언제 커밋할지는 별도 운영 절차 문제다. 이번 변경은 verify 시작 시점의 배타 모순만 해소한다.
