## 할 일

1. **`customization-relations` fact 추가** (kind `customization_relations`): ID로 정렬된 리스트, 각 항목에
   - `changed_paths` (매니페스트 implementation.changed_paths, 제품 repo, 정렬)
   - `required_changed_paths` (매니페스트 implementation.required_changed_paths, 정렬, ⊆ changed_paths)
   - `contracts` (registry `entry.contracts[]` = authoritative, 정렬)
   - `tests` (그 ID contracts→required_tests ∪ 매니페스트 `assurance.direct_tests`, 정렬, 검사기 selector, **그 ID 한정**)
2. **`contract-tests` fact 추가** (kind `contract_tests`): `{contract_id: [required_tests...]}` contract별 분리, 정렬.
3. **`id-contract-consistency` fact 추가** (kind `id_contract_consistency`): 세 소스(entry.contracts / manifest assurance.contracts / contracts.yaml contract.customization_ids)의 일치 여부 `{consistent: bool, divergences: [...]}`.
4. 기존 flat fact(registered-customizations·registered-customization-paths·registered-contracts·registered-tests·shared-path-owners)는 **전부 유지**.
5. 모든 리스트·매핑 키 **명시 정렬**(canonical_digest는 리스트 순서 보존하므로 삽입순서 의존 금지).

## 수용 기준 (명세 §6, Claude가 반례 검증)

1. `customization-relations`가 각 ID의 관계를 **그 ID 것만** 담음(ID-A 것이 ID-B에 안 섞임).
2. 공유 경로가 여러 ID 각각에 나타남(정상). **shared-path-owners와 등가 비교 금지** — 포함관계(⊇)만(1.13.1: serviceConnection.ts가 006·007엔 있으나 shared엔 없음 → 등가검사면 거짓실패).
3. `contract-tests`가 contract별로 분리(전역 union 아님).
4. changed_paths(제품)·tests(검사기) 필드 분리 + tests에 assurance.direct_tests 포함.
5. **entry 순서·매니페스트 경로 순서를 뒤섞어 입력해도 동일 digest**(정렬 강제 확인).
6. 기존 flat fact·기존 테스트 회귀 0.
7. 매니페스트 부재/경로이탈 → 기존 `REGISTRATION_MANIFEST_PATH_INVALID` 유지.
8. `required_changed_paths` per-ID 보존(⊆ changed_paths).
9. `id-contract-consistency`가 세 소스 불일치를 divergence로 잡음(한 소스만 조작해도 consistent=true면 실패).

각 수용기준에 반례 테스트 동반. 신규 fact로 전체 discovered_facts_digest는 바뀜(정상, per-item digest 불변이라 기존 테스트 회귀 없음) — 옛 산출물 digest 재사용 금지.
