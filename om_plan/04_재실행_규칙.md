# 재실행 규칙 — 실패하면 어디부터 다시 하나

## 문제 (사용자 질문에서 발굴 → 1차 검토 P1-9로 등록)

사용자 질문: "각 단계별로 실행 결과에 문제가 있으면 어디를 다시 봐야 하는지, 재실행 시점에 대한
의견이 설계에 있었나?"

확인 결과 **절반만 있었다**:
- 파이프라인 수준(A~D: 계획→구현→검증)의 "무엇이 바뀌면 어디부터"는 발표덱에 존재.
- `/om-plan` **내부 4단계**(preflight → 사실 수집 → LLM 제안 → 제안 검증)의 재실행 규칙은 부재.
  유일한 원칙이 "실행마다 새 폴더, 이전 실행 재사용 금지" = 사실상 "실패하면 통째로 다시".

더 나쁜 점: 로드맵(00)이 **스스로** "각 명령은 구현 전에 ④중단 조건과 실패 후 재실행 방법을
확정한다"를 조건으로 걸었는데 01A가 STOP만 정의 — **자기 확정 조건 미충족**.
비용 문제도 실재: upgrade의 공식 문서 수집(다운로드·버전 검증·digest)은 비싼 단계인데,
제안 검증만 실패해도 전부 반복해야 했다.

## 논의 경과

- "이전 run 재사용 금지"를 문자 그대로 지키면 재검증 비용 폭발,
  느슨하게 하면 LLM이 기존 run 안에서 사실 파일까지 고치는 구멍. → 원칙을 정밀화해야 한다는 결론:
  **"완료된 run 재사용 금지"**로 좁히고, 미완료 run의 부분 수정은 대상을 proposal로 한정.

## 결정 — 단계별 재실행 표 (01A에 확정)

| 실패 지점 | 다시 시작 | 재사용 가능 | 수정 가능 | 보존 |
|---|---|---|---|---|
| preflight 실패 | 새 run | 없음 | 입력 | 실패 결과·원인 |
| 사실 수집 실패 | 새 run | 검증된 문서 snapshot(조건부) | 새 입력 | 실패 run 전체 |
| 문서 수집 실패 | 새 run | 대상 버전·URL·byte digest 동일한 snapshot만 | 새 입력·새 snapshot | 출처·digest |
| LLM 제안 중단 | **같은 미완료 run** | 사실 파일·snapshot | `proposal/`만 | 사실 파일·중단 기록 |
| 제안 검증 실패 | **같은 미완료 run** | 사실 파일·snapshot | `proposal/`만 | **모든 검증 시도 이력·순서** |
| 검증 중 재계산 불일치 | 새 run | 없음 | 새 입력 | 불일치 결과·이전 run |
| 검증 완료 | 새 요청은 항상 새 run | 읽기 전용 근거로만 | 없음 | 완료 run 전체 |

- 같은 run 재검증 시 `input-lock`·`discovered-facts`·문서 snapshot은 **불변**.
- `validation-result.json` 하나를 덮어쓰지 않고 `validation-attempts/`에 append-only 보존.
- `/om-resume`은 **이 표의 자동화 후보일 뿐** 별도 판정 규칙이 아님 (완료 run 재개·facts 수정 불가).

## 고려한 것

- 비싼 단계(문서 수집)의 재사용 조건을 "URL 같음"이 아니라 **byte digest 같음**으로 —
  URL만 같고 내용이 바뀐 문서의 재사용을 차단 (R06).
- 검증 실패 시 사실까지 같이 고치는 우회(R03)와 이력 덮어쓰기(R05)를 반례로 못박음.

## 반영 위치

- 설계: `01A` §실패 후 재실행 규칙(표), `01` §4.4 말미, `common-control.md` Retry rule,
  `00` 로드맵(/om-resume 확정 시점 갱신)
- 반례: R01~R07 (7행 표와 1:1 대응)
- 2차 재검토 판정: **충족** (P1-9)
