## 조치 1 — clean-export의 dangling 명령 정합 (A2, P0)

- 문제: clean-export `om_workflow.py`가 `watch`·`risk`·`source`·`runtime`·`patch-kill`·`typecheck`·`apply`·`bootstrap` 서브명령을 노출하나, 그 워커 스크립트(prepare_registration.py·run_upgrade_watch.py 등)가 export에서 제외돼 **호출 시 FileNotFoundError**. 실동작은 `plan` 계열 5종뿐.
- 결정 필요: (a) export의 `om_workflow.py`를 `plan`·`plan-*`만 남기게 트림, 또는 (b) 워커 스크립트를 export에 동봉. **/om-plan 파이프라인만 담는 clean-export 취지에는 (a)가 정합**(권고, 단 Codex 확정).
- 할 일: 선택한 방향으로 CLI 표면과 실제 실행 가능 명령을 일치시킨다. export에 남는 명령은 전부 실행 가능해야 한다.

## 조치 2 — sensitive-zone/watch의 배포 정합 (A1, P0)

- 문제: clean-export에 `zones.py`·`run_upgrade_watch.py`·`run_upgrade_risk_gates.py`가 없어 sensitive-zone/watch 검사를 **실행할 수 없는데**, `sensitive-zones.yaml`은 배포돼 **데드 파일**로 남는다.
- 결정 필요: (a) watch/risk를 clean-export에서 돌릴 것이면 위 3개 + 의존 모듈 동봉, 또는 (b) sensitive-zone/watch는 완전본(별도 게이트 환경)에서만 돌린다고 확정하고 clean-export에서 `sensitive-zones.yaml`을 빼거나 "이 배포본에서는 미사용"을 명시.
- 할 일: 데드 파일이 남지 않게 (a)/(b) 중 하나로 정합. 어느 쪽이든 "watch가 어디서 실제로 도는가"를 결과 문서에 명시.

## 조치 3 — upgrade 산출물 3층 검증 (A3, ✅ 결정됨 Q11=3층)

- 문제: 01A §4는 upgrade 출력 9종(CHK-1~9)을 규정하나, `collectors.py::validate_proposal`은 3개만 조건부 형식검사하고 나머지(특히 path-remap)는 **존재조차 강제 안 함**. "존재만 강제"는 N/A·자기신고 라벨로 우회되는 checkbox 극장이라 폐기.
- **결정(Q11, 24 문서): 3층.** Codex는 아래 **층1·층3(결정론 검사)만 validate.py에 구현**한다. **층2는 검사기(결정론 Python)가 아니라 별도 LLM 판독**이므로 validate.py에 넣지 말 것(스킬 흐름/별도 agent 배선 — §조치 6 참조).
  - **층1 [사실-근거 커버리지, 못 속임]**:
    - `path-remap`: 영향 경로 = `official-upgrade-paths ∩ 등록 커스텀 경로`. proposal의 path-remap이 이 집합을 **전부 커버**해야 함(shared_impact의 자동 교집합과 동형). 빠진 경로 → block.
    - `doc-code-crosscheck`: `official-doc-findings`의 각 항목 id가 crosscheck에 연결돼야 함(operations의 finding_id 연결과 동형). 미연결 → block.
  - **층3 [존재만]**: `upgrade-plan` 등 나머지 판단형 산출물은 비어 있지 않은 존재만 강제.
- 할 일: `validate_proposal`에 위 층1·층3 검사 추가 + 반례 테스트(누락 경로 있는 path-remap → block, 미연결 finding → block, 판단형 누락 → block).
- 금지: 내용 "정확성"(어느 파일이 어디로가 맞나)까지 판정하지 말 것 — 그건 층2/뒤 테스트 몫.

## 조치 4 — apply의 changed_path_count 정합 (A5, P1)

- 문제: apply(`registration_prep.py::apply_plan`)가 `current-diff-paths.txt`는 다시 쓰나 `customization-registry.yaml`의 `source.changed_path_count`(정수)는 안 고쳐 **어긋날 수 있고**, bundle validator가 교차검증하지 않는다(추정, grep 기반 — 코드로 재확인 요망).
- 할 일: apply가 `source.changed_path_count`를 `current-diff-paths.txt` 실제 행수로 재계산하거나, bundle validator가 둘의 일치를 검사. 둘 중 하나로 어긋남을 차단.
- 선행: bundle validator(`om-temp-1.13.0/validate_registration_bundle.py`)가 실제로 이 값을 검사하는지 코드로 확정(감사는 grep 기반 추정).

## 조치 5 — CI가 approval(exit 2)을 성공으로 처리 (Q9, ✅ 결정됨: 성공)

- 문제: `/om-plan` 정상 결과는 대개 exit 2(approval)인데, CI 기본은 0만 성공 → 정상 계획이 빨간불. 이 때문에 GitLab 파이프라인을 아직 1회도 못 돌렸다.
- **결정(Q9, 24 문서): exit 2 → CI 성공으로 처리.** `/om-plan`은 아무것도 반영하지 않으므로 안전하고, 미해결 항목은 뒤 단계(apply owner_status 게이트·verify·최종 배포 승인)에서 강제된다. 계획 단계에 사람 정지 게이트를 두지 않는다.
- 할 일: GitLab 파이프라인 validate 잡(또는 `ci/om_plan_ci.py` wrapper)이 exit 2를 **CI 성공**으로 매핑. 가능하면 잡 상태/아티팩트에 "review-ready(사람 검토 대기)"를 표기해 "성공=자동 진행"으로 오인되지 않게 한다. exit 1(block)·3(analysis_error)은 그대로 CI 실패로 둔다.
- 주의: exit 2를 성공으로 바꾸되 **approval이 "배포 승인"이 아니라 "계획 검토 준비"임**을 상태 표기로 유지.

## 조치 6 — upgrade 문서 완전성 2차 판독 (Q11 층2, LLM 단계·검사기 아님)

- 문제: `official-doc-findings`·`operations`의 **문서 누락**(예: 릴리스노트의 "기동 전 DB 마이그레이션"을 LLM이 못 봄)은 **코드가 아니라 배포 요구사항**이라 뒤 계약 테스트가 못 잡고 운영에서 터진다(05 문서 한계).
- 성격: 이건 결정론 검사가 아니라 **독립 LLM 판독**이다. `validate.py`에 넣지 말 것(검사기는 LLM을 타지 않는다는 원칙 유지).
- 할 일: proposal 작성 LLM과 **분리된 컨텍스트의 LLM(별도 agent)**이 `official-doc-snapshots/*` 원문 bytes를 직접 읽어 요구사항 findings를 독립 추출하고, proposal의 `official-doc-findings`와 대조해 **누락 항목**을 산출. 누락이 있으면 unresolved-question 또는 block으로 게이트.
- 배선: 이 2차 판독을 /om-plan 흐름의 어느 지점(예: proposal 후 validate 전)에 둘지, 결과를 어디에 기록·게이트할지 결정. 같은 LLM이 자기검토하면 편향으로 무의미하므로 **반드시 독립 컨텍스트**.
- 정직 고지: 2차 판독도 LLM이라 ground truth가 아니다 — 게으른 누락을 줄이되 없애지는 못한다. 잔여 위험은 결과 문서에 명시.
