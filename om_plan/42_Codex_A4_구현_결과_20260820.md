## 1. 구현 목적과 범위

기존 collector는 등록된 ID, 경로, 계약, 테스트를 각각 하나의 목록으로 합쳤다. 이 방식은 `BANK-OM-001`의 경로·계약·테스트가 무엇인지 ID 단위로 다시 연결할 수 없었다.

이번 구현은 등록자료에 이미 있는 관계를 다음 세 fact로 보존한다.

- `customization-relations`: ID별 변경 경로·필수 경로·계약·테스트
- `contract-tests`: 계약별 필수 테스트
- `id-contract-consistency`: Registry·Manifest·계약 파일의 ID↔계약 관계 일치 여부

범위는 **사실 수집과 노출**까지다. 새 fact를 사용해 proposal을 차단하거나 관측 분기를 판단하는 A-3 로직과 downstream verify는 추가하지 않았다.

## 3. 신규 fact 출력 예시

테스트 등록자료의 핵심 출력은 다음과 같다.

```yaml
customization-relations:
- customization_id: BANK-OM-001
  changed_paths:
  - product/a.py
  - product/shared.py
  required_changed_paths:
  - product/a.py
  contracts:
  - CONTRACT-A
  tests:
  - tests/contracts_a.py::test_roundtrip
  - tests/direct_a.py::test_guard
- customization_id: BANK-OM-002
  changed_paths:
  - product/b.py
  - product/shared.py
  required_changed_paths:
  - product/b.py
  contracts:
  - CONTRACT-B
  tests:
  - tests/contracts_b.py::test_roundtrip

contract-tests:
  CONTRACT-A:
  - tests/contracts_a.py::test_roundtrip
  CONTRACT-B:
  - tests/contracts_b.py::test_roundtrip

id-contract-consistency:
  consistent: true
  divergences: []
```

`product/shared.py`는 두 Manifest에 모두 있으므로 두 ID 관계에 모두 나타난다. 이 결과를 `shared-path-owners.yaml`과 같다고 판정하는 로직은 넣지 않았다.

## 7. 범위 준수와 남은 위험

### 이번에 하지 않은 것

- `validate_proposal`에서 신규 fact를 읽거나 강제하지 않음
- 관측된 제품 diff와 ID별 경로를 비교하지 않음
- contract·runtime verify를 실행하거나 연결하지 않음
- apply, 제품 코드, 활성 등록자료, `/om-plan` `SKILL.md`·references를 수정하지 않음

코드 검색 결과 신규 fact ID는 collector와 신규 test에만 존재한다. 따라서 수집 결과가 불일치해도 현재 단계에서는 divergence를 **기록만** 하며 자동 block하지 않는다. 소비와 판정은 A-3 범위다.

### 후속 작업에서 지켜야 할 사항

1. A-3는 Manifest에서 계산한 공유 경로 집합과 `shared-path-owners.yaml`을 등가 비교하면 안 된다. 큐레이션 파일은 부분집합이므로 포함관계만 사용할 수 있다.
2. `required_changed_paths ⊆ changed_paths`의 위반을 차단하는 새 규칙은 이번 범위에 넣지 않았다. 이번 구현은 원본 값을 그대로 보존한다.
3. 신규 fact가 추가됐으므로 다음 수집의 전체 `discovered_facts_digest`는 이전 산출물과 달라진다. 과거 evidence의 digest를 새 plan에 재사용하면 안 된다.
4. Claude 독립 반례 검증에서 신규 fact를 의도적으로 섞거나 누락했을 때 위 테스트가 실제로 실패하는지 다시 확인해야 한다.
