## 질의 ① — 재베이스(upgrade re-base)를 어느 단계에서, 어떻게 통제하나

### 배경 (사실)
- upgrade로 OM 버전을 올리면 등록부 `source` 블록을 새 바닥으로 갱신해야 한다: `upstream_tag`·`upstream_sha`(새 릴리즈), `snapshot_sha`(새 커스텀 스냅샷), `changed_path_count`, `diff_inventory`(source-diff-paths.txt).
- **여러 번 버전업(1.13.1→2→3…)에는 이 재베이스가 필수** — 2번째 업그레이드가 올바른 바닥에서 비교하려면.
- 현재: apply(`registration_prep.py`)는 `snapshot_sha`를 **read-only**로만 쓰고 갱신하지 않는다(Claude 실측). custom_baseline은 요청서에서 들어와 어떤 잠긴 SHA와도 대조 안 됨(`preflight.py:150-153`).
- 관련 사람 결정(대기·확정): Q10(재베이스, 열림), 기준선 잠금 A는 "릴리즈 때만 전진"(R-1, 확정·임시), P1-1: `changed_path_count`는 원본(source) 스코프 = `build_reconstruction_plan` 불변식.

### 물어보는 것 (선택지+트레이드오프, 단독 결정 금지 — Q10은 사람 결정)
1. **어느 단계에서 source 블록 재베이스를 계산·기록해야 하나?** plan / implement(미구현) / apply 각각의 장단점. 특히 "실제 재베이스된 코드 트리가 있어야 전체 diff가 확정된다"는 제약을 고려해.
2. **어떻게 통제(오·조용한 재베이스 방지)하나?** 후보: `changed_path_count == build_reconstruction_plan` 불변식 재검증 / 새 base SHA를 릴리즈 잠금과 대조 / 재계산된 source-diff-paths.txt를 실제 트리로 확정 / 사람 승인 게이트. 각 방식이 무엇을 막고 무엇을 못 막는지.
3. **후보(upgrade 산출물)에 이미 있는 데이터로 어디까지 파생 가능하고, 무엇은 실제 트리에서만 나오나?**(등록 밖 잔재 포함 여부 등)
4. 기존 결정(R-1 릴리즈-only 전진, P1-1 source 스코프)과 **충돌 없는** 안을.

### 답변 형식
선택지별 [단계 · 통제방식 · 막는 것/못 막는 것 · 기존결정 정합 · 권고]. 사람이 Q10을 정하도록 **옵션으로** 제시.

## 질의 ② — "등록 밖 변경(unregistered change)" 게이트가 정말 없나

### Claude의 실측(plan 단계 한정) — Codex가 독립 확인·반박
- `registered-customization-paths` fact는 생성되나(`collectors.py`), **`validate_proposal`에서 소비·대조 안 됨**(내 grep: validate.py·collectors 판정부에 `registered-customization-paths` 미사용).
- `net-custom-paths`(initial)·`observed-change-paths`(change)를 등록 경로와 **차집합 비교하는 게이트 없음**.
- 등록부 `source.unregistered_findings`는 **정적 필드(사람 작성)**로 보이고, 검사기가 계산·강제하는 흔적을 못 찾음.
- **결론(잠정)**: plan `plan check` 단계에는 "바뀐 경로인데 어떤 커스텀도 등록 안 함 → block/flag" 게이트가 **없다.**

### 물어보는 것
1. **위 잠정 결론이 맞나?** plan 단계(`validate_proposal`·`validate.py`)에 실제 diff경로 ↔ 등록경로 커버리지 대조가 **정말 없는지** 파일·줄로 확인/반박.
2. **apply 단계는 어떤가?** `registration_prep.py`의 `build_reconstruction_plan`이 `source-diff-paths.txt`(=전체 커스텀 diff)를 쓰는데, **여기서 "등록 안 된 경로"를 잡거나 막는 로직이 있나?** (있으면 파일·줄·차단 조건. 없으면 "없음" 명시.)
3. 어느 단계든 **부분적으로라도** 등록 밖 변경을 잡는 장치가 있으면 전부 열거. 없으면 "전 단계에 없음"을 확정.

### 답변 형식
