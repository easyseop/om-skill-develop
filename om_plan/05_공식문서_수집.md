# 공식 문서 수집 (upgrade 모드) — 위조·구버전·정규화 함정

## 문제

`/om-plan upgrade`는 Git diff만으로는 모르는 것(변경 의도·migration·호환성·배포 절차)을
공식 릴리스 노트·업그레이드 가이드에서 읽어야 한다. 여기에 함정이 여럿 있었다:

1. **정규화 함정** (1차 P1-5): 초안은 `content_sha256: digest of normalized main content` —
   "정리된 본문"의 정규화 규칙이 미정의라, 같은 문서를 두 번 받아도 광고·네비게이션·타임스탬프로
   digest가 달라질 수 있음. 내용 변경 감지(C28)가 오탐/미탐.
2. **구버전 함정** (C29): `latest` URL·화면 버전 표시는 대상 버전인데 본문은 이전 버전 설명.
3. **기억 위조** (C27): 네트워크 실패 후 LLM이 기억으로 문서 내용을 작성.
4. **검증 한계 과대 서술** (1차 P1-4): "문서가 migration을 요구하는데 계획에서 빠지면 validation
   실패"(C24) — 그러나 문서 해석(findings)은 LLM 산출물이라, **LLM이 원문에서 migration을 아예
   안 읽어낸 경우**는 어떤 기계 검증도 못 잡는다. 기계가 할 수 있는 건 "findings에 적힌 것이
   checklist에 반영됐는가"까지.
5. **다중 홉 미정의** (1차 P1-7): 1.13.1→1.15.0처럼 버전을 건너뛰면 중간 버전 문서·migration
   누적 규칙이 없는데 입력·반례 모두 단일 홉 전제.

## 결정

1. **정규화 포기, 원문 그대로**: 받은 응답 raw bytes를 `official-doc-snapshots/`에 저장하고
   **그 파일 bytes의 digest**를 기록. LLM이 추린 본문은 저장·hash 대상이 아님.
   해석은 항상 저장된 snapshot 기준.
2. **버전 token 검증**: 저장된 snapshot에서 버전 표기를 추출해 요청 버전과 대조.
   불일치면 `status: unverified` + STOP.
3. **기계 수집(출처·digest) / LLM 해석(findings) / 대조(crosscheck) 3파일 분리**.
   문서-코드 관계는 5분류: 양쪽 있음 / 문서만(위치 미확인) / 코드만(미문서화 위험) /
   운영 절차 전용 / **서로 모순(`documented_contradicts_observed` — 2차에서 추가, 어느 쪽도 임의 채택 금지)**.
4. **검증 한계를 정직하게 문서화**: C24를 "findings→checklist 정합 검사"로 재정의하고,
   원문 누락 여부는 **사람이 snapshot과 findings를 함께 검토**한다고 명시.
5. **버전 관계 분류**: adjacent / non_adjacent / equal / reversed. 사람 정책(Q2) 확정 전에는
   adjacent 외 전부 `analysis_error` — 임의로 릴리스를 합성하지 않음.
6. 폐쇄망: 사전 다운로드 문서도 URL·대상 버전·조회 시각·raw snapshot·byte digest가 있어야만 대체 입력 허용.

## 고려한 것

- OpenMetadata 공식 docs가 latest 중심이라 과거 버전 본문 확보가 어려울 수 있음 →
  그래서 "문서 없음 = analysis_error, 조사 결과는 `code_only_preliminary`로만 보관(구현 승인 근거 불가)".
- snapshot 재사용은 새 run에서 대상 버전·URL·**byte digest**가 모두 같을 때만 (R06, 재실행 규칙과 연동).
