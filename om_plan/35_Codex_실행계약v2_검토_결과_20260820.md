## 1. 최종 판정

**설계 수정 후 가능. 현재 v2 그대로는 구현 착수 불가다.**

v2는 v1보다 분명히 나아졌다. `plan-approval`, `implement-result`, `verify-receipt`를 분리하고, Q10을 미결정으로 되돌렸으며, 계약·공유 파일의 자동 반영을 금지했다. 그러나 문서에 아티팩트 이름과 필드 목록을 적은 것만으로 실행 계약이 성립하지는 않는다.

현재 남은 핵심 문제는 다음과 같다.

1. 계획 승인·구현 결과·검증 결과를 연결할 **검증 가능한 digest 체인**이 아직 완성되지 않았다.
2. 구현 결과가 계획보다 **빠진 경우**를 현재 subset 규칙이 잡지 못한다.
3. 검증 영수증이 실제 후보 commit·실행 이미지·테스트 환경·테스트 집합에 충분히 결속되지 않는다.
4. `change`의 계약 앵커를 계산하는 데 필요한 **ID별 경로·계약·테스트 관계가 현재 facts에서 소실**된다.
5. 구현 후 deviation·충돌이 발생하면 기존 proposal-only resume을 쓸 수 없는데, v2는 새 run과 resume의 경계를 모호하게 남겼다.
6. Q9의 “CI exit 2 성공 처리”를 “구현 자동 승인”으로 확대 해석했다. 이는 확정된 결정이 아니다.
7. 사람이 직접 수정하는 curated 파일이 원래 계획과 등록 상태를 바꾸는데, 그 변경을 다시 연결하는 절차가 없다.
8. mutant를 필수로 선언했지만 Q7은 여전히 보류 중이고, 현재 patch-kill 규약과도 범위가 다르다.

즉, v2는 **아티팩트의 목록**은 만들었지만, 아직 **누가 무엇을 재계산하고 어떤 불일치를 차단하는지**가 완결되지 않았다.

이번 검토는 정적 검토만 수행했다. 구현·설정·등록자료를 수정하지 않았고, 테스트·커밋·push도 수행하지 않았다.

## 3. 질문 2 — 신규 아티팩트 3종 구현 가능성

### 3.1 `plan-approval.yaml`

판정: **현재 정의로는 구현 불가. 스키마 작성은 가능하지만 승인 증거로 쓸 수 없다.**

검증 불가능하거나 미정의인 지점:

1. `plan_digest`가 무엇을 포함하는지는 현재 plan digest 정의와 연결할 수 있지만, 승인 대상 validation attempt와 result가 빠진다.
2. `approved_scope`가 proposal에서 계산되는 값인지 사람이 다시 쓰는 값인지 미정이다. 사람이 복사하면 두 번째 자기신고가 된다.
3. `approved_by: automation-policy:<id>`의 정책 실체·digest·결정 결과가 없다.
4. 승인 사유, 만료, 철회, superseded 상태가 없다.
5. approval 자체 digest와 canonical payload가 없다.
6. unresolved owner나 required human action이 있는 계획을 승인할 수 있는지 규칙이 없다.

반례: `approved_scope`에서 위험 경로 하나를 빼고 approval을 만든다. proposal과 자동 대조하지 않으면 좁아진 범위로 구현이 진행된다.

필요 필드의 최소선:

```yaml
run_id: ...
plan_digest: sha256:...
plan_result_digest: sha256:...
validation_attempt_digest: sha256:...
approved_scope_digest: sha256:...
approved_by: ...
approved_at: ...
reason: ...
policy_decision_digest: null
approval_digest: sha256:...
```

### 3.2 `implement-result.yaml`

판정: **현재 정의로는 구현 불가. 특히 subset 규칙이 안전하지 않다.**

문제:

1. `actual_paths ⊆ expected_paths + approved deviations`는 계획보다 빠진 구현을 통과시킨다.
2. path에 repository 구분과 add/modify/delete/rename 상태가 없다.
3. `approved deviations`가 어떤 approval에 결속됐는지 없다. deviation 자체가 우회 화이트리스트가 될 수 있다.
4. 구현 기준 commit·tree·repo와 plan approval digest의 결속이 부족하다.
5. self-digest 계산 규칙이 없다.
6. 충돌 해결 결과와 일반 deviation의 차이가 없다.
7. manual implementation에서 commit 전·후 어느 시점에 결과를 만드는지 없다.

코드 근거:

- 현재 request는 product/checker repo를 구분한다: `work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/acgh/plancore/schema/plan-run-request.schema.json:19-39`.
- 현재 preflight는 product ref와 checker HEAD/tree를 따로 결속한다: `work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/acgh/plancore/preflight.py:146-179`, `206-250`.

반례: expected가 `A.java`, `B.java`인데 구현은 `A.java`만 변경한다. 현재 subset 조건은 참이므로 B 누락을 통과시킨다.

최소 보강:

- 계획 항목별 `required`, `optional`, `retired`, `manual_action` 상태를 두고 완전성을 항목 단위로 검사한다.
- 경로는 `{repository, path, change_type, plan_item_id}`로 기록한다.
- 모든 deviation은 별도 approval digest에 결속하고 원래 계획을 supersede해야 한다.

### 3.3 `verify-receipt.yaml`

판정: **현재 정의로는 구현 불가. 검증했다는 주장만 기록할 수 있고 재현 가능한 영수증이 되지 않는다.**

문제:

1. candidate tree만 있고 repo·commit·artifact가 없다.
2. 실행 이미지, fixture, 환경 설정, harness/suite/catalog/policy 버전이 없다.
3. `log_digest`는 원본 위치·보존 규칙·재생 방법이 없어 확인할 수 없다.
4. `command + exit_code`만으로 test semantics와 completeness를 증명할 수 없다.
5. required contracts/test 집합을 누가 재계산하는지 없다.
6. mutant 결과의 필드와 성공 조건이 없다.
7. receipt 자체 digest가 없다.
8. apply가 receipt를 어떤 스키마와 코드로 다시 확인하는지 없다.

코드 근거:

- 현재 `TestRunSet`은 필요한 결속 모델을 이미 제공한다: `work/review-openmetadata-test-om-plan/harness/acgh/testruns.py:44-73`, `178-255`.
- 현재 release 검증도 후보와 test run set을 함께 대조한다: `work/review-openmetadata-test-om-plan/harness/acgh/release.py:156-236`.

반례: 필수 테스트 9개 중 1개만 실행하고 exit 0을 받은 로그를 receipt에 적는다. 필수 집합 재계산이 없으면 “실행한 1개는 성공”을 “검증 완료”로 오인한다.

### 3.4 digest 체계 충돌 여부

판정: **기존 체계와 기술적으로 충돌하지는 않지만, 새 정의가 기존 체계를 충분히 재사용하지 않는다.**

- 기존 canonical digest 패턴은 재사용 가능하다: `work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/acgh/plancore/schema.py:77-84`.
- 기존 CandidateLock·TestRunSet·ReleaseLock을 참조하면 중복 모델을 피할 수 있다.
- 새 아티팩트별 digest를 별도로 정의하되, 상위 아티팩트가 하위 아티팩트의 **내용 전체가 아니라 검증된 digest**를 결속해야 한다.
- 현재 v2의 `self_digest`는 self 필드 제외, key 정렬, timestamp 정규화, 파일 경로 포함 여부가 없어 구현자마다 결과가 달라질 수 있다.

## 4. 질문 3 — §4 관측 분기의 계산 가능성

판정: **현재 코드로는 정확한 ID별 계약 앵커를 계산할 수 없다.**

### 현재 가능한 것

- registry의 ID 목록 수집.
- 모든 Manifest의 `changed_paths` 합집합 수집.
- 모든 contract ID와 test ID 합집합 수집.
- shared owner 목록 수집.

코드 근거: `work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/acgh/integrations/om/collectors.py:44-127`, `359-385`.

### 현재 불가능한 것

1. `BANK-OM-001 -> product changed_paths` 같은 ID별 관계가 facts에서 소실된다.
2. `BANK-OM-001 -> contract IDs -> test selector paths` 관계가 합집합으로 평탄화된다.
3. product repo 경로와 checker repo 테스트 경로가 같은 namespace처럼 취급될 위험이 있다.
4. post-change 관측은 product repo 변경만 본다: `collectors.py:305-326`.
5. checker repo는 clean HEAD/tree만 lock되고, 변경 후보 ref나 diff가 request에 없다.
6. shared path는 여러 ID가 소유하므로 단순 교집합으로 단일 ID의 행위를 판정할 수 없다.

### 앵커 정의 자체의 구멍

- 경로를 건드렸다는 사실은 동작을 바꿨다는 증거가 아니다. 주석·import 정리·format 변경도 걸린다.
- 경로를 건드리지 않았다고 동작이 유지된 것도 아니다. 공용 API·schema·framework 변경으로 간접 영향이 생길 수 있다.
- 테스트 파일 변경은 “계약이 변했다”는 신호일 수 있지만, 새 공식 구조에 맞춘 test harness 보정일 수도 있다.
- 삭제·rename·move를 문자열 경로로만 보면 이전 경로와 새 경로의 관계를 잃는다.

반례 1: 공용 `CollectionDAO.java`에 BANK-OM-002만 관련된 수정이 생기지만 owner 목록에는 001·002가 함께 있다. 단순 경로 교집합은 두 ID를 모두 behavior-changing으로 판정한다.

반례 2: 제품 코드는 그대로이고 checker test만 느슨하게 수정해 실패를 숨긴다. 현재 post-change facts는 checker diff를 보지 못해 이를 관측하지 못한다.

최소 보강:

- facts에 다음 관계를 보존한다.

```text
ID → product paths
ID → contract IDs
contract ID → checker test selectors
shared path → owner IDs
각 경로 → repository + change type + digest
```

- “앵커 접촉”은 자동 behavior-changing 확정이 아니라 **contract review required** 신호로 사용한다.
- checker candidate ref/diff를 request·input-lock·facts에 추가한다.

| 상황 | 허용 방식 | 이유 |
|---|---|---|
| 구현 전 proposal 검증 실패 | 같은 run proposal-only resume | 입력·facts가 같고 제안만 수정한다. |

v2의 “새 run 또는 proposal-only resume”은 이 경계를 흐린다: `33_생애주기_실행계약_v2_초안_20260820.md:65-68`.

## 8. 추가 적대 발견

### P0-A. curated 수동 변경이 아티팩트 체인을 끊는다

v2는 자동 overwrite를 막았지만, 수동 수정 뒤 원래 plan의 input-lock과 registration digest가 낡는 문제를 해결하지 않았다. 안전해지려면 수동 변경을 action receipt로 기록하고 새 run에서 다시 수집해야 한다.

### P0-B. mutant 필수와 Q7 보류가 모순이다

Q7이 아직 사람 입력·pending으로 남아 있는데 v2 §5는 mutant 계약을 기준선으로 요구한다. 1차 구현에서는 기존 patch-kill 지원 범위를 명시적으로 재사용하거나, Q7 확정 전까지 mutant를 필수 gate로 만들면 안 된다.

### P1-A. “계약 변경” 트리거가 proposal 누락에 취약하다

대체·폐기 신호가 proposal finding에 의존하면 LLM이 놓친 요구사항은 retire 검토 자체를 시작하지 못한다. 공식 문서 finding을 discovered facts로 구조화하고 proposal과 독립적으로 cross-check해야 한다.

### P1-B. 동일 tree와 동일 실행 후보를 혼동한다

동일 tree를 가진 여러 commit이 존재할 수 있다. 감사와 승인에는 commit provenance가 필요하고, runtime에는 image/artifact가 필요하다. tree만으로 충분하지 않다.

### P1-C. 검증 결과의 보존·조회 계약이 없다

digest만 남기고 원본 log나 evidence URI를 보존하지 않으면 나중에 감사자가 내용을 재확인할 수 없다. 보존 기간, immutable 위치, digest 재검산 방법이 필요하다.

### P2-A. 시간·식별자 형식이 정의되지 않았다

timestamp는 RFC 3339 문자열, ID는 허용 패턴, 경로는 repo-relative POSIX로 정규화하는 등의 공통 형식이 필요하다.

---

## 9. 우선순위와 최소 보강안

### P0 — 구현 전 반드시 수정

1. 신규 아티팩트 3종의 canonical schema·self-digest·재계산 주체를 정의한다.
2. `plan-approval`을 latest validation attempt와 plan result에 결속한다.
3. `implement-result`의 subset 규칙을 폐기하고 required/optional/retired 항목 완전성으로 바꾼다.
4. `verify-receipt`가 CandidateLock·TestRunSet·artifact·환경·fixture·policy를 참조하게 한다.
5. apply가 verify receipt digest와 정확한 candidate commit/tree/artifact를 재검산하도록 계약을 수정한다.
6. ID별 product paths·contracts·tests 관계를 facts에 보존하고 repo namespace를 분리한다.
7. proposal-only resume과 구현 후 새 run을 명확히 분리한다.
8. curated 수동 action receipt와 수동 변경 후 새 run 규칙을 추가한다.
9. Q7 확정 전 mutant 필수화를 보류하거나 기존 patch-kill 범위로 제한한다.
10. Q13 확정 전 자동 plan approval을 금지한다.
11. A5 작업 트리 모순을 확정 결정에 맞게 해소한 뒤에만 기존 freshness 검사를 전제로 삼는다.

### P1 — 1차 구현 범위에서 보강

1. proposal index와 허용 파일 digest를 도입한다.
2. checker candidate ref/diff를 request·lock·facts에 추가한다.
3. add/modify/delete/rename과 repo를 경로 모델에 포함한다.
4. contract retire trigger를 discovered facts와 독립 판독 결과에서 재계산한다.
5. policy approval의 보호된 정책 digest·evaluator result를 정의한다.
6. evidence URI·보존·재검산 규칙을 정의한다.
7. 이전 run supersede·approval 철회·재사용 금지 규칙을 정의한다.

### P2 — 구현 중 정리 가능

1. 공통 timestamp·ID·path 정규화 규칙.
2. 사람이 읽는 요약 문구와 상태 코드의 일관성.
3. evidence 파일 이름과 폴더 배치 표준화.

## 10. 구현 착수 전 사람 결정이 필요한 질문

다음은 구현자가 임의로 확정하면 안 된다.

1. Q13: 어떤 plan 분류까지 자동 승인 정책에 위임할 것인가?
2. Q7: mutant/patch-kill을 모든 계약에 필수화할 것인가, high/critical만 적용할 것인가?
3. curated 수동 변경은 원래 plan approval의 하위 action으로 볼 것인가, 항상 새 plan 승인을 요구할 것인가?
4. deviation이 하나라도 생기면 항상 새 plan인가, 사전 승인된 deviation class를 허용할 것인가?
5. verify receipt의 runtime 환경·fixture는 어느 수준까지 재현 가능해야 하는가?
6. contract retirement의 최종 승인자는 기능 owner인가, 통합 승인 담당자인가?

권고:

- 1차 구현에서는 자동 plan approval을 제외한다.
- mutant는 기존 patch-kill이 실제 지원하는 범위로 제한한다.
- curated 변경과 deviation은 모두 새 run으로 연결한다.
- verify receipt는 기존 CandidateLock·TestRunSet·ReleaseLock을 참조하고 새 유사 모델을 만들지 않는다.

---

## 11. 수용 기준

다음 반례가 실제로 차단되기 전에는 v2 구현 완료로 판정하면 안 된다.

1. expected A·B 중 A만 구현하면 실패한다.
2. 승인 뒤 proposal 또는 validation result가 바뀌면 approval이 무효화된다.
3. 같은 tree의 다른 commit 또는 다른 image로 test하면 verify가 실패한다.
4. 필수 테스트 일부만 실행하면 receipt가 실패한다.
5. checker test만 느슨하게 바꾼 경우 change 관측이 이를 보고한다.
6. 사람이 curated 파일을 계획과 다르게 수정하면 다음 단계가 중단된다.
7. 구현 후 deviation을 같은 completed run의 resume으로 덮어쓸 수 없다.
8. LLM이 임의의 `automation-policy:<id>`를 쓰면 승인되지 않는다.
9. mutant 파일만 만들고 mutation을 실행하지 않으면 검증 완료가 되지 않는다.
10. 공식 문서의 폐기 요구를 proposal이 누락해도 독립 facts가 불일치를 보고한다.
11. A5에서 source inventory 수와 current working diff 수가 달라도 정본 count가 바뀌지 않는다.

## 12. 결론

v2는 v1의 가장 큰 문제였던 “plan 이후가 비어 있음”을 인식했고, 아티팩트 체인의 방향도 맞다. 그러나 현재 상태는 **이름이 붙은 세 파일을 추가한 설계 초안**이지, 실행 가능한 안전 계약은 아니다.

구현 전에는 최소한 다음 네 축을 확정해야 한다.

1. 아티팩트별 digest와 재계산 규칙.
2. ID·계약·테스트·repo 관계를 보존하는 facts 모델.
3. 구현 후 새 run과 proposal-only resume의 경계.
4. 사람 승인과 자동 정책 위임의 실제 권한 경계.

최종 판정은 다음과 같다.

> **설계 수정 후 가능. P0 보강과 사람 결정이 끝나기 전에는 구현 착수 금지.**
