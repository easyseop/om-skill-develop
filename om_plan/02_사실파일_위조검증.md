# 사실 파일 위조 검증 — "검사기만 사실을 쓴다"를 실제로 보장하기

## 문제

`/om-plan`의 신뢰 대전제: 사실(`discovered-facts.json`·`input-lock.yaml`)은 검사기만 쓰고,
LLM은 읽기만 한다. LLM의 모든 `observed` 주장은 이 파일을 가리키는 것으로 신뢰를 얻는다.

그런데 (1차 검토 P0-2):
- Hook은 **Edit/Write 도구만** 막는다. LLM은 **Bash로도 파일을 쓸 수 있다**
  (`python -c "json.dump(가짜사실, …)"`) — DESIGN.md 스스로 "Bash 문자열 검사는 신뢰 불가"라고 인정.
- 마지막 관문 `plan-validate`의 검사 목록은 전부 **proposal 검사**였다.
  사실 파일 자체가 진짜인지는 검사 항목에 없음 → 위조된 사실을 가리키는 proposal이 전 검증 통과.

파생 문제(P1-1): evidence_ref의 JSON pointer도 형식만 보면
`discovered-facts.json#/없는/경로` 같은 **허상 pointer**가 통과한다.

파생 문제(P1-6): 다음 단계로 넘기는 `plan_digest`가 proposal만 커버 —
계획 승인 후 **사실 파일만 바꿔치기**해도 digest가 유효했다.

## 논의 경과

- "수정을 막는다"는 접근은 기각 — Bash까지 완벽 차단은 불가능함을 인정.
- 대신 **"수정되면 반드시 들킨다"**로 목표 전환. 근거: 이 파일들은 Git에서 언제든
  **재계산 가능한 내용**이다. 패키지의 기존 못박기(digest 결속) 원리와 동일.

## 결정

`plan-validate`가 저장된 파일을 믿지 않고 처음부터 다시 확인한다:

1. pin된 SHA를 다시 해석
2. **같은 collector로 Git·등록 사실을 재수집**
3. canonical input-lock·항목별(item) digest·전체 facts digest 재계산
4. 저장본과 대조 — 불일치는 `analysis_error`
5. 모든 `evidence_ref`를 **실제 파일의 실제 값으로 역참조** (pointer 모양만 보지 않음)
6. 두 저장소의 잔여 변경(계획 실행이 남긴 미신고 수정) 스캔
7. run 도중 활성 등록자료가 바뀌었으면 `registration_stale: true` (차단이 아니라 stale 표시 — C20 일관)
8. `plan_digest = proposal digest + input-lock digest + discovered-facts digest` 3-결속

## 고려한 것

- 재계산 비용: 항목이 크면 item digest만 재검증하는 절충 허용.
- Hook(예방)과 재계산(탐지)의 역할 구분 — Hook이 꺼진 CI·수동 셸에서도 재계산은 돌므로
  이것이 **최후 안전망**. 운영 도입 조건에 "Hook을 꺼도 CI의 plan-validate가 같은 위조를 차단"이 들어감.
- canonical 규칙: 판정 필드/관찰 필드 분리는 기존 `verdict.canonical_digest` +
  `acgh-result`의 canonical_payload/observational_metadata 패턴 재사용 (2차 NEW-P2-3에서 명시 권고).
