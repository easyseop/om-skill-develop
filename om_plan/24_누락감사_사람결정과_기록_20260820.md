  - **실행 순서(중요)**: 기준선 잠금(A)은 **apply를 고쳐야** 성립(잠금 칸 신설 + 릴리즈 시 전진)하는데 apply·GitLab 반영은 현재 보류 영역이라 **지금은 못 끝낸다**. 그래서 **지금은 검사기만 고치는 A′**(그 커스텀에 등록된 테스트가 `contracts-to-run`에 반드시 존재 — 없으면 block. 관측·동작판정은 안 함)를 먼저 하고, apply 개방 시 그 위에 A(기준선 잠금 + custom_baseline==릴리즈 잠금 강제)를 얹는다. A′와 A는 겹치지 않아 A′ 먼저 해도 A가 버려지지 않는다.
  - **판정 자체의 한계(불변)**: "동작 바뀜/보존"의 자동 판정은 계획 단계에선 원천적으로 불가(양쪽 입력이 운영자 저작). 실제 판정은 verify(실행)+사람. A′는 판정이 아니라 "테스트 누락 방지"만 한다.

### D-directtest — registered-tests와 direct_tests 비대칭 (A′ 구현 중 발견, 2026-08-20)
- **문제**: A-4 fact `customization-relations[X].tests`는 매니페스트 `assurance.direct_tests`를 포함하나, 기존 flat fact `registered-tests`는 **Contract의 `required_tests`만** 포함한다. 그래서 contract에 없는 direct-only 테스트를 proposal이 `status: existing`으로 표기하면 기존 검사(`collectors.py:600` "test claimed as existing is not registered")가 **거짓 block**한다. A′는 그 테스트를 실행목록에 넣도록 요구하므로 둘이 충돌 가능.
- **현황**: 1.13.1 실데이터엔 `assurance.direct_tests` 항목이 **하나도 없어** 지금은 발현 안 됨(잠재). Claude 데이터 확인 완료(direct-only=NONE). **방향은 false-BLOCK(과잉차단)** 쪽이라 위험(false-pass)은 아님 — 안전 실패.
- **선택지**: (1) `registered-tests`에 direct_tests도 포함(Codex·Claude 권고 — 제안자·검사기 해석 일치). (2) direct-test 전용 status 의미를 문서·검사기에 명시. (3) A-4 관계 fact의 tests를 contract-tests로 축소.
- **선택지 검토 후 권고 변경**: 처음 (1)을 권고했으나, direct_tests는 계약을 우회하는 통로이고 실데이터에서 전부 `[]`(아무도 안 씀)임을 확인. 통로를 하나(계약)로 정리하는 (3)이 더 깔끔.
- **✅ 확정(사람 결정, 2026-08-20): 옵션(3).** A-4가 매니페스트 `assurance.direct_tests`를 관계 fact `tests`에 union하던 것을 **제거** → 관계 `tests` = 그 ID 계약 required_tests만. `registered-tests`(계약 테스트)와 의미 일치해 §7 소멸. 매니페스트 필드는 死필드로 남김(등록자료 미변경). → Codex 지시서 `48_Codex_directtest제거_지시_20260820.md`. 결과 49에서 Claude 재검증.



### Q10 — upgrade 반영 경로 (갭 A4)

- 문제: 정책 §6은 "upgrade도 plan→승인→apply"라 하나, 구현된 apply(`registration_prep.py`)는 `source` 블록(`upstream_sha`/`upstream_tag`/`snapshot_sha`/`changed_path_count`)을 갱신하지 않는다. 등록 폴더는 버전별(`om-temp-1.13.1`)이라, 새 공식 버전의 등록 `source`를 **누가 만드는지** 정해져 있지 않다.
- 선택지:
  - (A) upgrade 반영을 apply가 하되, apply가 새 버전의 `source` 블록을 갱신하도록 확장.
  - (B) 새 공식 버전은 **새 등록 폴더를 bootstrap**으로 생성(기존 커스터마이징을 새 버전 위로 이관). apply는 동일 버전 내 변경만.
  - (C) 혼합: 커스터마이징 이관은 plan/apply, 버전 기준선 갱신은 bootstrap.
- 무엇을 막나: 이 결정 전에는 실제 upgrade 반영을 실행할 경로가 닫혀 있다.
- 권고: 정보 부족. 사람 결정 필요.

- **★ Codex 코드조사(2026-08-21, 질의응답 doc 55) 반영 — 재베이스 단계 선택지 구체화:**
  - **핵심 사실**: `/om-plan upgrade`만으로는 재베이스를 **확정할 수 없다.** 요청서가 잠그는 ref는 `official_base·official_target·custom_baseline`뿐이고 **"재베이스된 최종 candidate ref"가 입력에 없다**(plan-run-request.schema.json:125-133). 새 `snapshot_sha`·전체 diff·`changed_path_count`·등록 밖 잔재는 **실제 재베이스 tree가 생긴 뒤에만** 계산 가능. 최초등록 선례(initial_registration.py:660-675)도 실제 SHA 2개가 있어야 source를 계산함.
  - **재베이스 단계 선택지 (Q10, 사람 결정)**:
    - Q10-A plan-only: 현재 입력구조로 **최종 source 확정 불가** → candidate 입력·post-implement plan 없이는 제외 후보.

    - Q10-C apply에서 처음 계산+기록: 원자적이나 **승인 전 검토자료가 없음**(늦은 발견).
    - **Q10-D 분리형 (Codex 권고)**: pre-plan 제안 → implement가 candidate 생성 → post-implement reconcile이 source 재베이스안 계산·검증 → 사람 승인 → apply가 승인값 한 번만 기록. R-1·P1-1과 정합(`changed_path_count`=새 source inventory 행수, vendor_rebuild.py:99-106 불변식). **단 사람 결정 전 미확정.**
