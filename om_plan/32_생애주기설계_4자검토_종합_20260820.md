## 재설계 원칙 (32 결론 — v2에 반영할 것)

1. **성격 3분법**: 동작 세움 / 동작 보존 / **기반이 동작 변경을 강제**(upgrade deprecation). 2분법 폐기.
2. **자기신고 분기 금지**: change의 보존/변경은 선언이 아니라 **관측(diff ∩ 계약 커버 경로)으로 기계 반증** + 판정 불가 시 LLM 2차판독(Q11 층2와 동형).
3. **연속성은 아티팩트 체인으로**: plan_digest만으론 불가. implement-result(구현 tree SHA + plan_digest 서명) → verify-receipt(실행한 계약·결과 + tree SHA + plan_digest) → apply가 이 체인 전건 검증. 인터페이스 스키마 먼저 정의.
4. **approval 용어 분리**: plan-verdict-approval(계획 검토 준비) ≠ registration-approval(사람 승인 파일). stage 표에 사람 승인 행 명시.
5. **계약·공유파일은 자동반영 금지**: 순환 오라클. 사람작업을 block 조건으로 명시 강제(챙 A의 (A)안). 화이트리스트 확장은 structured merge·검증·롤백 규약 설계 전 금지.
6. **initial 기준선 = mutant 실패**: green 아님. 계약 초안에 알려진 반례 동봉 필수.
7. **upgrade 재베이스는 Q10 결정 후**: 그전까지 설계에 "미결정" 명시. 선점 서술 금지.
8. **N/A 공동화 방어**: 교집합 ∅일 때의 upgrade 최소 실질 증거(예: 문서 findings 비공허 + 2차판독 실효) 별도 정의.
9. **verify 완전성**: shared-impact 전 소유 ID의 contracts-to-run 전건 실행을 계약으로.
10. **feature/change 필수 산출물**: upgrade 9항목과 동형의 모드별 필수 목록 + proposal 스키마 도입(현재 무스키마라 누락 무비용 — C).
