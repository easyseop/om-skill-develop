## 1. 결과 요약

- 첫 `/om-plan`에서 `UserPromptExpansion`이 먼저 발생해도 차단하지 않고 session marker를 발급하도록 고쳤다.
- 바로 뒤의 같은 `UserPromptSubmit`은 Expansion이 발급한 marker를 중복 run으로 오인하지 않는다.
- Expansion 없이 Submit만 발생하는 환경에서는 기존처럼 첫 Submit만 발급하고 두 번째 Submit을 차단한다.
- `command_name`과 `slash_command_name`을 모두 수용한다.
- 오늘 재현 순서와 기존 중복 방지 경로를 반례 테스트로 고정했다.
- 전체 결과는 `293 collected / 283 passed / 10 skipped / 실패 0`이다.
- 커밋·push·MR은 하지 않았다.

## 2. 수정 위치

### 훅 처리

파일: `harness/acgh/plancore/hook_cli.py`

- `30~31행`: 계획 스킬 이름과 Expansion→Submit 1회 인계 상태 키를 상수로 정의했다.
- `73~83행`: `command_name`·`slash_command_name` 중 실제 계획 명령을 찾는다. 빈 값과 무관한 명령은 무시한다.
- `86~106행`: Expansion이 발급한 marker에만 `expansion_submit_pending: true`를 기록하고, 아직 run에 결속되지 않은 상태에서 바로 뒤 Submit이 한 번만 소비하게 했다.
- `131~154행`: 이벤트 순서를 다음처럼 바꿨다.

```text
Expansion + marker 없음 → marker 발급 + 통과
Expansion + marker 있음 → 중복 차단
Submit + Expansion 발급 대기 marker → 대기 상태 1회 소비 + 통과
Submit + 일반/이미 소비된 marker → 중복 차단
```

단순히 “Submit에서 marker가 있으면 통과”로 만들지 않았다. 그렇게 하면 Expansion이 없는 환경의 두 번째 Submit도 통과하기 때문이다. marker가 Expansion에서 발급됐고 아직 run에 결속되지 않은 경우만 한 번 통과시킨다.

### 반례 테스트

파일: `harness/tests/test_plan_workflow.py`

- `1905~1947행`: 오늘 재현 순서인 Expansion → Submit → 두 번째 Expansion을 그대로 시뮬레이션한다.
- `1950~1966행`: Expansion 없는 환경에서 첫 Submit은 통과하고 두 번째 Submit은 차단되는지 확인한다.
- `1969~1985행`: `slash_command_name` 필드로도 marker가 발급되는지 확인한다.
- `1988~2010행`: 빈 명령 필드와 무관한 명령이 marker를 만들지 않는지 확인한다.
- `2013~2043행`: 이미 run에 결속된 marker는 Expansion 대기 상태가 남아 있어도 Submit이 소비하지 못하는지 확인한다.

## 4. 중복 방지 유지 확인

중복 run 방지는 다음 층에 그대로 남아 있다.

1. `UserPromptExpansion`: marker가 이미 있으면 즉시 중복 차단한다.
2. `UserPromptSubmit`: Expansion에서 방금 발급한 미결속 marker만 한 번 통과시키며, 그 밖의 marker는 차단한다.
3. `plan start`: 기존 활성 run 차단 로직을 수정하지 않았다.
4. `PreToolUse`: marker 없는 계획 명령과 허용되지 않은 명령을 막는 기존 정책을 수정하지 않았다.

`harness/acgh/plancore/hook_policy.py`, `.claude/settings.json`, `harness/tests/test_claude_wiring.py`는 이번 핫픽스에서 변경하지 않았다.
