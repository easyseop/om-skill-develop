# om-apply 설계·범위서 (초안 — 적대검토 전)

작성일: 2026-08-21. 작성자: Claude. **성격: 구현 전 설계 초안.** 확정 아님 — 적대검토 + 사람 결정 후 지시서로 전환.

## 0. 전제 (확정된 것)

- **방식 A 확정**: /om-apply는 **LLM이 om-plan 계획대로 실제 코드를 작성·반영**하고, 각 변경에 커스텀 ID를 커밋 트레일러로 남긴다. (개발자가 만든 걸 등록만 하는 B가 아님.)
- **주의점 확인(코드 실측)**: 기존 apply(`registration_prep.py`, 2026-07-30 생성 = om-plan보다 먼저)는 **이미 만들어진 ID-트레일러 커밋을 "등록"하는 B형**이다(`build_plan(patch_ref, custom_ref)`가 존재 커밋을 읽음, `apply --proposal --approval`은 기록만). → **"LLM이 코드를 작성"하는 부분은 없음. 신규.** 단, 기존의 **귀속·등록 밖 변경 차단(UNOWNED_NET_CHANGE)·매니페스트 정합·기록** 기계는 om-apply 뒷단(작성 후 정합·등록)에 **재활용**한다.

## 0.5. ★★★ 절대 불변식 — 관리파일 싱크 (모든 모드·모든 상황 공통)

**om-apply는 어떤 상황에서도(어느 mode든, upgrade 자동 병합이든) 관리 파일(매니페스트·레지스트리 등)이 항상 실제 코드와 일치하도록, 코드와 관리 파일을 함께 갱신하며 개발한다.**

- 개발하다 보면 코드가 원래 계획(초기 매니페스트)에서 **어긋날 수 있다 — 자연스러운 일.**
- 어긋나면 **코드를 되돌리는 게 아니라, 관리 파일을 실제 코드에 맞게 갱신**해 싱크를 회복한다. (관리 파일 = 실제 코드의 살아있는 반영.)
- **절대 금지 = 코드는 바뀌었는데 관리 파일은 옛날 그대로 두는 불일치 방치.** 이게 흐트러지면 등록↔코드 불일치로 **뒤 단계 판정이 전부 거짓**이 되어 다 박살난다.
- 강제(§6): 각 최소 단위 후 **"모든 코드 변경이 관리 파일에 반영됐나"**(등록 밖 변경 0 + 매니페스트가 실제 코드와 일치)를 확인하고, 어긋나 있으면 **관리 파일을 갱신해 맞춘 뒤** 다음 단위로.
- 이 불변식은 §3 해석·§4 분해·§5 실행·§6 게이트 **전부에 우선**한다.

## 1. 위치와 경계 (직전=om-plan / 다음=om-verify) — 요구4

```
om-plan(계획) → 【om-apply: 코드 작성 + ID커밋 + 후보 매니페스트와 정합 확인】 → om-verify(실제 테스트 실행·대조)
```

- **om-apply가 하는 것**: 계획을 실제 코드로 구현, ID-트레일러 커밋 생성, "작성한 코드가 om-plan 후보 관리파일(매니페스트 등)과 일치하는지" **정적 정합 확인**까지.
- **om-apply가 하지 않는 것(=다음 단계 om-verify)**: **실제 테스트 실행·통과 확인**, 계획↔Git 최종 대조, 최종 SHA 결속. → om-apply는 "테스트를 돌리지 않는다". 여기까지만 구현.

## 2. 모드별 입력 (직전 om-plan 산출물) — 요구1·2

om-apply는 **먼저 계획이 어느 mode에서 왔는지 식별**하고, 그에 맞는 파일을 읽는다.

| om-plan mode | om-apply가 읽을 것 | 구현 성격 |
|---|---|---|
| initial | 후보 매니페스트(ID별 changed_paths), decisions, 계약 초안 | 최초 커스텀 코드 전량 작성 |
| feature | 새 ID 매니페스트(changed_paths·목적), 계약 초안 | 새 기능 코드 신규 작성 |
| change | 매니페스트 delta(바뀐 경로만), 재실행 계약·테스트 목록 | 기존 코드 수정 |
| upgrade | 경로 이동표(path-remap), upgrade-plan(이동·대체·충돌), 매니페스트 delta, 공유코드 이동분, operations | 새 공식 버전 위로 이동·재적용 |

공통: proposal 문서(decisions·shared_impact·미해결질문), discovered-facts(대조 근거).

## 3. 파일 해석 규칙 (가장 중요) — 요구3

각 입력을 **개발 행위로 어떻게 번역하는가**. (초안 — 적대검토 핵심 대상)

- **매니페스트 `changed_paths`** → 이 커스텀이 **생성/수정할 파일의 초기 계획 목록**. 개발 중 이 목록 밖 파일을 건드리게 되면(자연히 생김) **금지가 아니라, 그 파일을 이 커스텀 것으로 매니페스트에 추가**해 싱크를 유지한다(§0.5). 절대 안 되는 건 "밖 파일을 건드렸는데 매니페스트에 반영 안 함".
- **매니페스트 `required_changed_paths`** → 반드시 실제로 변경돼야 하는 핵심 파일(load-bearing). 이게 안 바뀌면 미완성.
- **계약(Contract)의 불변식** → 코드가 **지켜야 할 동작 명세**. 구현의 목표. (테스트 작성/통과는 verify지만, 구현은 이 불변식을 만족하도록.)
- **decisions** → "무엇을 왜" 하는지의 의도. 구현 판단 근거.
- **(upgrade) path-remap** → 커스텀 코드를 **어느 위치에서 어느 위치로 옮기는지**의 대응표. 이동 후 그 위치에 재적용.
- **(upgrade) upgrade-plan의 충돌 항목** → 공식 변경과 충돌하는 부분. 여기서 **사람 판단이 필요할 수 있음**(자동 병합 금지 영역).
- **shared_impact** → 공유 파일을 건드리면 다른 커스텀에 영향. 그 지분대로만 수정.

> ★ 이 §3 규칙표가 om-apply의 핵심이자 위험지대. 잘못 해석하면 엉뚱한 파일을 바꾼다. **적대검토에서 "각 규칙이 오해·우회 가능한가"를 집중 검증.**

## 4. 최소 개발 단위 분해 + 선행작업 (참고: ai-harness-template의 seed/decompose) — 요구5

참고 레포(Ouroboros)의 아이디어 차용(그대로 복제 아님):
- 그쪽: 수용기준(AC)을 **레이어별 최소 태스크**(Data→Logic→Presentation)로 분해, 의존·순서 명시.

om-apply 적용안:
- **커스텀(기능) ID 하나 = 하나의 개발 묶음.**
- 각 ID를 **최소 개발 단위**로 쪼갠다. 단위 기준(초안): **매니페스트 `changed_paths`를 레이어/역할별로 그룹핑**(예: 스키마/DB → 서비스/로직 → API/UI). OpenMetadata 구조상 이 레이어 구분이 자연스러움(`openmetadata-spec` → `openmetadata-service` → `openmetadata-ui`).
- 각 단위에 **선행작업 리스트**를 붙인다: 그 단위를 하기 전 충족돼야 하는 것(예: "스키마 정의가 먼저 있어야 서비스 코드 작성 가능"). 의존 순서대로 실행.
- 산출: **개발 계획서**(ID별 → 단위 목록 → 각 단위의 대상 파일·선행작업·완료조건).

## 5. 개발 수행 + 커맨드 분리 여부 — 요구6

- **질문**: "개발 계획 세우기"(설계)와 "계획대로 개발 수행"(실행)을 **별도 커맨드로 분리할지.**
- **당신 제안**: 분리를 염두에 두되 일단 한 번에.
- **권고(동의)**: **v1은 한 커맨드**로 하되, 내부를 **2단계(①분해=계획, ②실행=코드작성)로 명확히 분리**해 나중에 커맨드로 쪼갤 수 있게 경계를 유지. (참고 레포도 decompose/run이 분리돼 있으나, 우리 PoC는 한 커맨드가 실용적.)
- 실행은 §4 계획의 **단위 순서대로**, 각 단위 완료 시 다음 단위로.

## 6. 게이트 배치 (넣을 수 있는 곳만, 과하지 않게) — 요구 전반

| 시점 | 게이트 | 성격 |
|---|---|---|
| 분해 직후 | 계획의 단위들이 매니페스트 `changed_paths`를 **전부 커버**하나 | 검사기(결정론) |
| **각 단위 후 (★불변식)** | 그 단위가 건드린 **모든 파일이 관리 파일에 반영됐나**(등록 밖 변경 0, 매니페스트=실제와 일치). 어긋나면 **차단이 아니라 관리 파일 갱신** | 검사기(기존 UNOWNED_NET_CHANGE 재활용) |
| 전체 개발 후 | 관리 파일이 실제 코드와 **최종 일치** + 등록 밖 변경 0 | 검사기(기존 재활용) |
| 전체 개발 후 | 계약 불변식을 구현이 충족하는지 **의미 판단** | LLM 판단(검사기론 불가) |

> 실제 테스트 실행·통과는 **여기 없음(=om-verify)**. 과한 게이트는 지양 — 위 4개면 충분.
> ★ "각 단위 후" 게이트가 §0.5 불변식의 실행 장치: **코드-관리파일 불일치를 매 단위마다 잡아 관리 파일을 맞춘다.**

## 7. 기존 apply 재활용 지도

- **재활용**: `build_plan`의 커밋→ID 귀속, `UNOWNED_NET_CHANGE`(등록 밖 변경 차단), 매니페스트 delta 생성, `apply_plan` 기록, `_safe_target` 쓰기 화이트리스트.
- **신규 필요**: "LLM이 계획대로 코드를 작성"하는 앞단(§3·§4·§5) — 기존엔 없음.
- **패키징**: 기존 apply는 완전본 트리에만, clean-export엔 없음. om-apply를 어디에 둘지 결정 필요(아래).

## 8. 열린 사람 결정 / 적대검토 대상

**사람 결정**:
- 8-1. upgrade 충돌 → **✅ 자동 병합 확정(사람 결정, 2026-08-21).** 단 자동 병합도 §0.5 관리파일 싱크 불변식을 반드시 지킨다. (병합 결과가 매니페스트와 어긋나면 진행 금지.)
- 8-2. om-apply 패키징 위치(완전본 트리 확장 vs clean-export 편입) — **대기.**
- 8-3. 재베이스(Q10)는 여기서 제외 확정 — 뒤 단계에서. (기결: 제외)

**적대검토 대상(구현 전)**:
- §3 파일 해석 규칙의 오해·우회 가능성(가장 중요).
- §4 최소 단위 기준이 OpenMetadata 실제 구조에 맞나(레이어 그룹핑이 타당한가).
- §6 게이트가 "형식만 통과"로 우회되지 않나.
- A(LLM이 코드 작성)의 근본 위험: LLM이 엉뚱하거나 불완전한 코드를 써도 **om-verify 전까지는 실행 검증이 없다** — §6 정합 게이트로 어디까지 막고, 무엇이 verify로 넘어가는지 정직하게.
