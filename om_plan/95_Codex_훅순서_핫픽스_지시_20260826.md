# Codex 핫픽스 지시 — 훅 이벤트 순서 버그 (첫 /om-plan 차단)

작성일: 2026-08-26. **실기동에서 확정된 결함**: 사용자가 `/om-plan`을 치면 UserPromptExpansion이 UserPromptSubmit보다 **먼저** 발화(공식 문서의 이벤트 순서)하는데, `hook_cli.py`의 Expansion 분기는 marker 부재 시 `block`을 반환한다. marker는 Submit 분기가 만들므로 **첫 슬래시 호출이 항상 자기 훅에 차단**된다. Claude 재현 시뮬레이션: Expansion(marker 無)→block / Submit(원문 가정)→marker 생성 / Expansion(marker 有)→통과.

대상: clean-export 작업트리(main 기준 — 현재 clean). **커밋·push·MR 금지**(Claude가 검증 후 대행).

## 수정 (설계)

`harness/acgh/plancore/hook_cli.py`:

1. **Expansion 분기 = 발급소로 변경**: `command_name`이 om-plan|om-resume일 때 —
   - marker **없으면 `create_session_marker` 후 통과**(None)
   - marker **있으면** 기존 Submit과 같은 사유로 중복 거부(`this session already has an active planning run`)
2. **Submit 분기 보완**: 프롬프트가 `/om-plan`|`/om-resume`으로 시작하고 **marker가 이미 있으면 거부 대신 통과**(None) — 같은 제출에서 Expansion이 방금 발급한 marker를 중복으로 오인하지 않게. (Expansion 이벤트가 없는 환경에서는 기존대로 Submit이 발급·중복거부를 담당 — 그 경로 보존)
3. 중복 run 방지는 계속 다층 유지: Expansion 중복 거부 + `plan start`의 활성 run 거부 + PreToolUse. 완화 없음 확인.
4. 공식 문서상 Expansion 입력 필드가 `slash_command_name`일 가능성(검토결과_om-plan_1차 부수발견) — **`command_name`과 `slash_command_name` 둘 다 수용**하도록 읽기(둘 중 있는 것). 없으면 기존대로 무시.

## 테스트 (필수 반례 — 오늘 재현 시나리오 그대로)

`handle_event` 순서 시뮬레이션 테스트 추가:
- (a) Expansion(marker 無) → **통과 + marker 생성됨** ← 오늘의 결함이 실패로 재현되던 케이스
- (b) 직후 Submit(원문 프롬프트, marker 有) → 통과(거부 아님)
- (c) 활성 marker 상태에서 두 번째 Expansion → 중복 거부
- (d) Expansion 이벤트 없는 환경 가정: Submit(marker 無) → 생성·통과, 두 번째 Submit → 중복 거부(기존 동작 보존)
- (e) `slash_command_name` 필드명으로도 (a) 동작
- 기존 전체 테스트 green(278+). hook_policy·wiring 불변 확인.
