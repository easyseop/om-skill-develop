## 1. 결론 요약

### 질의 ①

현재 `/om-plan upgrade`만으로는 최종 재베이스 값을 확정할 수 없다. 요청서가 잠그는 ref는 `official_base`·`official_target`·`custom_baseline`뿐이며, 재베이스를 마친 새 candidate ref는 입력에 없다(`PLAN/harness/acgh/plancore/schema/plan-run-request.schema.json:125-133`). 따라서 현재 plan에서 확정 가능한 것은 새 공식 기준 commit과 공식 버전 간 변경 경로까지다. 새 `snapshot_sha`, 새 공식 기준→최종 커스텀 코드의 전체 diff, 그 경로 수와 등록 밖 잔재는 실제 재베이스 candidate가 생긴 뒤에만 계산할 수 있다(`PLAN/harness/acgh/integrations/om/collectors.py:434-455`).

Q10의 선택지는 아래 네 가지다. 코드 근거상 가장 안전한 구성은 **계산·검증·기록을 나누는 선택지 D**지만, 이는 권고안일 뿐 사람 결정을 대신하지 않는다.

### 질의 ②

Claude의 잠정 결론은 **핵심은 맞지만 일부 문구는 수정해야 한다.**

- 맞는 부분: `/om-plan`에는 실제 커스텀 전체 diff에서 `실제 변경 경로 - 등록 경로`를 계산해 남은 경로를 block하는 **일반 커버리지 게이트가 없다**.

- 별도 등록 준비 단계에는 `UNOWNED_NET_CHANGE`가 있다(`APPLY/harness/acgh/registration_prep.py:507-519`).

## 2. 질의 ① — 현 코드에서 확인한 재베이스 전제

### 2.1 custom_baseline은 run 안에서는 잠기지만, 등록 source와는 대조하지 않는다

- preflight는 요청서의 **모든 ref**를 commit SHA로 pin한다. 따라서 `custom_baseline`도 run 내부에서는 고정된다(`PLAN/harness/acgh/plancore/preflight.py:146-175`).
- 잠긴 commit SHA와 tree SHA는 input lock에 기록된다(`PLAN/harness/acgh/plancore/preflight.py:206-250`).
- 다만 등록부의 `source.snapshot_sha`는 과거 생성 근거인 fact로만 취급한다. 코드 주석도 이를 active lock이나 block 규칙으로 사용하지 않는다고 명시한다(`PLAN/harness/acgh/integrations/om/collectors.py:228-232`).
- 반례는 등록 `snapshot_sha`와 요청 `custom_baseline`이 서로 달라도 validation이 `approval`임을 확인한다(`PLAN/harness/tests/test_plan_workflow.py:1235-1257`).

따라서 정확한 표현은 다음과 같다.

> `custom_baseline`은 해당 run의 입력으로는 잠긴다. 그러나 그것이 현재 활성 등록부의 `source.snapshot_sha`와 같은 코드인지 확인하는 교차 게이트는 없다.

### 2.2 현재 upgrade plan에는 최종 candidate가 없다

- upgrade 요청은 `official_base`·`official_target`·`custom_baseline`만 필수로 받는다(`PLAN/harness/acgh/plancore/schema/plan-run-request.schema.json:125-133`).
- collector는 `official_base → official_target`의 공식 변경 경로와 파일 object만 계산한다(`PLAN/harness/acgh/integrations/om/collectors.py:434-455`).
- 모든 요청 ref는 잠기므로 공식 기준과 과거 커스텀 기준은 식별 가능하지만, 재베이스 후 최종 커스텀 tree는 입력 자체가 없어 식별할 수 없다(`PLAN/harness/acgh/plancore/preflight.py:151-175`).

### 2.3 현재 registration apply는 source를 재베이스하지 않는다

- `registration_prep.build_plan`은 기존 `source.snapshot_sha`와 `source.upstream_sha` object의 존재만 확인한다(`APPLY/harness/acgh/registration_prep.py:399-409`).
- `registry_after`는 기존 registry의 복사본으로 시작하고, 코드상 추가되는 것은 신규 ID의 `entries`다(`APPLY/harness/acgh/registration_prep.py:530-578`).
- proposal에는 `registry_after`가 registry entry가 바뀐 경우에만 들어간다(`APPLY/harness/acgh/registration_prep.py:800-819`).
- apply가 기록하는 기본 파일은 `commit-inventory.yaml`, `current-diff-paths.txt`, 변경 Manifest이고, `registry_after`가 있을 때만 registry를 기록한다(`APPLY/harness/acgh/registration_prep.py:1054-1069`).
- 현재 diff 경로 수가 달라져도 source의 `changed_path_count`는 유지된다는 반례가 있다(`APPLY/harness/tests/test_registration_prep.py:669-699`).

즉, 현재 apply에는 새 `upstream_tag`·`upstream_sha`·`snapshot_sha`·source inventory·`changed_path_count`를 계산하거나 갱신하는 재베이스 구현이 없다.

### 2.4 실제 tree에서 source를 만드는 기존 선례

최초 등록 코드는 실제 공식 SHA와 커스텀 SHA를 받아 다음을 함께 만든다.

- `snapshot_sha = custom_sha`
- `upstream_sha = official_sha`
- `changed_path_count = len(net_paths)`
- `diff_inventory = source-diff-paths.txt`
- `ancestry_preserved = official_sha가 custom_sha의 조상인지`

근거: `APPLY/harness/acgh/initial_registration.py:660-675`. Registry schema도 이 필드들을 source의 필수값으로 요구한다(`APPLY/harness/acgh/schema/customization-registry.schema.json:10-33`).

이 선례는 재베이스 역시 **새 공식 SHA와 실제 최종 커스텀 SHA가 모두 있어야** 완전한 source를 계산할 수 있음을 보여준다.

### 선택지 D의 최소 흐름

```text
pre-plan
  공식 base/target + 현재 custom 기준을 잠그고 영향·이식 계획 제안
      ↓
implement
  새 공식 target 위에 커스텀 반영 → 실제 candidate commit/tree 생성
      ↓
post-implement reconcile
  target → candidate 실제 diff로 새 source-diff-paths.txt·경로 수·소유/제외 계산
      ↓
verify + 사람 검토
  등록 커버리지·Contract·예외를 확인하고 결과를 candidate에 결속
      ↓
apply
  승인된 candidate/ref·등록상태·digest를 재확인하고 source를 한 번에 기록
```

이 흐름은 구현 확정안이 아니라 Q10 선택지다.

### 기존 결정과 충돌하지 않는 계산 정의

- P1-1의 `changed_path_count`는 `current-diff-paths.txt`의 수가 아니라 **새 공식 target→새 snapshot의 source inventory 행수**로 계산해야 한다. `build_reconstruction_plan`의 불변식은 inventory 행수와 registry source count의 일치다(`APPLY/harness/acgh/vendor_rebuild.py:99-106`).
- R-1을 지키려면 implement/reconcile 결과는 **재베이스 제안물**로만 보관하고, 활성 registry source 전진은 릴리즈 candidate 검증·사람 승인 뒤 apply에서 한 번만 해야 한다.

### 6.1 `/om-plan` plan/check

**판정:** `/om-plan`에 일반적인 “최종 실제 변경 경로 전체가 등록 또는 명시적 제외로 덮였는가” 게이트는 없다. upgrade remap과 dirty worktree 검사는 부분 장치다.

## 7. 우회 가능성까지 포함한 최종 답

1. **현재 `/om-plan`만 실행한 경우**
   - 미커밋 변경과 upgrade의 기존 등록 경로 remap 누락은 잡는다.
   - 최종 candidate 전체 diff의 등록 밖 경로는 잡지 못한다.

2. **`registration_prep.build_plan`까지 실행한 경우**
   - patch→custom의 최종 net 경로가 단일-ID commit에 소유되지 않으면 block한다.
   - 기존 Manifest에 없던 ID 소유 경로는 버리지 않고 Manifest 변경안·사람 검토로 올린다.

3. **`vendor_rebuild plan/verify` 또는 bundle validate까지 실행한 경우**
   - source inventory가 실제 Git diff와 같은지, 모든 경로가 등록 또는 명시적 제외인지, reconstructed candidate가 정확한 경로·ID·내용을 갖는지 확인한다.
   - 단, `unregistered_findings`로 명시적으로 제외한 경로는 허용된다. 이것은 우회라기보다 현재 설계의 승인된 예외 통로다.

4. **`registration_prep.apply_plan`만 놓고 본 경우**
   - 등록 밖 경로를 새로 계산하지 않는다.
   - 승인한 proposal, ref, 등록상태가 그대로인지 확인해 앞 단계 결과의 바꿔치기를 막는다.

따라서 필요한 사람 결정은 “게이트를 새로 만들 것인가” 하나가 아니라 다음 두 가지다.

- Q10: source 재베이스를 A~D 중 어떤 생애주기로 계산·승인·기록할지.
- 배선 결정: 이미 존재하는 `registration_prep`·`vendor_rebuild` 커버리지 검사를 `/om-plan`의 어떤 완료 조건으로 묶을지. 이 문서는 도입 여부를 확정하지 않는다.

## 9. Q10에 올릴 선택지

- **Q10-A:** plan-only. 현재 입력으로는 최종 source 확정 불가이므로 candidate 입력과 post-implementation plan을 추가하지 않는 한 제외 후보.
- **Q10-B:** implement 계산 + implement 기록. 실제 계산은 가능하지만 R-1과 자기검증 위험 때문에 활성 기록을 분리할지 결정 필요.
- **Q10-C:** apply 계산 + 기록. 원자적 기록은 가능하지만 승인 전 검토 자료가 없어지는 문제가 있음.
- **Q10-D:** pre-plan 제안 → implement candidate → post-implement reconcile 계산·검증 → 사람 승인 → apply 기록. 코드 근거상 권고안이지만 **사람 승인 전에는 확정하지 않음**.
