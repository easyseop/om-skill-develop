## 3. 질문별 적대 검토

### 3.1 후보 연속성 — 불성립 (P0)

#### 현재 성립하는 것

- CLEAN의 `plan_digest`는 `proposal_digest`, `input_lock_digest`, `discovered_facts_digest` 세 값의 digest다.
  - 근거: `work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/acgh/plancore/validate.py:430-447`
  - Schema도 이 네 값만 강제한다: `.../plancore/schema/plan-result.schema.json:19-28`
- 이것은 “어떤 입력·사실에서 어떤 proposal 바이트가 검증되었나”를 식별하는 데는 유효하다.

#### 현재 성립하지 않는 것

- CLEAN CLI에는 `plan start/check`, `plan-session-start`, `plan-preflight`, `plan-validate`, `plan-resume`만 있다. `/om-implement`와 `/om-verify`는 없다.
  - 근거: `work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/om_workflow.py:300-372`
- FULL apply의 승인 결속은 별도 `registration_prep.proposal_digest`다. CLEAN의 `plan_digest`를 읽지 않는다.
  - 근거: `work/review-openmetadata-test-om-plan/harness/acgh/registration_prep.py:1000-1021`
- FULL의 `vendor_rebuild.plan_digest`는 재구성 경로·소유권 plan의 digest이며 CLEAN `plan_digest`와 다른 개념이다.
  - 근거: `work/review-openmetadata-test-om-plan/harness/acgh/vendor_rebuild.py:812-823`
- FULL에는 candidate commit·artifact에 검사 결과를 묶는 기존 부품은 있다.
  - test run↔candidate: `.../acgh/testruns.py:178-205`
  - release lock↔candidate·test·result: `.../acgh/release.py:79-114`, `156-226`
  - 그러나 이 부품들에도 CLEAN `plan_digest`는 없다.

#### 구체 반례

1. plan은 `A.java`를 수정하고 `TEST-A`를 실행하라고 제안한다.
2. implement는 proposal을 읽지 않고 `B.java`를 수정한다.
3. verify는 candidate SHA에서 우연히 통과하는 `TEST-B`만 실행한다.
4. 현재 구조에서는 두 결과가 같은 candidate임은 묶을 수 있어도, 그 candidate가 검증된 `plan_digest`를 따랐는지는 못 묶는다.

#### 최소 보강안

구현 전에 다음 연결 규약부터 별도 Schema로 정의해야 한다.

1. `implementation-result`: `plan_digest`, candidate commit/tree, 실제 diff digest, 계획과 다른 변경 목록.
2. `verification-result`: `plan_digest`, implementation result digest, candidate commit/tree, 실행 test 목록·결과·test catalog digest.
3. `apply-request`: 위 두 result digest와 같은 candidate commit/tree, 정확한 관리 파일 delta.
4. apply는 이 세 단계의 digest·candidate가 하나라도 다르면 중단.

### 3.2 apply 화이트리스트 — 현재 불성립, 전용 delta 규약이 있을 때만 조건부 (P0)

#### 현재 코드

- `_safe_target`은 `commit-inventory.yaml`, `current-diff-paths.txt`, `customization-registry.yaml`, `manifests/BANK-OM-*.yaml`만 허용한다.
  - 근거: `work/review-openmetadata-test-om-plan/harness/acgh/registration_prep.py:964-978`
- apply proposal Schema는 manifest 변경과 registry_after만 표현한다. `contracts.yaml`·`shared-path-owners.yaml` delta 필드가 없고 `additionalProperties: false`다.
  - 근거: `.../acgh/schema/registration-proposal.schema.json:5-17`, `44-82`
- `contracts.yaml`과 `shared-path-owners.yaml`은 apply 직전 상태 digest에는 포함되어 변조를 잡지만, apply가 새 내용을 만들거나 검증하지는 않는다.
  - 근거: `.../acgh/registration_prep.py:114-132`

#### 안전 가드와의 관계

- 정확한 상대경로를 화이트리스트에 추가하는 것 자체는 `_safe_target`의 경로 이탈·symlink 가드와 기술적으로 양립할 수 있다.
- 하지만 그것은 **경로만 안전**하게 만들 뿐이다. 계약 의미, 소유자 정합성, 기존 entry 보존, 다른 ID와의 충돌은 보장하지 않는다.

#### 구체 반례

- LLM이 `shared-path-owners.yaml`을 전체 파일 교체로 제안하면서 BANK-OM-002를 실수로 누락한다.
- 새 경로만 화이트리스트에 추가하면 `_safe_target`은 이를 막지 않는다.
- 이후 공유 파일 영향 test가 하나 빠지고, 소유 ID 전체 재검사 요구도 사라진다.

#### 최소 보강안

- 화이트리스트만 넓히지 말고, `before_digest + structured_delta + expected_after_digest`를 가진 전용 제안을 정의한다.
- 전체 교체가 아니라 ID/contract/path 단위 merge를 한다.
- after 전체 Schema·Registry↔Manifest↔Contract 역참조·공유 경로 소유자 전체를 다시 검증한다.
- owner 신원·업무 의미같이 Git으로 정할 수 없는 값은 자동 입력하지 말고 `unresolved`+STOP으로 남긴다.

### 3.5 `change_kind` 분기 — 현재 불성립, 일관성만 부분 강제 가능 (P1)

#### 현재 상태

- run request Schema에 `change_kind`가 없다.
  - 근거: `work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/acgh/plancore/schema/plan-run-request.schema.json:7-18`, `36-71`
- 현재 change 분기는 `change_path=pre_plan|post_change_reconcile`뿐이다.
  - 근거: 같은 Schema `90-123`

#### 결정론적으로 잡을 수 있는 거짓 선언

- `behavior_preserving`이라고 쓰고 Contract 정의·expected·public API schema를 바꾸는 proposal.
- `behavior_preserving`인데 신규 test만 추가하고 기존 필수 test를 제거하는 proposal.
- `behavior_changing`인데 Contract delta와 영향 test가 전혀 없는 proposal.
- 이것들은 선언과 출력의 **형식·구조 모순**이므로 규칙으로 막을 수 있다.

#### 결정론적으로 잡을 수 없는 거짓 선언

- 용도는 같다고 선언하면서 응답 필드의 의미를 바꾸는 코드.
- 항상 참을 반환하는 기존 test를 그대로 두고 실제 동작을 바꾸는 코드.
- 동일한 파일·함수 구조를 유지하면서 업무 의미만 바꾸는 코드.
- `pre_plan`은 candidate가 없으므로 diff 특성으로 진위를 확인할 수도 없다.

즉 `change_kind`는 최종 진실 판정기가 아니라 **요청자의 intent + 규칙 분기 입력**으로만 쓰어야 한다. 실제 동작 보존 여부는 충분한 행동 test와, 필요하면 별도 LLM/사람 판독으로 확인해야 한다.

#### 구체 반례

- 사용자가 `behavior_preserving`이라고 선언한다.
- 코드는 API `status=active`를 `status=enabled`로 바꾸지만 기존 test는 해당 필드를 검증하지 않는다.
- diff 경로·Contract ID·test ID가 같아도 특성이 변했으므로, 현재 구조로는 거짓 선언을 결정론적으로 잡을 수 없다.

**반례:** 누락 경로 10개 모두에 `to: README.md`를 쓰면 원본 커버리지는 충족하지만 이식 계획은 무의미하다.

### P1-4. “upgrade는 test 경로만 수정”은 과도하게 강한 가정이다

- `29:49`, `29:52`는 동작 보존이면 test는 경로만 수정하고 신규 test는 없다고 단정한다.
- 공식 API, UI selector, authentication, fixture 형식, DB migration 절차가 바뀌면 **업무 Contract은 그대로여도 test 구현·fixture·실행 순서**는 바뀌어야 한다.
- 새로 발견한 upgrade 위험은 동작 보존 목적의 신규 회귀 test를 요구할 수도 있다.

**반례:** 생성 API의 응답 코드와 재시도 규칙이 공식 버전에서 변경된다. 커스텀 기능의 결과는 같아야 하지만 기존 test harness는 수정 없이 실행될 수 없다.

**정밀화:** “Contract 의미는 기본적으로 보존”과 “test artifact는 이유를 기록하고 갱신 가능”을 분리해야 한다.

### P1-5. pre-plan에서 implement로 갔다면 post-change reconcile이 필수다

- `change/pre_plan`은 후보 ref가 없고 모든 경로·코드·test가 제안이다: `01A` change 설계.

**반례:** pre-plan은 A, B 경로를 예상했지만 implement에서 C까지 바뀌다. test가 통과하면 verify만으로는 C가 미승인 추가 변경인지 편입에 필요한 신규 경로인지 구분하지 못한다.

  - 근거: `.../harness/acgh/integrations/om/collectors.py:675-707`

**반례:** 주 LLM이 자신의 findings와 자신이 작성한 `independent_document_review`를 한 run에 넣는다. 현 validator는 `review_context=independent_agent`라는 자기신고와 digest 목록을 보지만, 생애주기 배선이 별도 agent 실행을 보장해야 Q11 의도가 살아난다.

### P1-7. apply 후 등록 bundle 재검증·결과 결속이 생애주기에 없다

- 현재 apply는 쓰기 실패 시 원본 바이트로 rollback하는 transaction은 있다.
  - 근거: `work/review-openmetadata-test-om-plan/harness/acgh/registration_prep.py:1076-1133`

**반례:** 화이트리스트를 넓혀 여러 관리 파일을 쓴 뒤, 개별 YAML은 파싱되지만 Registry↔Contract 역참조가 깨진다. 쓰기 자체가 성공했으므로 rollback되지 않는다.

### P1-8. 새 plan의 proposal 파일명이 일관되지 않는다

- `29:25`는 `test-plan`·`contract 정의`를 implement 소스로 지칭한다.

## 8. 최소 설계 보강안 — 구현 지시가 아님

P0를 해소하기 위한 최소 설계 순서만 제시한다. 코드 구현을 시작하지 말아야 한다.

1. **현재 상태 정리:** A5 잘못된 미커밋 조치가 실제로 되돌려졌는지 확인한다.
2. **사람 결정:** Q10(A/B/C)과 curated 파일 자동/사람 경계(Q12)를 확정한다.
3. **정본 상태명:** `review_ready`, `implementation_ready`, `verified`, `apply_ready`, `deployed`를 별도로 정의한다.
4. **연속성 Schema:** plan→implementation→verification→apply의 digest·candidate·diff·test-run 연결을 정의한다.
5. **모드별 출력 Schema:** initial/feature/change/upgrade의 필수 파일·필수 필드·N/A 조건을 확정한다.
6. **코드가 증명할 수 없는 경계:** `change_kind`는 intent로 취급하고, 행동 보존은 test/LLM/사람 판독의 한계를 명시한다.
7. **apply 전용 delta:** 화이트리스트 확장 전에 curated 파일의 structured merge·after validation·rollback 규약을 설계한다.

## 9. 최종 판정

`29`는 개념 방향은 맞다. 계획 후보가 구현·검증·반영에서 재유도되지 않게 하고, 하나의 정확한 candidate에 결과를 묶어야 한다는 문제 설정은 올바르다.

그러나 현재 초안은 아직 **생애주기 설명**이지 **실행 계약**이 아니다. 가장 중요한 연결부인 implement result, verification result, apply input이 정의되지 않았고, 코드도 이를 소비하지 않는다. 더군다 upgrade apply는 Q10 미결정을 초안이 임의로 해소한 모양이다.

따라서 현재 판정은 다음과 같다.

> **설계 불성립. P0-1~P0-6과 Q10·Q12를 먼저 해소하고, 연속성 Schema와 반례를 승인받은 뒤에만 구현 착수가 가능하다.**
