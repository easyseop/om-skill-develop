# change 모드 분리 — "계획 먼저" 원칙과의 자기모순 해소

## 문제 (1차 검토 P0-3)

전체 규칙: **계획(plan) → 사람 검토 → 구현(implement)**. 그런데 초안의 change 모드는
필수 입력으로 **"변경 후보 ref"(=이미 변경된 커밋)**를 요구했다.

- 앞으로 할 수정을 계획하려면 → 후보 ref가 없어 시작 불가
- 후보 ref가 있다면 → 이미 plan 없이 구현했다는 뜻 (경계가 깨진 상태의 사후 승인)

즉 한 모드가 서로 다른 두 업무(사전 계획 / 사후 등록 정합)를 하나의 입력 규격에 뭉뚱그렸다.

## 논의 경과

- 기존 하네스의 `registration_prep.build_plan`이 하는 일이 정확히 "사후 정합"이었음을 확인 —
  초안의 change는 사실상 이것의 재포장이었고, "사전 계획" 경로가 통째로 빠져 있었다.
- 선택지: (a) change를 사후 전용으로 낮추고 사전 계획은 feature에 우겨넣기 → 기존 ID 수정과
  신규 기능은 입력·검증이 달라 부적합. (b) 모드를 쪼개 두 경로로.

## 결정

`/om-plan change --change-path <pre-plan|post-change-reconcile>` — 한 모드, 두 명시 경로.
자동 추측 선택 없음(`change_path` 누락·모호 시 STOP).

| 경로 | 시점 | 입력 | 사실/제안 경계 |
|---|---|---|---|
| `pre_plan` | 코드 수정 전 | 기존 ID + 승인 기준 ref + 요구사항 (**후보 ref 받지 않음**) | 경로·코드·테스트 변경 전부 `proposed` |
| `post_change_reconcile` | 변경 후보 존재 | 기존 ID + 변경 전 ref + 후보 ref + 이유 | Git diff는 `observed`, 등록자료 변경은 `proposed` |

공통: 공용 경로가 영향받으면 소유 ID 전원 확인 + 그 ID들의 테스트를 재실행 목록에 포함.
STOP에 "pre_plan이 후보의 실제 변경을 관측했다고 주장" / "post 경로에 후보 ref 없음" 각각 명시.

## 고려한 것

- 두 경로의 출력 파일명은 공통 6종 — 혼입이 아니라 공유. 경로 구분은 run-request 기록과
  상태 라벨(observed/proposed)로 유지된다고 판단.
- **1차 구현에 두 경로를 다 넣을지는 사람 결정으로 분리** (Q1, 권고 C=둘 다).
  설계가 임의 확정하지 않게 했다.
