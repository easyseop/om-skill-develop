## 1. 결과 요약

새 공유 경로를 사람이 확인했다는 내용을 `execution-report.yaml`에 기록하고, 같은 apply run에서 `apply check --final-ref <동일 SHA>`를 다시 실행할 수 있게 했다.

- 승인 없음: 기존처럼 `awaiting_shared_path_review`, verify 인계 불가
- 경로와 ID 조합이 정확히 일치하는 승인: 질문 해소, `static_consistent_awaiting_verify`, `eligible: true`
- ID 조합 불일치: 명시적 차단 사유를 남기고 수용 거부
- 실제 새 공유 경로가 아닌 잉여 승인: 무시하지 않고 결과의 `warnings`에 기록
- 승인 내용과 경고는 `apply-result.json` 및 `result_digest`에 포함

승인 입력 예시는 다음과 같다.

```yaml
shared_path_acknowledgments:
  - path: src/shared.txt
    customization_ids:
      - BANK-OM-001
      - BANK-OM-002
    approved_by: shared-path-owner
    rationale: 두 기능 담당자가 새 공유 경로의 공동 사용을 확인함
```

`customization_ids`의 나열 순서는 달라도 되지만, 실측된 ID 집합과 정확히 같아야 한다.

## 2. 스키마 변경

### `harness/acgh/applycore/schema/apply-execution-report.schema.json:39`

`shared_path_acknowledgments` 배열을 추가했다. 각 항목은 다음 네 필드를 모두 요구한다.

- `path`: 비어 있지 않은 경로
- `customization_ids`: 중복 없는 ID 2개 이상
- `approved_by`: 비어 있지 않은 승인자 기록
- `rationale`: 비어 있지 않은 승인 근거

필드는 기존 완료 run의 하위 호환과 사후 승인 입력을 위해 스키마상 선택 항목으로 두었다. 새 run을 만들 때는 항상 빈 배열로 생성한다.

### `harness/acgh/applycore/schema/apply-result.schema.json:15`

검사 결과에 다음 항목을 추가했다.

- `warnings`: 잉여 승인 등 비차단 경고
- `shared_path_acknowledgments`: 검사에 사용한 승인 입력

## 3. 코드 변경

### `harness/acgh/applycore/workflow.py:32,501,694,976,1120`

- adapter 호출 계약을 `차단 사유 / 미해결 질문 / 경고` 세 묶음으로 확장했다.
- apply run 시작 시 `shared_path_acknowledgments: []`를 생성한다.
- check 시 execution report의 승인 배열을 관리자료 검사기에 전달한다.
- 승인 입력과 경고를 canonical result에 넣어 `result_digest`로 함께 고정한다.
- 기존 결과가 `awaiting_shared_path_review`인 동안은 같은 run과 같은 SHA로 재검사할 수 있다.
- `static_consistent_awaiting_verify`에 도달한 결과는 기존 규칙대로 읽기 전용이다.

### `harness/acgh/integrations/om/apply.py:56,165`

- baseline에 없고 최종 ID 관계상 소유자가 2개 이상인 경로만 `새 공유 경로`로 계산한다.
- 승인 경로와 실측 경로를 대조한다.
- 승인 ID는 정렬 후 실측 소유 ID와 정확히 비교한다.
- 중복 승인 경로와 ID 불일치는 차단 사유가 된다.
- 새 공유가 아닌 경로의 승인은 경고가 된다.
- 기존 공유 소유자 맵 불일치와 참여 ID 불일치 차단은 그대로 유지했다.

## 4. 반례와 재검사 실증

변경 위치: `harness/tests/test_om_apply_counterexamples.py:723-840`

| 반례 | 기대 결과 | 실측 결과 |
|---|---|---|
| 승인 없음 | awaiting 유지 | `approval`, `awaiting_shared_path_review`, `eligible: false` |
| ID 조합 불일치 | 수용 거부 | `block`, owner mismatch 사유 기록 |
| 정확한 승인 | verify 인계 가능 | `pass`, `static_consistent_awaiting_verify`, `eligible: true` |
| 잉여 승인 | 통과하되 경고 | `pass`, `eligible: true`, `warnings`에 경로 기록 |
| 기존 shared owner map 누락 | 계속 차단 | 기존 OA-10 차단 유지 |

### 같은 run 재검사

다음 순서를 한 테스트 안에서 실증했다.

1. 승인 없이 check → `awaiting_shared_path_review`
2. 동일 run의 `execution-report.yaml`에 정확한 승인 추가
3. 동일 candidate SHA로 check 재실행
4. `static_consistent_awaiting_verify`, `eligible: true` 도달
5. candidate SHA가 바뀌지 않았고 승인 내용이 결과에 남았음을 확인
6. 승인 내용을 포함해 재계산한 `result_digest`가 저장값과 같음을 확인

따라서 전체 apply를 다시 실행하지 않고 이번 run을 구제할 수 있다.

## 7. 남은 위험과 검토 포인트

1. `approved_by`는 현재 구조화된 사람 기록이지 전자서명이나 인증된 사용자 신원은 아니다. 운영 도입 시 승인 파일의 작성 권한과 리뷰 절차로 통제해야 한다.
2. 잉여 승인은 지시대로 비차단 경고다. 경고는 결과와 digest에 남지만, 조직 정책상 잉여 승인도 차단할지는 별도 결정이 필요하다.
3. 엔진 반례에서는 같은-run 구제를 실증했지만, 실제 업그레이드 run의 새 공유 경로 4건을 넣은 실기동 재검사는 Claude 최종 검증 단계에서 확인할 수 있다.
4. 이번 작업은 승인 창구에만 한정했다. 기존 차단 로직, 제품 코드, 활성 등록자료, SKILL/references는 수정하지 않았다.
