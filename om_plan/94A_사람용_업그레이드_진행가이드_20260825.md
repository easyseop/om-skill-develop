## 1단계. 계획 — /om-plan

세션에 입력:

**정상이면**: Claude가 검사기 명령을 돌리고 계획서를 쓴 뒤, 마지막에 "**종료코드 2 = 사람 검토 준비 완료(review_ready)**"라고 보고함.
> 즉, 이 파이프라인에서 계획 성공은 0이 아니라 2입니다. Claude가 2를 "성공"이라고 정확히 말하는지가 관전 포인트 1.

**이상 신호**: "Unknown command"(스킬 인식 실패), 훅 거부 메시지에 막혀 진행 불가, 판정을 Claude가 말로 뒤집으려 함 → **멈추고 그 화면을 그대로 저에게(이 세션에) 가져오기.**

## 2단계. 반영 — /om-apply

```
/om-apply 승인된 방금 계획으로 반영 run을 시작해줘
```

**정상이면**: 1.13.2 코드를 가져와 우리 커스텀과 병합하는 작업이 단위별로 진행되고, 마지막에 "**static_consistent_awaiting_verify**(정적 정합, 검증 대기)"로 끝남.
> 즉, "코드는 합쳐졌고 장부와도 맞는데, 실제로 돌아가는지는 아직 검증 전"이라는 상태가 이 단계의 유일한 성공입니다.

**멈추는 게 정상인 경우**: 병합 충돌로 STOP, 계획 밖 경로 발견(scope_variances) → Claude가 사유를 정리해 승인을 요청하면 **내용 보고 승인/거부 결정**. Claude가 임의로 뚫고 가면 이상 신호.
> 소요: 병합 규모에 따라 수십 분+.

## 3단계. 검증 — /om-verify

```
/om-verify 방금 인계로 검증 run을 준비해줘. 선행물(빌드 영수증·fresh 서버)부터.
```

**알아둘 것**: 여기가 제일 오래 걸립니다 — 후보 이미지 빌드 수십 분 + 전용 서버 기동 + 계약 테스트. **상주 lab(8585)은 건드리지 않고 별도 포트에 새로 띄우는 게 정상**입니다.

**정상이면**: `verified`(0)이면서 — 테스트에 **browser 종류가 포함되어 실제 브라우저로 화면 동작까지 실행**된 집계가 receipt에 남음. 마지막 보고에 "digest는 무결성 증명이지 발행자 진위 증명은 아니다"라는 신뢰 한계 문구가 그대로 나오는지도 관전 포인트.

**failed/infra_error가 나오면**: 그게 업그레이드 호환성 문제를 잡은 것일 수 있음(=파이프라인의 존재 이유). 이유 코드 그대로 보고받고 멈춤 — 저에게 가져오기.
