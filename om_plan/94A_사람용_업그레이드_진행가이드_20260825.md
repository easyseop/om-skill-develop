## 그림 먼저: 무엇이 어디서 벌어지나

| 저장소(깃랩) | 역할 | 작업 브랜치 | 여기서 바뀌는 것 |
|---|---|---|---|
| **kb-datacatalog** (제품) | 수술 대상 | `upgrade/1.13.2-run-20260825` | **코드** (1.13.2 병합 + 커스텀 7기능) |
| **kb-datacatalog-upgrade-checker** (검사기) | 감독관+장부 | `upgrade/1.13.2-registration-20260825` | **장부**(등록자료) 갱신 — 2단계에서만 |

- 두 저장소의 **main은 승인 전까지 절대 불변**. 모든 작업은 위 브랜치에서.
- Claude 세션은 **검사기 폴더에서** 연다(스킬이 거기 설치되어 있음). 제품 폴더에서 열면 /om-plan이 안 잡힌다.
- 슬래시는 필수: `/om-plan …` 형식(뒤는 자연어 자유). 슬래시 없이 "업그레이드 해줘"는 설명서 미장착+통행증 미발급이라 동작하지 않는다.
- initial(최초 등록)은 이미 완료 — 장부가 검사기 저장소에 포함되어 clone에 들어 있다. 선행 작업 없음.

## 시작점 — 매 run의 첫 동작은 "요청서 만들기"다

(이번 run은 원큐 스크립트가 요청서까지 배치해 줬지만, **다음 run부터의 표준 시작은 이것이다**)

세션에 붙여넣기:
```
<하려는 일> 요청서를 만들어줘. 템플릿·장부·git 실측으로 채울 수 있는 값은 채우고,
사람이 정할 값(목적지 버전 또는 대상 ID / 공식 문서 / owner)만 나에게 물어봐.
완성되면 저장소 밖 run-requests/ 에 두고 스키마 검증 통과를 확인한 뒤 경로를 보고해줘.
```

- 사람 결정값은 보통 3개뿐: **무엇을**(upgrade 목적지 버전 / change 대상 ID / feature 새 ID 채번), **공식 문서**, **owner**.
- 요청서는 "사람 승인 입력물" — 자동으로 채워져도 **최종 훑어보고 GO는 사람**이다.
- 기존 요청서(run-requests/)가 템플릿 — 버전업이면 버전·태그·문서 세 값만 바뀐다.

## 3단계. 검증 — /om-verify

### [먼저] 툴체인 게이트: JDK 21·Maven·yarn·Python3.11 venv 설치됐는지 확인 (미설치면 여기서 설치 — 관리자 권한)

### [입력]
```
/om-verify 방금 인계로 검증 run을 준비해줘. 선행물(빌드 영수증·fixture·fresh 서버)부터 순서대로.
```
(가장 오래 걸림: 이미지 빌드 수십 분 + 전용 서버 기동 + 계약 테스트. **기존 운영 서버는 건드리지 않고 별도 포트에 새로 띄우는 게 정상**)

### [끝나면 확인]
- [ ] 최종 상태 셋 중 하나 그대로: **verified(0) / failed(1) / infra_error(3)** — "거의 통과" 같은 표현이 나오면 이상 신호
- [ ] verified면: 테스트 집계에 **browser 종류 포함**(실브라우저 화면 검증이 실행됐다는 뜻), skip 0
- [ ] 보고 끝에 신뢰 한계 문구("digest는 무결성 증명이지 발행자 진위 증명 아님")가 그대로 전달됨
- [ ] failed/infra_error면: **그게 업그레이드 문제를 잡은 성과일 수 있음** — reason code 그대로 받아 검증자 세션으로
- [ ] 종료 후: `검증용 fresh 서버·볼륨 정리했는지 확인해줘`
