# om-apply 구현 지시서 (v1)

작성일: 2026-08-21. 작성자: Claude. 구현: Codex.
정본: 이 문서가 om-apply v1 구현의 정본이다. 설계 초안 `58`과 Codex 적대검토 `60`, 사람 결정(공유정리/하위_om-apply)을 통합·반영했다. **58과 충돌 시 이 문서를 따른다.**

> ★ **아직 구현 착수 신호 아님** — 사용자 지시로 "구현 직전까지"만 준비. 실제 코딩은 별도 착수 지시 후.

## ★★ 반드시 지킬 것 — 검증·누락 금지 (지난 반복 실수 방지)

1. **코드로 확인 전 단정 금지.** 예전 apply·현재 스키마·게이트 동작을 "있다/한다"로 가정하지 말고 **파일·줄로 실측**한 뒤 쓴다.
2. **예전 apply 재사용 전 현재 정책 부합 실측**(아래 §6). direct_tests·per-ID 관계·계약/공유 파일 쓰기 등 **현재 정책과 어긋나는지 확인**하고, 어긋나면 그 부분은 신규.
3. **Codex 검토(60)의 P0·P1·반례(§8) 하나도 빠뜨리지 말 것.** 아래 §5 체크리스트와 60을 대조.
4. **"테스트 N개 green"으로 완료 주장 금지.** 반례가 실제로 판정을 뒤집는지 확인.
5. **v1 범위만.** 미확정(안전유형 자동통과)·향후(독립검토 sub-agent)는 **구현하지 마라**.
6. commit·push·MR은 별도 지시 전까지 금지.

## 1. 목적·범위·경계

- **목적**: om-plan이 낸 "계획"대로 **LLM이 실제 코드를 작성·반영**하고, 관리 파일을 실제 코드와 일치시킨다. (방식 A.)
- **직전** om-plan / **다음** om-verify.
- **경계(중요)**: om-apply는 **테스트를 실행하지 않는다.** "계획대로 구현 + 코드·관리파일 정합 + 빠른 정적 검사"까지. 최종 상태 = **`static_consistent_awaiting_verify`**. 배포·최종 승인으로 승격 금지(om-verify가 실제 테스트 통과·동일 candidate SHA 결속 후).
- **패키징**: clean-export(`kb-datacatalog-upgrade-checker`)에 편입. 필요한 안전 primitive만 이식.

## 2. 확정된 사람 결정 (구현 고정)

- **방식 A**: LLM이 코드 작성.
- **관리파일 3방향 대조**(가장 중요): 코드=매니페스트 2개만 보면 같은 LLM이 둘 다 틀려도 통과(자기세탁). 반드시 **①승인된 계획 ②실제 Git diff ③최종 관리파일**을 독립 대조.
- **계획 범위 우선**: 스킬 md에 "최대한 계획(후보 매니페스트) 범위 내 개발, 범위 밖은 예외·최소화" 명시.
- **범위 이탈 처리**(v1): 민감 경로 → **STOP**. 그 외 → LLM이 **구조화 사유**(①어떤 기능 ②기존엔 왜 안 건드려도 됐나 ③이번엔 왜 필요 ④근거 위치) 작성 → **사람 승인**. (독립검토 sub-agent는 v1 제외·향후 우선순위0.)
- **자동 매니페스트 확장 금지**: 계획 밖 변경을 조용히 매니페스트에 추가해 통과시키지 말 것. `scope_variance`로 기록 + STOP + 승인/재계획 후에만 반영.
- **병합 실패(upgrade) 3단 복구**: ①LLM이 사라진 동작 재적용 → ②안 되면 롤백+재계획 → ③그래도 안 되면 사람.
- **끝낼 때 빠른 실행 검사 포함**: 컴파일·코드 생성기 같은 싸고 빠른 것까지. 테스트 전체 실행은 verify.
- **계약(업무규칙) 충족은 pass로 처리 금지**: LLM 판단은 `claim`/`review_note`로만. 실제 충족은 verify.
- **예전 apply 부분 재활용만**: 안전 primitive(Git 고정·safe write·rollback·digest 대조)만, 본체 신규.

## 3. Codex 검토(60) 반영 항목 (설계 고칠 것)

1. **3방향 대조**로 §0.5 개정(위 §2). "코드=매니페스트"만 보지 말 것.
2. **범위 이탈 = scope_variance + STOP**, 자동 매니페스트 확장 금지(P0-1).
3. **touch-후-revert 방어**: required 파일을 한 커밋에서 건드리고 뒤에서 원복하는 우회 차단 — 최종 tree에 요구 내용·심볼이 남는지 검사(P0-1 강한 반례).
4. **path-remap 스키마 강제**(P0-2): `action(keep|move|replace|delete|generate)` + action별 `from`/`to` 필수조건 + literal 경로만(`..`·절대·symlink 차단) + from/to 실재 대조 + 영향경로마다 정확히 1 disposition + 다대일/일대다 명시.
5. **`changed_paths`(최종 구현 범위)와 `planned_actions`(계획) 분리**(P1-1). required 의미 세분화: `required_final_paths/assertions` vs `required_transaction_actions`(P1-2).
6. **삭제·이동**: 예전 `_check_path_modes`(최종 HEAD에 경로 존재 강제)는 move/delete와 충돌 → action 모델로, 이전 위치 부재가 정상인 경우 명시(P1-3).
7. **공유 신규**: 새로 두 ID가 함께 쓰게 된 경로를 최종 per-ID 관계에서 계산, 기존 shared map과 포함·차이 보고, 신규 공유는 사람 검토. 계약·공유정의도 A형 산출물 1급(P1-4).
8. **자동병합 2단계**: 기계병합 성공 ≠ 의미보존. 병합 후 계획·공유·정적 assertion·테스트목록 대조(P1-5).
9. **최소 단위 = role/action/dependency DAG**(P1-6): 폴더 레이어 추정만으로 정하지 말 것. role 예: migration·schema-source·generation·generated-output·backend·api·ui·i18n·shared-integration·operation. 근거는 repository-layout·생성기 설정·공식 문서·관계 fact.
10. **게이트 정직화**(P0-3): 계약 충족 LLM판단을 pass에서 제거→claim. 최종 상태 `awaiting_verify`. mode별 typed 입력 스키마 강제(P1-7). `id-contract-consistency=false`면 시작 전 fail-closed. 검사기·제품·관리파일 저장소 최종 결속(P1-8): plan_digest·기준commit/등록digest·단위 시작/종료/최종 candidate SHA·관리파일 digest·verify로 넘길 candidate SHA+테스트목록.

## 4. 최소 단위·실행 흐름 (v1: 한 커맨드, 내부 2단계)

- 내부 ①**분해**(계획→role/action/dependency DAG 단위) ②**실행**(단위 순서대로 코드 작성). 나중에 커맨드 분리 가능하게 경계 유지.
- 각 단위 후 **관리파일 정합 게이트**(§5). 어긋나면 관리파일 갱신 or scope_variance STOP.

## 5. 게이트 (넣을 수 있는 것만)

| 시점 | 게이트 | 성격 |
|---|---|---|
| 시작 전 | `id-contract-consistency=true`, 입력 typed schema 통과 | 검사기 fail-closed |
| 분해 후 | 단위들이 계획 경로 전부 커버 | 검사기 |
| 각 단위 후 | 그 단위 변경이 **3방향 정합**(계획·실제diff·관리파일), 등록밖 변경 0, touch-후-revert 아님 | 검사기(UNOWNED 재활용+신규) |
| 전체 후 | 최종 관리파일=실제 코드, path-remap 목적지 실재, 공유 신규 보고, 빠른 실행검사(컴파일·생성기) 통과 | 검사기 |
| 전체 후 | 계약 충족 | **claim만**(verify가 판정) |

## 6. 예전 apply 재활용 (실측 후 결정)

- **재활용 후보(안전 primitive)**: Git ref→SHA 고정·재확인, 커밋 트레일러 검사, per-commit/net diff 계산, 경로 방어(symlink/submodule/lfs), digest 대조, `_safe_target`·apply lock·atomic write·rollback.
- **신규 필요**: A형 orchestration(단위 DAG 실행), 단위 시작/종료 SHA·scope_variance, action 모델, 병합 시도/수용 분리, verify 인계 binding.
- **현재 정책 부합 실측(누락 금지)**: 예전 apply의 direct_tests 사용·per-ID 관계 미인지·쓰기 화이트리스트(계약·공유 파일 없음)가 **현재 정책과 어긋남** → 그 부분 재활용 금지, 신규. (근거: doc 60 §6.2.)

## 7. 반례 (구현 시 포함 — doc 60 §8의 OA-01~20)

핵심: OA-01(계획밖 파일+매니페스트 동시추가→scope variance STOP), OA-02(touch후 revert→block), OA-05(path-remap `to` 없음→block), OA-07(target 실재 안함→block), OA-08(합법 move인데 source 없음→정상), OA-09(신규 공유→STOP), OA-13(빈 문서→schema block), OA-14(consistency=false→block), OA-15(정합 맞지만 필수테스트 미실행→awaiting_verify), OA-17(direct_tests 재유입→회귀실패), OA-19(clean merge인데 assertion 사라짐→block). 전 20개는 60 참조.

## 8. 사람 결정 (확정/미결)

- **신규 공유 경로 처리 — ✅ 확정(v1): 승인자 미지정, "STOP + 사람 검토 질문".** 새로 공유된 경로 감지 → **STOP → 결과에 unresolved-question 기록**("이 파일이 X·Y 공유가 됨 — 이대로 둬도 되나? 소유 지분?") → 실제 운영자가 보고 판단. (정식 승인 주체 — 관련 담당자 전원 vs 통합 담당자 한 명 — 은 **승인 체계 생길 때 재검토**, v1 미정.)
- (검토 중) 안전 유형 자동통과 도입 — v1 미포함.
