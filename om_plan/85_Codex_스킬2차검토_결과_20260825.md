## 검토 1 — 적대 검토

### P0-1. `feature`에서 새 ID를 고정하지 않아 기존 ID 재사용 제안이 `approval`로 통과한다

#### 문제

`om-plan`은 `feature`의 대표 실패 게이트로 “새 ID가 이미 등록돼 있으면 block”을 설명한다.

- 스킬: `/Users/seop/claude-skill-by-seop/.claude/skills/om-plan/SKILL.md:105-109`

그러나 현재 `feature` 입력 스키마는 `requirement`와 `refs.custom_baseline`만 필수로 하고 `customization_id`는 필수로 하지 않는다.

- 스키마: `work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/acgh/plancore/schema/plan-run-request.schema.json:82-87`

중복 ID 검사도 요청에 적힌 `request.customization_id`만 등록 ID와 비교한다. 요청에서 이 필드를 생략하면 `None`과 등록 ID를 비교하므로 중복 검사가 작동하지 않는다.

- 검사: `work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/acgh/integrations/om/collectors.py:546-553`
- 최종 판정: 다른 문제가 없으면 `approval`: `work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/acgh/plancore/validate.py:524-531`

#### 실측 반례

임시 Git 저장소와 활성 등록부를 만들고 다음 조건으로 실제 `run_preflight`와 `run_validation`을 실행했다.

- 활성 ID: `BANK-OM-001`, `BANK-OM-002`
- `mode: feature`
- 요청의 `customization_id`: 생략
- 제안의 `affected_customization_ids`: 기존 ID `BANK-OM-001`

실제 결과:

```yaml
request_customization_id: null
proposal_affected_id: BANK-OM-001
already_registered_ids:
  - BANK-OM-001
  - BANK-OM-002
verdict: approval
review_state: review_ready
```

따라서 스킬 문면대로 필수 입력 표를 따라도 “신규 기능”이 기존 ID를 재사용한 제안을 review-ready로 만들 수 있다. 이는 단순 설명 누락이 아니라 거짓 성공 경로다.

#### 수정 선택지

권고는 **검사기에서 막는 것**이다.

1. 권고: `feature` 스키마에 `customization_id`를 필수로 추가하고 현재 중복 검사에 연결한다.
2. 새 ID를 LLM이 제안하게 유지해야 한다면, 제안서에서 신규 ID를 구조화해 추출하고 등록 ID와 중복되지 않는지 결정적으로 검사한다.

스킬 문구만 고쳐서는 우회를 막을 수 없다. 엔진·스키마 수정 후 반례가 `block` 또는 `analysis_error`로 바뀌는지 확인해야 한다.

### P0-2. 스킬에 적힌 Python 실행 명령이 현재 이식 대상 환경에서 실행되지 않는다

#### 문제

두 스킬은 다음 인터프리터를 고정한다.

- `om-plan`: `python3 harness/om_workflow.py ...` — `/Users/seop/claude-skill-by-seop/.claude/skills/om-plan/SKILL.md:16-17,142,176,190`
- `om-verify`: `python harness/om_workflow.py ...` — `/Users/seop/claude-skill-by-seop/.claude/skills/om-verify/SKILL.md:15,128-131`

현재 clean-export 작업 환경의 실측값은 다음과 같다.

```text
python: command not found
python3: /usr/bin/python3
python3 --version: Python 3.9.6
```

CLI는 Python 3.11 미만을 시작 즉시 종료코드 2로 거부한다.

- `work/kb-datacatalog-upgrade-checker-om-plan-cli/harness/om_workflow.py:14-20`

그러므로 현재 상태에서는:

- `/om-verify`의 명령은 셸 종료코드 127로 실패해 문서의 0/1/2/3 지도 밖으로 벗어난다.

`om-verify`가 “Python 3.11 미만은 exit 2”를 설명한 것은 맞지만, 실제 명령의 `python` 자체가 없을 때의 127은 설명하지 않는다. 이식 직후 정상 호출이 불가능하므로 설치 준비 차단으로 판단한다.

1. 권고: 저장소가 관리하는 Python 3.11+ 실행 래퍼를 하나 정하고 두 스킬이 동일 래퍼를 호출하게 한다.
2. 또는 이식 전 필수 설치 절차로 저장소 내부 `.venv`를 만들고, 스킬 명령을 그 명시 경로로 고정한다.
3. PATH의 `python`·`python3`에 의존하는 방식은 다른 컴퓨터에서 재현성이 낮아 권하지 않는다.
