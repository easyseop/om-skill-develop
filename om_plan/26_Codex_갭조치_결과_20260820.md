## 1. 조치별 결과

### 조치 1 — dangling 명령 정합

선택: clean export를 plan 전용으로 트림했다.

- `harness/om_workflow.py`의 공개 CLI를 `plan start`, `plan check`, `plan-session-start`, `plan-preflight`, `plan-validate`, `plan-resume`로 한정했다.
- 제거한 명령의 parser뿐 아니라 실행 불가능 worker를 참조하던 dead dispatch 코드도 제거했다.
- `plan`만 입력하면 하위 명령 누락으로 exit 2가 난다.
- 제거된 `watch`를 실제 호출하면 FileNotFoundError가 아니라 argparse의 `명령 없음`과 exit 2가 난다.
- Python 3.11 미만은 import 전에 명확히 중단한다.

반영: `harness/om_workflow.py`, `harness/tests/test_plan_cli.py`.

### 조치 2 — sensitive-zone/watch 배포 정합

선택: watch/risk는 완전본 게이트 환경에서만 실행한다.

- clean export의 데드 `harness/registrations/om-temp-1.13.1/sensitive-zones.yaml`을 제거했다.
- `README.md`에 clean export가 plan 전용이며 watch/risk worker는 완전본에서 실행됨을 명시했다.

주의: 이번 작업은 완전본 watch/risk를 실행하거나 변경하지 않았다.

### 조치 3 — upgrade 산출물 3층 검증

결정론 검사는 `harness/acgh/integrations/om/collectors.py`에 반영했다.

1. Manifest의 `implementation.changed_paths`를 등록 커스터마이징 경로 사실로 수집한다.
2. `official-upgrade-paths ∩ registered-customization-paths`의 모든 경로를 proposal `path-remap`이 커버해야 한다. 누락하면 block.
3. 모든 `official-doc-findings.id`가 `doc-code-crosscheck`에서 참조돼야 한다. 누락하면 block.
4. upgrade 출력 9종이 비어 있지 않아야 한다. 해당 없음은 `not_applicable: true`와 비어 있지 않은 `reason`이 있어야 한다.
5. 하이픈·언더스코어 표기와 decision 내부 `required_tests`를 동일 의미로 인식한다.

독립 LLM 판독 자체는 결정론 validator에 넣지 않았다. 별도 agent 배선은 25 결과서에 기록했다. validator는 그 agent가 남긴 결과에 대해 다음만 결정론적으로 확인한다.

- 별도 컨텍스트 표기
- 공식 snapshot digest 전체 일치
- `missing_requirements` 목록 존재
- 누락 요구사항이 있으면 block

이는 LLM 판단의 정확성을 인증하는 검사가 아니라, 별도 판독 단계가 지정 snapshot에 대해 수행됐고 누락 신고를 무시하지 않았는지 확인하는 게이트다.

추가 반례: remap 한 경로 누락, finding 미연결, 판단 산출물 누락, 독립 판독의 요구사항 누락 신고.

### 조치 4 — changed_path_count 정합

코드 재확인 결과 기존 완전본 validator는 `source.changed_path_count`와 `current-diff-paths.txt`를 비교하지 않았다.

다음 두 겹으로 보강했다.

- `harness/acgh/registration_prep.py::apply_plan`: apply 시 현재 diff 경로 수로 Registry `source.changed_path_count`를 재계산하고 Registry도 원자적 쓰기 목록에 포함.
- `harness/registrations/om-temp-1.13.0/validate_registration_bundle.py`: 두 값이 다르면 구조화된 `analysis_error`로 차단.

완전본 관련 검사 26건이 통과했다. Registry source의 다른 provenance 필드는 건드리지 않았다.

### 조치 5 — CI approval 처리

`harness/ci/om_plan_ci.py`에서 CLI 판정 정합 검사는 그대로 유지하면서 CI 반환만 분리했다.

| CLI verdict | CLI exit | CI exit | 표기 |
|---|---:|---:|---|
| pass | 0 | 0 | success |
| approval | 2 | 0 | success-review-ready |
| block | 1 | 1 | failed |
| analysis_error | 3 | 3 | failed |

요약에는 `approval은 배포 승인이 아니라 계획 검토 준비 상태`라고 함께 기록한다. 실제 subprocess의 stdout verdict와 CLI exit가 맞지 않으면 기존처럼 fail-closed한다.

### 조치 6 — 공식 문서 2차 판독

반영 위치:

- `.claude/agents/om-plan-official-doc-reviewer.md`: 공식 snapshot을 다시 읽는 read-only 별도 agent.
- `CLAUDE.md`: upgrade proposal 작성 뒤, `plan check` 전에 agent 결과를 별도 proposal 파일로 기록하는 흐름.
- `.claude/settings.json`·Hook 정책: 지정 agent만 보호 세션에서 허용.

2차 판독은 proposal 작성 agent의 요약을 재사용하지 않고 raw snapshot을 다시 읽는다. 그러나 같은 계열 LLM 검사이므로 ground truth가 아니며, 누락 확률을 줄이는 보조 단계로만 취급한다.

## 3. 남은 위험·결정 필요

1. Q10(upgrade apply의 source/provenance 전이)이 미확정이다. 이번에는 `changed_path_count`만 고쳤으며 provenance를 추측해 바꾸지 않았다.
2. path-remap 검사는 영향 경로의 누락을 잡지만, 제안한 새 경로가 의미적으로 옳은지는 판정하지 않는다. 후속 실제 코드·동작 테스트 책임이다.
3. 독립 문서 판독도 LLM이므로 문서 요구사항을 전부 찾았다고 보장하지 않는다.
4. 실제 GitLab pipeline과 실제 Claude Code 4모드 Hook 반례는 아직 실행하지 않았다.
5. apply 변경은 대조용 완전본 작업 트리에 있고 clean export에는 apply가 없다. 이후 Q10 결정과 함께 운영 반영 경계를 다시 정해야 한다.
6. 작업 트리에는 commit·push가 없으며 두 저장소 모두 의도적으로 수정 상태다.
