## 집중 검토 항목 (깨보기)

1. **§0.5 관리파일 싱크 불변식** (최우선)
   - "코드 변경 → 관리파일을 실제에 맞게 갱신, 불일치 방치 금지"가 **실제로 강제 가능한가.** 매 단위 후 게이트(등록 밖 변경 0 + 매니페스트=실제 일치)가 이 불변식을 빠짐없이 잡나? 어디로 새나(예: 삭제·이동·공유파일·자동생성 파일).
   - 갱신을 LLM이 자기신고로 하면 "코드는 A인데 매니페스트는 A라고 우겨" 통과되나? 검사기가 실제 diff로 재확인하나?

2. **§3 파일 해석 규칙** (가장 중요)
   - 각 규칙(changed_paths·required_changed_paths·계약·path-remap·shared_impact)이 **오해·우회 가능한가.** 특히 upgrade의 path-remap·충돌 자동병합(8-1 확정)에서 엉뚱한 위치/병합이 나올 수 있는 지점.

3. **§4 최소 개발 단위 분해**
   - "레이어(스키마→서비스→UI)별 그룹핑"이 **OpenMetadata 실제 구조에 맞나.** 한 커스텀이 레이어에 안 맞게 걸치는 실제 사례가 있나(예: 마이그레이션 SQL·i18n·생성 파일). 선행작업 순서가 실제 의존과 어긋나는 경우.

4. **§6 게이트**
   - "형식만 통과"로 뚫리나. 각 단위 후 게이트가 divergence를 놓치는 경로. LLM 의미판단(계약 충족) 게이트의 잔여 위험.

5. **A(LLM이 코드 작성)의 근본 위험**
   - om-verify(실제 테스트 실행) 전까지 **실행 검증이 없다.** §6 정적 게이트가 어디까지 막고, 무엇이 verify로 넘어가는지 — 설계가 이 경계를 정직하게 긋고 있나, 아니면 "정적 게이트로 다 잡히는 척"하나.

6. **예전 apply 재활용 타당성** (사람 결정용 실측 — 사용자가 특히 우려)
   - (a) **흐름 불일치**: `registration_prep.py`는 **"개발자가 만든 ID-커밋을 등록"(B형)** 흐름이다. om-apply(A형: LLM이 쓰며 싱크)에서 **무엇이 그대로 재활용 가능하고**(UNOWNED_NET_CHANGE·매니페스트 기록 등), **무엇이 흐름 불일치로 안 맞나.**
   - (b) **현재 정책 부합 여부(중요)**: 이 코드는 **다른 용도의 구버전(2026-07-30, om-plan보다 먼저)**이다. **지금의 관리파일 구조·정책과 부합하는지 자체가 불명.** registration_prep이 읽고 쓰는 매니페스트/레지스트리/계약 스키마·필드가 **현재 것(트랙A 결정 반영본: direct_tests 계약only, per-ID 관계 등)과 어긋나는지 실측.** 어긋나면 재활용 부적합 → A형 전용 신규 로직.
   - 결론: (a)+(b)를 근거로 **재활용 / 부분 재활용 / 신규** 중 선택지와 각 득실. **확정 말고 선택지.**
