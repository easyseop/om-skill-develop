# om-verify 설계 초안 (적대검토 전)

작성일: 2026-08-24. 작성자: Claude. **성격: 구현 전 설계 초안** — 적대검토 + 사람 결정 후 구현지시로 전환.

## 0. 위치·경계

```
om-apply(awaiting_verify 인계) → 【om-verify: 실제 실행·검증·결속】 → om-report(요약)
```
- 합의된 논리 6단계 중 **4(필수 테스트 실행)·5(결과 결속)** 담당 (+3의 최종 확인 일부).
- **verify는 코드·관리파일을 절대 바꾸지 않는다.** 실행하고 판정하고 기록만.
- 최종 상태: `verified` / `failed` / `infra_error`(실행불가≠통과). 종료코드 0/1/3.

## 1. 본체 (기준 설계 — 도구와 무관)

### ① 인계 수신·재검증 (위조 방지)
- om-apply 결과의 결속값(plan digest·candidate SHA/tree·등록자료 digest·required_tests)을 받되 **믿지 않고 재검증**: candidate SHA/tree 실재 확인, 등록자료 digest 재계산 대조, **required_tests는 인계 문서가 아니라 등록 계약에서 재계산**(제안서 값 아님 — 목록 위조 차단).
- 하나라도 어긋나면 `infra_error` fail-closed.

### ② 후보 환경 기동 (V-1, 사람 결정 — 설계 최대 난제)
candidate 코드가 **실제로 떠 있는 서버**가 필요. 선택지:

| 안 | 방식 | 장점 | 단점·위험 |
|---|---|---|---|
| A | **상주 lab에 candidate 배포** (이미지 교체) | 빠름·인프라 재사용 | lab 데이터 오염·이월 영향, "떠 있는 게 진짜 candidate인가" 별도 결속 필수 |
| B | **매회 fresh 빌드·기동** (compose) | 격리·정확 최상 | OM 빌드가 무거움(수십 분+) |
| C | **혼합** — 평시 A(빠른 회귀), 릴리즈 관문은 B(완전 격리) | 균형 | 두 경로 유지 |

- **권고: C** (v1은 A로 시작하되 아래 결속 검사 필수, 릴리즈 시 B).
- **환경↔candidate 결속(못 속임)**: 어느 안이든 실행 직전에 **서버가 정말 그 candidate인지 기계 확인** — `/api/v1/system/version`의 revision/버전 + 배포 이미지 digest를 receipt에 기록하고 candidate와 대조. 불일치 → `infra_error`.

### ③ 계약 테스트 실행 (pytest — 본체)
- 재계산된 required_tests(pytest selector)를 candidate 서버 대상 실행.
- **결정론**: 재시도 없음(간헐은 실패), 부분 실행은 통과 아님, 전체 시간 상한(초과 → infra_error).
- UI가 필요한 계약 테스트는 pytest 안에서 Playwright 사용(기존 방식).

### ④ UI층 부품 슬롯 (test-agent — 채택됨, 교체 가능)
- **계약된 I/O로만 연결**: 입력 = 시나리오 YAML(스킬이 생성 → 스키마 검증), 출력 = report.json·JUnit·종료코드.
- 역할: 커스텀 화면 스모크(콘솔·HTTP 오류) + **UI↔API/DB 대조** + 증거(비디오·trace·절차서).
- 정답원 원칙 유지: 기대값 근거는 **기획 의도(계약)**, 구현 코드 WHERE절 복제 금지(동어반복 함정).
- 파일럿으로 실증됨(72): 세션·SPA·대조 17=17·정형 I/O·실전 검출(instanceCode).
- **부품 실패·부재 시**: 본체(③)만으로도 verify는 성립 — 부품 결과는 별도 게이트로 합산.

### ⑤ 검증 영수증(verify-receipt) — 결과 결속 (논리 5)
- receipt = { candidate SHA/tree · 환경 식별(버전 rev·이미지 digest) · 테스트별 결과(selector→pass/fail·소요) · test-agent report digest · 시작/종료 시각 · 판정 } → **canonical digest**로 봉인.
- **재사용 금지**: receipt는 그 candidate SHA에만 유효. SHA가 바뀌면 무효(재실행 필요). 완료 receipt는 읽기 전용.
- om-report와 사람 승인·배포는 이 receipt를 근거로.

### 판정 규칙
- `verified` = ①재검증 통과 ∧ ②환경 결속 확인 ∧ ③required 전부 pass ∧ ④UI층 게이트 통과(부품 사용 시).
- 하나라도 fail → `failed`. 실행 자체가 안 됨 → `infra_error`. **어느 쪽도 통과 아님.**

## 2. 속임 방지 점검 (적대검토 집중 대상)

- 인계 위조 → ①의 재계산·재검증으로 차단되나? (특히 required_tests 재계산 소스)
- **환경 바꿔치기** → "떠 있는 서버 ≠ candidate" 시나리오를 ②의 결속이 정말 잡나? (rev만으론 부족한가 — 이미지 digest·기동 로그?)
- 테스트 스킵/부분실행 우회 → ③의 "부분≠통과"가 빈틈없나?
- receipt 재사용/짜깁기 → ⑤의 SHA 결속·읽기전용이 충분한가?
- UI층 시나리오의 동어반복(정답원을 구현에서 복제) 방지 장치.

## 3. 사람 결정 목록

- **V-1**: 환경 기동 방식 A/B/C (권고 C).
- **V-2**: UI층 시나리오 범위 — 커스텀 화면 어디까지(전 커스텀? 핵심만?), 정답원(API vs DB) 기준.
- **V-3**: 콘솔 결함(예: instanceCode 파서 에러)의 게이팅 수위 — verify 실패로 볼지, 경고로 볼지. (upgrade 재적용 후엔 사라져야 정상 → 회귀 지표 후보.)
