## 3. 발견 사항 (P0/P1/P2)

### P0
없음. false pass로 직결되는 위조·우회는 발견하지 못했다(관련 반례는 실제로 방어함, §4).

### P1-A (Serious) — validate가 run-request.refs를 재고정(re-pin)하지 않아, input-lock+facts를 다른 로컬 커밋으로 "일관 재작성"하면 approval이 난다

- **근거 파일·줄:** `harness/acgh/plancore/validate.py` `_run_validation_active`
  L363–369 — 재계산 시 `locked_refs_override=stored_lock[...]["commit_shas"]`로
  **저장된 input-lock의 sha를 앵커로 사용**한다. `collect_state`(preflight.py L123–148)는
  override가 주어지면 `binding.pin(request["refs"])`를 **호출하지 않는다.** 즉 validate는
  run-request의 refs를 다시 해석해 저장 sha와 대조하는 단계가 없다.
- **실증(PoC):** 사람이 승인한 `refs.current_custom = shaA`로 preflight한 뒤,
  공격자 커밋 `shaB`(로컬 존재, 전혀 다른 내용) 기준으로 `input-lock.yaml`과
  `discovered-facts.json`을 **일관되게**(digest까지) 재작성하고 run-request는 그대로 두면:

  ```
  run-request.refs.current_custom = shaA (5acc8e36…)  ← 사람이 승인
  validate가 bind한 plan             = shaB (c14e3551…) ← 공격자 커밋
  VERDICT: approval
  ```

  request_digest는 refs(shaA)에서, repositories·facts는 override(shaB)에서 계산되는데
  둘을 잇는 불변식(`pin(refs) == 저장 sha`)이 없어 상호 일관성만 성립하면 통과한다.
- **왜 기존 반례가 못 잡나:** C46은 input-lock의 sha만 바꾸고 facts를 그대로 둬서
  facts 재계산 불일치로 잡힌다. C31/C33은 facts를 바꾸되 proposal의 `expected`나
  self-digest로 잡힌다. **input-lock과 facts를 함께 일관 재작성**하는 경우만 이 경로에
  해당하며, 그에 대한 반례가 없다.
- **위협 모델(정확히):** hook이 켜진 Claude Code 안에서는 이 파일들에 대한 Bash 쓰기가
  차단된다(§4 hook). 따라서 이 구멍은 **hookless/CI·수동 셸**에서만 성립한다 —
  그런데 그곳이 설계(01·02 문서)가 "Hook이 아니라 plan-validate 재계산이 최후 안전망"이라고
  명시한 영역이다. 즉 **최후 안전망 자신의 구멍**이다.
- **완화:** approval의 exit code는 `2`(APPROVAL, `verdict.py:33`)라 naive CI에서
  0(자동 통과)로 뭉개지지 않고 사람 검토로 남는다. 또 공격자는 **로컬에 존재하는 커밋으로만**
  이동 가능하다(임의 위조 불가). 그래도 "기계가 사람이 못 보는 바꿔치기를 잡는다"는
  판매 문구에 대해, 기계는 approval을 내고 refs↔facts 불일치를 **플래그하지 않는다.**
- **c03과의 긴장:** 단순 re-pin은 "preflight 이후 브랜치가 움직여도 무효화하지 않는다"는
  C03(의도된 통과)와 충돌한다. 그래서 이건 순수 버그가 아니라 **설계 결정이 필요한 지점**이다.
  권고: (a) run-request.refs가 리터럴 40-hex SHA면 `pin==저장 sha`를 단언하고, 심볼릭이면
  최소한 결과에 refs·저장 sha 쌍을 노출해 사람이 대조하게 한다. 또는 (b) input-lock을
  run 디렉터리 밖의 무결성 보호 저장소에 두어 "저장 sha가 신뢰 루트"임을 명시적으로 만든다.

### P2-B — 실질 내용이 없는 proposal이 approval을 받는다

- **근거:** `validate.py` `_validate_required_decision_fields`(L169)는 `decisions` 키가

  검사는 특정 키(decisions·findings·shared_impact·crosschecks…)가 있을 때만 발동한다.
- **실증:** `proposal/plan.yaml = {"note": "looks fine to me"}` (decisions·evidence 전무) →
  **VERDICT: approval**, `next_action: review the proposal`.
- **평가:** 설계(05 문서)가 "기계는 findings→checklist 정합까지만, 원문 누락은 사람"이라고
  이미 인정한 한계의 구체적 발현이다. 다만 **비어 있는 계획에 approval**이 찍히면 검토자가
  "게이트 통과=계획 있음"으로 오독할 위험이 있다. 권고: 최소 1개 decision/finding을 요구하거나,
  실질 내용 부재를 결과에 표시.

### P2-C — 경계 lint가 문자열 결합 회피를 못 잡는다

- **실증:** `PREFIX = "BANK" + "-OM-" + "042"` → `boundary_violations()` = `[]`(위반 없음).
- **평가:** 경계 lint는 **우발적 리터럴 유입에 대한 트립와이어**이지 악의적 회피 방어가 아니다.
  경계검토 문서 §8도 "위반 0건 유지"를 조건으로만 걸었다. 항목 1("plancore가 BANK-OM을
  알지 않는가")의 강제 수단이 이 정도임을 명시할 것. (실제 현재 코드에는 우발적 리터럴이
  없음은 확인 — baseline lint 통과.)

### P2-D — hook이 파일명 접미사만으로 신뢰하고, subprocess 쓰기는 hook을 우회한다

- **근거:** `hook_policy.py` `_workflow_action` L57–63은 `token.endswith("om_workflow.py")`
  로 신뢰 명령을 판별한다.
- **실증:** `python evidence/run/proposal/om_workflow.py plan-validate …` → hook `allowed=True`.
  Write는 proposal 디렉터리에만 허용되므로, proposal에 심은 가짜 `om_workflow.py`를 이 경로로
  실행할 수 있고, 그 subprocess의 파일 쓰기는 PreToolUse(Edit/Write/Bash) 단위 검사를 벗어난다.
- **평가:** **false pass는 아니다.** 그렇게 만든 제품/checker 변경은 plan-validate의
  dirty 스캔(`validate.py` L230 `_dirty_paths`)과 checker_catalog_digest 재계산(L363–380)이
  잡아 `analysis_error`가 된다(§4에서 확인). 즉 hook은 경계가 아니고 net은 validate라는
  설계 전제를 재확인할 뿐이다. 권고: 접미사 대신 실제 신뢰 인터프리터/스크립트 절대경로를 매칭.

- `validate`는 `observed`에만 evidence_refs를 요구한다(collectors.py L419). `human_input`·

## 5. C·R 반례를 실제 mutant로 확인한 것

- **재계산 가드가 load-bearing임을 입증:** `validate.py`의
  `stored_facts["canonical_payload"] != recomputed_facts["canonical_payload"]` 비교를
  `pass`로 무력화한 사본에서, "net-custom-paths를 존재하지 않는 경로로 일관 위조(+digest 갱신,
  proposal은 expected 없이 참조)"한 PoC가 **approval**로 통과했다. 원본 복원 시 동일 PoC는
  **analysis_error**로 차단됐다. → 항목 2·8의 재수집 방어가 장식이 아님을 확인.
- **baseline에서 C01~C46(단 C44 제외)·R01~R07에 대응하는 test 75개가 통과.** test 이름과
  본문이 각 결함 시나리오를 실제로 구성함을 정독으로 확인(예: C10 다중 ID→block, C17
  skip≠pass, C38 등록 변경→stale, C46 sha·deployment 변경→analysis_error, R04/R05 append-only).
- **개별 전건 mutation은 하지 않았다.** 시간·범위상 대표 가드 1개만 mutation했고, 나머지는
  baseline 통과 + 코드 경로 정독으로 판정했다. C44는 test에 대응 이름이 없어 **미확인**으로 남긴다.

## 6. 실자료 예행연습 재실행 여부

**재실행하지 않았다.** 사유: 인수인계(07 §4)가 밝힌 대로 예행연습 JSON은
`/private/tmp/om-plan-rehearsal.*`에 있었고 이는 다른 컴퓨터의 임시물이라 첨부 스냅샷에 없다.
저장소에도 plan run의 영구 evidence가 커밋돼 있지 않다(확인: `git ls-files`에
`preparation-plans/om-temp` plan 산출물·`evidence/om-plan*` 없음). 실자료로 수집했다는
"공식 변경 1,702경로·object 3,040개·공유 교차 23개·공식 문서 2개"(07 §4)는 **본 검토가
독립 재현하지 못했으므로 미검증**이다. 지시대로 증거 부재를 성공으로 바꾸지 않는다.
대신 synthetic 저장소 위 PoC(§5)와 baseline suite로 판정했다.
