## 0. 왜 이 문서가 필요한가

지금까지의 "보호 CI"는 **GitHub Actions 워크플로**(`.github/workflows/om-plan-ci.yml`)로
구현됐다. E안의 안전성은 GitHub이 공짜로 제공하던 보증들(신뢰된 fresh checkout, job 격리,
`needs` 그래프, environment required reviewers, actions 권한)에 기대고 있었다.
**GitHub을 안 쓰면 그 보증들이 사라진다.** 코드 로직은 대부분 재사용 가능하지만, "누가
보증하는가"를 대체 환경에서 다시 세워야 한다.

## 1. 그대로 유효한 것 (재사용 — GitHub 비의존)

다음은 provider-neutral이라 GitHub과 무관하게 유지한다.

- `harness/acgh/plancore/preflight.py`, `validate.py` — 지문 계산·재검증·`--expected-input-lock-digest`
  게이트·`review_state`. (E-hardening `1f02e1d3`에서 채택됨)
- `harness/acgh/plancore/paths.py`의 `.pyc` 제외 수정 (`7aaa18f`, 채택됨).
- `harness/ci/om_plan_ci.py`의 6개 함수 — `prepare_request`, `capture_preflight`,
  `package_proposal`, `restore_run`, `rebind_run_request`, `run_fresh_validation`.
  이들은 GitHub이 아니라 **경로·파일·subprocess**만 다루므로 어떤 실행 환경에서도 쓸 수 있다.

## 2. 폐기/보류할 것

- `.github/workflows/om-plan-ci.yml` — **배포 대상 아님.** 삭제하지는 말되(참조 자료), 운영
  경로로 쓰지 않는다. GitHub environment·required reviewers·actions 권한 전제는 무효.

## 3. 코덱스가 다시 세울 것 — GitHub이 주던 보증의 대체

E안의 안전은 아래 5개 성질에 달려 있다. GitHub 없이 각각을 **무엇이 보증하는지** 명시하라.
환경이 무엇인지(내부 CI인지, 사람 수동인지)는 §4에서 사용자가 정한다. 코덱스는 두 경우
각각에 대해 아래를 어떻게 만족시키는지 설계한다. **임의로 하나로 확정하지 마라.**

| 성질 | GitHub이 주던 것 | GitHub 없이 필요한 것 |
|---|---|---|
| ① expected 지문 보관 | job output / secret (LLM 접근 불가) | LLM이 생성·수정 못 하는 보관처: 사람이 손으로 보관, 또는 내부 CI의 보호 저장 |
| ② 비신뢰 proposal 격리 | 별도 job·권한 | proposal을 **데이터로만** 취급하는 별도 프로세스/권한 경계. `package_proposal`은 그대로 쓰되, 이를 **호출하는 쪽**이 LLM 쓰기 밖이어야 함 |
| ③ 신뢰된 checker/product | 매번 fresh checkout(clean) | **매 실행 checker·product를 신뢰된 상태로 확보.** 지저분한/조작된 worktree에서 시작하지 않음(§5와 직결) |
| ④ 사람 intent 게이트 | environment required reviewers | 사람이 `intent_summary`(요청 ref·고정 SHA·모드)를 **본 뒤에** 진행하는 절차. GitHub 승인 화면 대체 |
| ⑤ 판정 근거 | 워크플로 결론이 아니라 fresh validate | `run_fresh_validation`의 종료 코드/stdout만 신뢰. 저장된 `validation-result.json` 바이트 신뢰 금지 |

## 4. 사용자 결정 필요 — 대체 환경 (임의 확정 금지)

- **(A) 내부 CI(GitLab CI·Jenkins·사내 러너 등)를 쓴다** → §3의 ①②③④를 그 CI의 job 격리·
  시크릿·승인 단계로 매핑. `om_plan_ci.py`는 그대로 호출.
- **(B) CI 없이 사람이 수동으로 돌린다** → 최소 절차:
  1. 신뢰된 사람이 신뢰된 머신에서 `plan-preflight` 실행 → 나온 `input_lock_digest`를
     **자기만 아는 곳에 보관**(LLM에게 주지 않음).
  2. `intent_summary`를 사람이 눈으로 확인(④).
  3. LLM은 proposal을 **데이터로만** 제출.
  4. 같은 사람이 `plan-validate --expected-input-lock-digest <보관값>`을 직접 실행,
     **그 종료 코드로만** 판정(exit 2=review_ready, 그 외=진행 불가).

코덱스는 (A)·(B) 각각의 구체 절차 문서와, `om_plan_ci.py`를 GitHub 없이 호출하는
얇은 래퍼(있다면)를 제시한다. 실제 채택은 사용자 몫이다.

## 5. 이번에 **필수로 승격**되는 것 — .pyc 방어심화

Claude 재검토(P2, `pyc수정_재검토_결과`)에서 남긴 이론적 약점: `directory_digest`가 `.pyc`를
제외하므로, checker의 `__pycache__`에 조작된 `.pyc`를 심으면 **지문은 그대로인데 그 코드가
실행**될 수 있다(실증됨). 이 약점은 **"checker가 매번 신뢰된 fresh 상태"라는 GitHub 보증이
있을 때만 도달 불가**였다.

**GitHub을 안 쓰면 그 보증이 사라진다.** 사람 수동(B)이나 재사용되는 사내 러너(A)에서
checker worktree가 깨끗하지 않을 수 있으므로, **이 통로를 반드시 닫아라.** 택1:

- (a) 권장 — catalog 지문 계산 직전 대상 디렉터리의 `__pycache__` 제거.
- (b) checker 실행을 `sys.dont_write_bytecode=True` / `PYTHONDONTWRITEBYTECODE=1`로 고정
  **하고** 시작 시 기존 `__pycache__` 제거(생성만 막으면 기존 조작본이 남으므로 제거 병행).
- (c) hash 기반 `.pyc` invalidation(`checked-hash`) 사용.

**수용 기준:** benign `.py`와 header가 일치하도록 조작한 `.pyc`를 심어도, 실행되는 코드가
`.py` 원본과 다르면 (a)~(c) 중 택한 방식으로 **차단되거나 무력화**됨을 test로 증명한다.
