# 2. Codex 답변 중 틀리거나 불완전한 것

**2-1 [오류·실증] input_lock_digest 하나로 충분하지 않다 (upgrade).**
input-lock canonical의 required는 `run_id, mode, request_digest, repositories, registration,
checker_catalog_digest`뿐 — **문서 필드 없음**(schema L13). validate는 문서를 git이 아니라
**저장된 `official-doc-sources.yaml`에서 재확인**한다(validate.py L360-367, `collect_documents=False`).
따라서 문서 바이트는 input_lock_digest에 결속되지 않는다. §5 PoC에서 악성 문서 교체가
input_lock_digest 불변인 채 `approval`. → **수정 필요.**

**2-2 [불완전] "한 파이프라인 CI"가 너무 넓다 (질문5).** 안전 조건은 "한 파이프라인"이 아니라
**LLM 단계가 (a)이전 preflight job의 output, (b)workflow 정의, (c)expected 값 전달 경로를
변경할 수 없음**이다. 같은 파이프라인이어도 LLM 단계가 이전 job artifact나 워크플로 정의를
쓸 수 있으면 무력(scenario #6와 동형).

**2-3 [누락] preflight 의도 자체는 E의 보호 밖 (질문6).** E는 "preflight가 확정한 것"을
validate까지 무결하게 옮길 뿐, **그 preflight가 사람 의도의 run-request로 시작됐는지는
보증하지 않는다.** LLM이 처음부터 다른 run-request로 preflight하면 expected digest는 그
잘못된 계획을 인증한다. → **run-request(또는 그 request_digest)를 사람/신뢰주체가 확인하는
경계**가 session-start 또는 preflight 승인 지점에 별도로 필요하다.

**2-4 [누락] verdict enum 변경 위험 (질문9).** `acgh/verdict.py`의 `APPROVAL/VERDICTS/
SEVERITY_RANK/EXIT_CODE`는 **release·patchkill·upgrade_run·initial_registration 등 20+ 비-plan
모듈이 공유**한다. enum을 `review_ready`로 바꾸면 전 시스템 파급 → **금지.**

# 3. E의 정확한 신뢰 경계

expected input-lock digest는 다음을 **모두** 만족하는 주체가 제공해야 한다:
(a) 그 값을 LLM이 생성·선택할 수 없다, (b) LLM이 이전 preflight output·workflow 정의·전달
채널을 변경할 수 없다, (c) fail-closed(값 부재=analysis_error). 질문4 경우별 판정:

| 실행 형태 | 판정 | 근거 |
|---|---|---|
| 사람이 신뢰 CLI로 preflight 실행 + digest 보관 | **안전** | 단 사람이 run-request **내용**을 검토했다는 전제(§2-3). digest만 맹목 수령이면 무효 |
| 보호 CI preflight job output → 후속 validate job | **조건부 안전** | LLM 단계가 그 job output·workflow 정의를 **수정 불가**할 때만(§2-2) |
| LLM이 preflight·validate·CLI 인자 모두 선택 | **불안전** | scenario #6, E 무력 |
| LLM이 읽기/쓰기 가능한 파일·환경변수에 expected 저장 | **불안전** | Codex #3과 동일, 같은 권한 값은 변조 가능 |

# 4. 최종 verdict 의미와 expected 누락 정책 (질문1·2·4)

**한 가지 의미로 고정:** `review_ready`는 **외부 expected digest 대조가 성공한 뒤에만** 나오는,
"기계 무결성 검증 통과 + 사람이 계획 **내용**을 검토할 준비가 됨"을 뜻한다. 승인이 아니다.

- **expected 누락 / 형식 오류 / 불일치 → 전부 `analysis_error`(fail-closed).** review_ready 도달 불가.
- **비검증 preview가 필요하면** 별도의 **명시적 unverified 명령/표시**로 분리하고 **절대
  review_ready로 부르지 않는다.** → "누락 시 analysis_error"와 "review_ready 의미"는 서로
  다른 상태라 모순 없음(질문4).

# 5. input-lock digest 하나로 충분한가 (질문3·5) — 실증

**initial/feature/change: 충분.** 모든 facts가 pinned SHA + `registration.state_digest`
(디렉터리 digest)에서 결정론적으로 재계산되므로, input_lock_digest가 그 입력을 고정하면
facts는 종속변수다.

**upgrade: 불충분 (PoC).** 공식 문서를 악성으로 교체(버전 토큰 1.0.1 유지):
```
input_lock_digest 변화? : False   (before=after= sha256:9d6873f5…)
VERDICT: approval
```
문서 바이트는 facts에만 있고(official-documents fact), validate는 저장된 sources에서 재확인하므로,
`{snapshot + sources.yaml + discovered-facts.json}` 일관 재작성이 input-lock을 안 건드린 채 통과한다.

**권고:** 다음 중 하나.
- (권장) **input-lock canonical_payload에 `official_doc_sources_digest` 필드 추가** → 단일
  외부 digest(input_lock_digest)가 전 모드를 커버. run-request/facts와 함께 이미 재계산되므로
  결속 비용 작음.
- (대안) 외부 기대값을 **`(input_lock_digest, discovered_facts_digest)` 쌍**으로 확장.
  facts digest가 문서 byte_digest와 모든 git 사실을 포함하므로 커버되나, 전달 값이 둘로 늘어남.

# 6. 빈 계획과 no_change 최소 규칙 (질문8)

**모든 모드 공통:** proposal은 `decision ≥ 1` **또는** `finding ≥ 1` **또는** 명시적 `no_change`
블록 중 하나를 반드시 포함. 셋 다 없으면 `block`.

**`no_change` 최소 필드(제안):**
- `no_change: true`
- `rationale`: 무변경 사유(자연어)
- `evidence_refs`: 무변경을 뒷받침하는 **재계산 사실**로의 역참조(예: `official-upgrade-paths`
  또는 `observed-change-paths`가 빈 배열임을 가리키는 pointer). 근거 없는 no_change=block.
- `affected_customization_ids`: 무변경 판단이 적용되는 ID 목록.

→ `{"note":"ok"}`·빈 proposal은 셋 다 불충족이므로 `block`. 정상 무변경은 근거 결속으로 통과.
전체 완결성 판정이 아니라 **최소 비어있지 않음 floor**임(설계 05의 "완결성은 기계 밖" 한계와 구분).

# 7. 이번 구현 범위 vs 후속 P2 (질문10)

**이번 P1-A 구현에 포함:**
1. 최종 validate의 **expected digest 게이트**(§5 권고: input-lock에 doc-sources digest 편입).
2. expected 누락/오류/불일치 → `analysis_error`.
3. **verdict enum 불변**, review_ready는 **plan-result의 표시 필드/next_action** 또는
   plan-local `review_state`로(§2-4, 질문9). exit code·Schema·기존 소비자 무영향.
4. 빈 proposal `block` + `no_change` 최소 필드(§6).
5. **run-request 의도 경계** 명시(§2-3): session-start 또는 preflight 승인에서 사람이
   run-request(또는 request_digest)를 확인.

**후속 분리 P2 (P1-A 신뢰 경계와 무관, 번들 금지 — blast radius 억제):**
- C44 대응 test 부재.
- 경계 lint 문자열 결합 회피(3차 P2-C).
- hook 신뢰 판별의 파일명 접미사 → 절대경로(3차 P2-D).

# 9. 최종 판정

**수정한 E안 구현.**

- E 골격은 채택하되, (1) upgrade 문서 결속(§5), (2) run-request 의도 경계(§2-3), (3) verdict
  enum 불변·표시 처리(§2-4), (4) 빈 proposal/no_change 최소 규칙(§6)을 반영한 **수정 E안**으로
  구현한다. "E안 그대로"는 §5 오류 때문에 불가.
- **신규 발견의 영향 구분:** upgrade 문서 결속(§5)은 **이번 결정에 직접 영향**(구현 범위에 포함).
  C44·경계 lint·hook 절대경로는 **별개 후속 P2**(§7).
- **심각도 유지:** P1-A는 현 개발 단계 잠복 P1, `/om-plan`이 실제 배포를 게이트하는 순간
  release-blocker. 시나리오 #6이 열려 있으면(expected가 LLM 출처면) 무인 운영에서 P0.
