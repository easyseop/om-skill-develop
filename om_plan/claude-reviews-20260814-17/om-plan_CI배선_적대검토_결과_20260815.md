# 2. P0 / P1 / P2

**P0: 없음. P1: 없음.** review_ready를 부당 획득하는 false pass·격리 우회를 발견하지 못했다.
격리·fresh 검증 로직은 실행 반례로 모두 fail-closed였다(§4).

## P2-1 (robustness, fail-closed) — checker_catalog_digest가 `__pycache__/*.pyc`를 포함해 cross-runner에서 catalog 불일치를 일으킨다

- **근거:** `harness/acgh/plancore/paths.py` `directory_digest`는 `root.rglob("*")`의 모든
  regular file를 digest한다(`.pyc` 제외 안 함). `checker_catalog_digest`는
  `plancore`·`integrations/om` 디렉터리 digest다(`preflight.py` `_checker_catalog_digest`).
  Python이 bytecode를 쓰면(기본) import 시 `__pycache__/*.pyc`가 생겨 그 디렉터리 내용이 변한다.
- **재현:** 지정 tree를 git 저장소로 만들어(`.git` 부여) `PYTHONDONTWRITEBYTECODE` 없이
  cross-runner 재현 실행 →
  ```
  exit_code: 3   verdict: analysis_error
  REASONS: ['recomputed input lock does not match the stored lock']
  ```
  `PYTHONDONTWRITEBYTECODE=1`로 같은 실행 → `exit_code: 2, REASONS: []`.
- **workflow 실측:** `.github/workflows/om-plan-ci.yml`에 `PYTHONDONTWRITEBYTECODE` 설정 없음.
  코드(`om_workflow.py`·`om_plan_ci.py`·`paths.py`)도 `sys.dont_write_bytecode`를 켜지 않고
  `directory_digest`가 `.pyc`를 제외하지 않는다.
- **영향:** **fail-closed다**(잘못된 review_ready로 이어지지 않음, false pass 아님). 다만 실제
  workflow에서 preflight job과 validate job이 **서로 다른 시각에 checkout**하므로, 기본
  timestamp 기반 `.pyc`는 source mtime을 embed해 두 runner의 `.pyc` 바이트가 달라질 수 있고,
  그러면 catalog가 매번 어긋나 **파이프라인이 review_ready에 영원히 도달하지 못할** 위험이 있다.
  즉 보안 결함은 아니나 **기능이 실환경에서 동작하지 않을 수 있는 견고성 결함**이다.
- **권고(택1):** (a) `directory_digest`에서 `__pycache__`/`*.pyc` 제외, (b) catalog를 git-tracked
  source로만 계산, (c) workflow의 preflight·validate job에 `PYTHONDONTWRITEBYTECODE=1` 설정.
  (a)가 근본적이다. **실제 GitHub 실행 전 최종 확인 필요**(§6).

## P2-2 (신호 의미, 실환경 확인 필요) — all-skipped green과 approval=exit2(red)의 반전

- **근거:** 모든 job에 `if: github.ref == default_branch` 가드가 있다. 비-default branch에서
  `workflow_dispatch`하면 4개 job 전부 skip → workflow 결론이 실패로 뜨지 않는다(green 계열).
  반대로 정상 경로의 review_ready는 `approval`→exit 2 → job이 non-zero로 **red**가 된다
  (`om_plan_ci.run_fresh_validation`가 `completed.returncode`를 그대로 반환, §4 확인).
- **위험:** "workflow green = 통과"로 읽는 소비자에게, **green은 '아무 것도 안 돎'을,
  red는 '실제 검증돼 review_ready'를** 뜻할 수 있는 **반전**. E01 공격(비-default dispatch가
  green으로 오독)과 직결된다.
- **판정:** GitHub의 required-check·skip 렌더링 실제 의미는 저장소 설정에 달려 있어
  **실환경 없이 확정 불가**(§6). 소비자가 반드시 `validate` job의 성공(skip 아님)과 step
  summary의 `review_state`를 근거로 삼아야 하며, Q9(exit 2 처리)와 함께 정해야 한다.

# 3. 수용 조건 판정

| 조건 | 판정 | 근거 |
|---|---|---|
| **A. protected digest 분리** | **성립** | digest는 신뢰 preflight의 `input_lock_digest`에서만 유도(`capture_preflight`), proposal artifact에서 유도 경로 없음. `untrusted-proposal` job은 `needs: intent-review`만이라 `needs.preflight.outputs` 접근 불가(GitHub needs 컨텍스트는 직접 needs만 노출). proposal 파일은 `trusted-run/proposal/` 하위로만 들어가 루트 `input-lock.yaml`을 덮지 못함. artifact 이름은 run_id+attempt로 유일, `overwrite:false` |
| **B. 비신뢰 proposal 격리** | **성립** | `package_proposal`이 symlink·비 yaml/json·절대경로·traversal·비어있지 않은 output을 전부 차단(§4에서 8/8 직접 확인). yaml/json 데이터만 복사, 실행·import 없음. PYTHONPATH는 checker/harness만 |
| **C. fresh validation만 신뢰** | **성립(+P2-1 견고성)** | `run_fresh_validation`이 저장 result 파일을 안 읽고 subprocess stdout+exit만 신뢰. verdict↔exit↔review_state 3중 대조, 불일치는 `analysis_error`(exit 3). `approval`은 exit 2로 나가 0으로 세탁 불가(§4 확인). 단 cross-runner catalog는 P2-1 |
| **D. upgrade 문서 결속** | **성립** | `official_doc_sources_digest`가 input-lock canonical에 편입돼 `input_lock_digest`(=expected)에 결속(E-hardening 검토서 E06 재확인). 신뢰 preflight run artifact는 `untrusted` job(actions:none, overwrite:false)이 못 바꿈. validate는 저장 snapshot으로 재검증(collect_documents=False), URL/repo-relative 모두 snapshot 기준이라 재fetch 없음 |
| **E. 사람 intent 경계** | **부분·실환경 미검증** | 코드가 `intent_review_required`·`intent_summary`를 요구·노출하고 운영 문서가 "순서 미보증"을 명시(정직). 그러나 **실제 사람 게이트는 GitHub environment `om-plan-intent-review`의 required reviewers 설정**이며 저장소 밖 설정이라 **미검증**. `OM_PLAN_INTENT_REVIEW_ENFORCED` var 체크는 필요조건이나 충분조건 아님(reviewers 미설정+var=true면 실게이트 없음). all-skipped green은 P2-2 |
