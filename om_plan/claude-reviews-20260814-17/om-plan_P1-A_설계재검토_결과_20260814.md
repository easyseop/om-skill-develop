# 1. 사실 정정

**1-1. (Codex #1·#2가 맞음, Claude 3차 결과 보강)** 3차 검토는 P1-A를 "2파일(input-lock+facts)
일관 재작성"으로 실증했다. Codex의 지적대로 **run-request까지 포함한 3파일 재작성이 더 근본**이며,
이는 3차 결과가 미처 실증하지 않은 부분이다. 본 재검토에서 3파일 PoC를 실증했다(§2).

**1-2. (Claude (a)/(b)안의 한계 = Codex #1이 맞음)** 3차 결과는 권고 (a)로 "리터럴 SHA면
`pin(refs)==저장 sha` 단언"을 제시했다. 이는 **2파일 재작성만 막고 3파일 재작성은 못 막는다.**
근거: 3파일 재작성에서는 `run-request.refs.current_custom`도 shaB가 되므로
`pin(shaB)==저장(shaB)`가 성립해 통과한다. → (a)/(b)는 단독 해결책에서 **제외**한다.

**1-3. (C03에 대한 정밀화)** 3차 결과는 "(a)와 C03의 긴장"을 언급했으나, 코드상 C03의 refs는
**리터럴 SHA**다(`_repos`가 `rev-parse HEAD` 결과를 refs로 사용). 리터럴 SHA는 브랜치가 움직여도
자기 자신으로 resolve되므로, (a)는 **리터럴 SHA에 한해 C03과 충돌하지 않는다.** C03과 충돌하는
것은 **심볼릭 ref를 현재값으로 다시 resolve하는 (A)안**이다(§4). 즉 3차 결과의 "순수 버그가
아니라 결정 사안" 판단은 유효하나, 충돌 주체는 (a)가 아니라 (A)로 정정한다.

**1-4. (Codex #4·#5가 맞음)** "run 밖 위치"만으로는 신뢰가 생기지 않는다 — 본 재검토 반례 #4로
확인 가능(receipt도 같은 권한이면 재작성됨). 이 점에서 Codex #5는 정확하다.

# 2. 위협 모델과 신뢰 경계

## 2-1. 현재 설계 문서의 위협 모델 (질문 1)

`om_plan/02_사실파일_위조검증.md`의 명시적 전제:
- "Hook은 Edit/Write만 막는다. LLM은 **Bash로도 파일을 쓸 수 있다**" → **쓰기 능력은 이미 전제됨.**
- 대응은 "수정을 막는다"가 아니라 "**수정되면 반드시 들킨다**(Git에서 재계산 가능)".

**핵심 정정:** 이 전제는 "input-lock·facts는 Git에서 재계산 가능"이라 위조가 탐지된다고 본다.
그러나 **run-request 자체는 Git에서 재계산되는 대상이 아니다** — 사람의 의도(어느 ref를
계획하는가)를 담은 입력이며, 재계산의 **기준**이지 재계산의 **결과**가 아니다. 문서의 위협
모델은 "재계산 결과물(facts)의 위조"는 다루지만 "**재계산 기준(run-request)의 위조**"는
다루지 않는다. Codex의 확장 위협 모델은 **문서에 명시적으로 포함돼 있지 않다.** 이것이 P1-A의
근본이다: run 안의 모든 파일이 같은 권한으로 쓰기 가능하면, "기준"과 "결과"의 구분이 무너진다.

## 2-2. 실증 (질문 2) — 3파일 동시 재작성

원본 harness를 읽기 전용 import하고 `/tmp` 임시 저장소에서 실행:

```
사람이 승인한 shaA : f05194c02c79   (run-request.refs.current_custom)
공격자 커밋 shaB   : b185928acd29   (전혀 다른 내용, 로컬 존재)
공격: run-request + input-lock + discovered-facts 3개를 shaB로 일관 재작성
validate가 bind한 : b185928acd29 (== shaB)
VERDICT: approval
```

**추가 실증 — 구별 불가능성:** shaB로 "일관 재작성한 공격 산출물"과 "애초에 shaB로 승인한
합법 계획"의 digest를 비교하면:

```
합법 shaB 계획   input_lock_digest: sha256:97cded1ee9af8…
공격 3파일재작성 input_lock_digest: sha256:97cded1ee9af8…   ← 동일
facts digest 동일? : True
```

→ **run 내부에는 두 경우를 구별할 어떤 신호도 없다.** 사람의 의도는 원래 run-request에만
있었는데 공격자가 그것까지 덮어썼기 때문이다. **이로써 "run 내부 상호 대조 강화"라는 방향
전체가 무효임을 증명한다**(Codex #2 확정).

## 2-3. 신뢰 경계 결론

같은 사용자 권한 하에서 run 디렉터리(및 그 안/밖의 같은 권한 파일) **전체가 공격자
재구성 가능**하다. 따라서 신뢰 루트는 반드시 **공격자가 위조할 수 없는 외부 값**이어야 한다.
후보는 셋뿐이다: (i) **실행 주체가 전달하는 expected digest**(사람 명령/CI 잡 설정),
(ii) **서명/MAC**(LLM이 갖지 못한 키), (iii) **실권한 분리**(별도 CI 단계·사용자가 preflight
산출을 캡처, LLM에게 read-only). "run 밖 파일"은 이 셋 중 하나를 동반할 때만 의미가 있다.

# 4. 단일 권고안

**(E) — validate의 APPROVAL을 외부 전달 expected digest에 결속한다. 필요 시에만 (C+)로 승격.**

구체:
1. `plan-preflight`가 산출하는 `input_lock_digest`(SHA·tree·request_digest·checker_catalog_digest를
   이미 캡슐화)를 **실행 주체가 보관**한다(사람이 눈으로/CI 잡이 시크릿·잡 출력으로).
2. `plan-validate`에 `--expected-input-lock-digest`(및 원하면 facts digest) 인자를 추가한다.
3. 이 인자가 주어졌는데 **재계산 digest와 불일치하면 `analysis_error`**. 인자가
   **없으면 `approval`을 낼 수 없고** 최대 `review_ready`(사람이 digest를 직접 대조해야 함)로 제한.
4. 완전 무인 CI가 필요하면 (C+): preflight 산출을 **LLM이 못 만드는 서명/CI artifact**로 봉인.

**왜 receipt 서브시스템(C)이 아니라 (E)인가:**
- receipt의 보안 가치는 "run 밖"이 아니라 "위조 불가"에 있다(§2-3). (E)는 그 위조 불가를
  **이미 권한을 가진 실행 주체(사람/CI)**에게 맡겨, receipt 파일·형식·수명·재사용 방지 로직을
  **새로 만들지 않는다.** run_id를 expected 대조에 포함하면 반례 #7(다른 run receipt 재사용)도
  자동 처리된다.
- (E)는 신뢰 루트를 "누가 validate를 실행시켰는가"라는 **이미 존재하는 권한 경계**에 둔다.
  이는 `/om-plan`의 전제("검증기는 독립 판정기")와 정합하며, LLM에게 새 신뢰를 주지 않는다.

**과설계 반대 명시:** Codex의 receipt는 무인 CI 시나리오에서만 (C+) 형태로 정당하다.
그 외(사람이 validate를 돌리거나, CI 잡이 preflight→validate를 한 파이프라인에서 캡처)에는
(E)가 더 작고 강하다. receipt를 "run 밖 파일"로만 구현하면 **보안 이득 0, 복잡도만 증가**다.

# 5. 구현 시 반드시 성립해야 할 불변식

1. **APPROVAL 필요조건:** 재계산한 `input_lock_digest`(및 facts digest)가 **run 밖에서 전달된
   기대값과 일치**할 때만 APPROVAL. 기대값 부재 시 최대 `review_ready`.
2. **기대값 위조 불가:** 기대값은 LLM/같은 권한 프로세스가 생성할 수 없는 채널로만 전달
   (사람 입력·CI 시크릿·서명). 같은 권한 파일 저장은 금지(반례 #4).
3. **C03 보존:** 기대값은 **preflight 당시 SHA를 캡슐화한 digest**이지 브랜치 현재값이 아니다.
   따라서 브랜치 이동은 허용되고 SHA 바꿔치기만 차단된다.
4. **run 결속:** 기대 대조는 `run_id`를 포함해 다른 run의 값 재사용을 차단.
5. **fail-closed:** 기대값 누락·손상·불일치는 전부 `analysis_error`(성공 추정 금지).
6. **경계 유지:** 무결성(이 불변식)과 승인자 신원(Q6)을 섞지 않는다(§7).

# 7. C03·Q6·P2-B 영향

**C03 (질문 4):** C03의 보호 대상은 **브랜치 이름이 아니라 preflight 당시 확정된 commit SHA**다
(test: 리터럴 SHA refs, 새 커밋 추가로 브랜치 이동해도 `approval`). 기대 digest에 그 SHA를
캡슐화하면 **브랜치 이동은 허용하고 바꿔치기만 차단** — C03과 P1-A 수정이 양립한다. (A)안만이
C03을 깬다.

**Q6 (질문 6):** (E)는 **검증기 입력 무결성**(재계산이 preflight 산출과 같은가)을 다루며,
**승인자 신원**(누가 승인했는가)과 무관하다. 기대 digest는 "값의 무결성"을 보증할 뿐 "전달한
사람이 누구인지"를 인증하지 않는다. 따라서 **Q6을 보류한 채 (E)를 안전하게 구현할 수 있다.**
단 경계: "사람이 전달하는 expected digest"는 **전달 채널의 신뢰**를 가정하는 것이지 신원 인증이
아니다. 채널 신뢰(CI 시크릿·같은 사람이 실행)와 신원 인증(Q6)을 혼동하지 말 것.

**P2-B (질문 9):** 단순 문구 문제가 **아니다.** 두 층이다.
- (의미) `approval`(exit 2)의 실제 의미는 "**사람이 검토할 준비가 됨**"이지 "승인/완결"이 아니다.
  용어가 과대 주장한다. **`review_ready`로 의미를 분리**하는 것이 정직하다(승인은 사람의 별도 행위).
- (완결성) 빈 proposal이 그 verdict를 받는 것은 **최소 완결성 게이트 부재**다. 전체 완결성은
  기계가 판정 불가(설계 05)지만, **최소 비어있지 않음(decision 또는 finding ≥1, 또는 명시적
  no-op 정당화)**은 값싸게 강제 가능하고 전체 완결성과 구별된다. → 최소 floor는 `block`,
  그 위 검토 준비는 `review_ready`로 구분 권고.

  에서는 **잠복 P1**이다. 그러나 `/om-plan`의 verdict가 **무인/CI 맥락에서 실제 배포를 게이트하는

  **운영 Skill 설치 전 해결이 필수인 pre-operational blocker**로 다뤄야 한다.
- 권고는 **(E)**, 무인 CI가 필요할 때만 **(C+)**. Codex의 receipt는 방향은 맞으나 "run 밖 파일"
